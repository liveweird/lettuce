# Internationalization (i18n) (`web/`)

Moved out of `web/CLAUDE.md` so it is read on demand; `web/CLAUDE.md` keeps a mandatory-read pointer and the always-on rules.

The SPA is **N-language by architecture** (v2.20.0) via **react-i18next** (`web/src/i18n.ts`); the shipped bundles are English (THE default and fallback everywhere) and Polish, with neither special-cased beyond that. All user-facing strings go through `const { t } = useTranslation()` / `<Trans>` — **no hardcoded UI text**. Conventions:

- **The language set is the build-time constant `SUPPORTED_LANGUAGES` in `i18n.ts`**, mirrored by the server's `dictionaries/Languages.kt` (they must agree — the server validates dictionary payload language keys against it). Only EN is statically imported (its typed `en` tree is the key canon AND the runtime fallback); every other language's bundle is auto-discovered from `locales/<lang>/` via `import.meta.glob` (the `AREA_MOUNT` map handles the four filename≠area cases). **Adding a language** = a complete `locales/<lang>/` folder (29 area files, parity-gated) + one code in `SUPPORTED_LANGUAGES` + one `NATIVE_LANGUAGE_NAMES` line + `common.languageName.<lang>` in EVERY language's common.json + one `EMOJI_I18N` line in `components/EmojiPicker.tsx` + one `DAYJS_LOCALES` line in `i18n.ts` (the calendar locale, v3.5.0 — a `Record` over the non-EN languages, so a missed line fails `tsc`) + the server constant + a parameter on the server's `LocalizedText` (every email text becomes a compile error until translated) — the Record types, the parity test, and the Kotlin compiler each fail loudly on a missed step. **Non-EN bundles are lazy (v4.15.1 — the PL JSON alone is ~170 KiB minified, the old ~150KB trigger):** `import.meta.glob` is no longer eager, only EN is in `resources` (`partialBundledLanguages`), and `loadLanguage(lang)` registers a language's bundle AND its dayjs calendar locale (memoized; EN and registered languages resolve at once). `main.tsx` waits for the detected language before the first paint (no English flash) and **`switchLanguage(lang)` is THE way to change language** (header switcher, `writeSession`'s server-stored language, EditUser self-edit) — a bare `i18n.changeLanguage("pl")` renders English fallbacks until the bundle arrives. `switchLanguage` is **latest-call-wins**: it writes `lettuce.lang` synchronously, takes a request token, and a call whose bundle resolves after a newer call (PL then EN; or account A's pending switch when account B signs in — `writeSession` always switches on a login and compares against `targetLanguage()`, the pending target, on a refresh) never applies; a superseded call resolves quietly, the newest one rejects when its bundle cannot load (callers `.catch` and log). Sign-in (`api/auth.ts`) and the first paint (`main.tsx`) wait for the bundle through `loadLanguageWithin`/`switchLanguage`, capped at 1 s, so there is no English flash. Code that renders text in a language OTHER than the UI's (`t(…, { lng })`, e.g. CreateUser's onboarding draft) must `await loadLanguage(lng)` first. Build: each non-EN language is ONE chunk (`i18n-<lang>`, a name-function group in `vite.config.ts` — locale JSON + dayjs locale), so a new language needs no config edit. **Tests:** `test/setup.ts` deliberately does NOT preload Polish (a global preload masks code that forgets to load a language); a test that needs `pl` does `import "../test/withPolish"`, and the lazy paths are tested on fresh module graphs (`i18n.test.ts`, `api/session.language.test.ts`).
- **Server-carried localized content** (dictionary entries, the career triple, pulse rotating-question snapshots) arrives as `values: {lang: value}` maps with `en` always present; **every display site resolves through `pickLocalized(values, lang)` in `utils/localized.ts`** (blank-guarded EN fallback) — never index a values map directly. Dictionary editing is EN-required/others-optional (`utils/dictionaryForm.ts`; a blank non-EN input is omitted from the PUT — the server's omit-to-clear contract); the editor shows English beside ONE picker-chosen translation column and the read-only view a per-entry language-count badge with a popover (v2.23.0 — both constant-width at any language count).
- **Emails are language-specific since v2.21.0**: every server-composed email (password reset, MFA code, welcome, notification mirror) renders in the RECIPIENT'S stored language (V61 `users.language`, EN fallback) — the server-side texts live as `LocalizedText(en, pl)` values (`infra/mail/LocalizedText.kt`), whose constructor arity is the server's parity gate. **The user language is ONE synced property**: the header switcher saves it to the server on switch (`setUserLanguage`), and `persistSession` applies the login/refresh response's `language` to the UI — so signing in restores the user's language on any device, and an admin change propagates at the ≤15-min silent refresh.

- **Resources** live in `web/src/locales/{en,pl}/<area>.json`, one file per area (`common`, `appShell`, `auth`, `dashboard`, `feedback`, `kudos`, `oneOnOne`, `goals` — mounted as area `goal` — `teamKpis` — mounted as area `teamKpi` — `performanceReviews` — mounted as area `performanceReview` — `daysOff`, `pulse`, `users`, `teams`, `templates`, `dictionaries` — mounted as area `dictionary` — `notifications`, `notificationPreferences`, `alerts`, `changelog`, `tour`, `org`, `career`, `impactLog`, `succession`, `sharing` — the v4.8.0 document-sharing dialog, banner and Shared screen, `activity` — the v4.9.0 activity log, `integration` — the v3.0.0 integration-clients admin screen); `i18n.ts` merges them into a single `translation` namespace, so keys read `area.key` (e.g. `t("feedback.editTitle")`). **Keys are typed**: `src/i18next.d.ts` augments i18next's `CustomTypeOptions` with `typeof en` from `i18n.ts` (the `@public`-tagged export — knip can't trace the d.ts consumer), so every `t()` call and `i18nKey` is compile-checked against the EN tree — a typo or removed key fails `tsc`/`npm run build`. Conventions that keep it working: fields holding a key are typed `ParseKeys` (from `i18next`), never `string` (the `labelKey`/`successKey`/nav-label pattern); functions taking a translator take `TFunction`, never a hand-written `(key: string) => string`; dynamic keys built from a statically known union type-check as-is, and the few genuinely dynamic sites (wire enum values in history/notification renderers) go through `dynamicKey` in `utils/i18nKey.ts` — use it only when the union is truly unknowable to TS, never to silence a typo; test stubs cast via `as unknown as TFunction`.
- **`common.*` is the shared source**: actions, field labels, table/pagination, filters, and the enum labels `common.status.*` / `common.visibility.*` / `common.role.*`. Reuse it instead of duplicating; build Mantine `Select` option labels from `t()` at render so they translate.
- **Creation-verb convention (v1.15.2):** buttons that open a create screen say **"New <thing>"** / PL **"Nowy/Nowa/Nowe <thing>"** (New team, New user, New template, New feedback, New alert, New 1:1, New goal, New team KPI — and the create screens' titles reuse the same wording); in-form list adders say **"Add …"** / **"Dodaj …"** (Add point, Add a provider, Add to team); the create form's submit button is the bare `common.action.create` **"Create"** / **"Utwórz"**. New buttons must pick the tier that matches their behavior, not mix verbs.
- **Keep key parity vs EN for every shipped language** — a shipped bundle is all-or-nothing: every English key must exist in each `locales/<lang>/` (language-specific plural variants like PL's `_few`/`_many` are expected), enforced by `locales/parity.test.ts` (auto-discovers language folders; also pins folders == `SUPPORTED_LANGUAGES`). Use i18next interpolation (`{{name}}`) and plural keys (`_one/_few/_many/_other`) rather than string concatenation.
- **Polish term for "feedback" is the loanword `feedback`, declined** (feedback / feedbacku / feedbacki / feedbacków), *not* "opinia". `teams.json` is the style reference.
- **Polish voice/gender convention:** **inclusive slash forms**, active/direct voice, same tense and meaning as the English — 3rd person `"{{provider}} odmówił/a…"`, 2nd person `"Poprosiłeś/aś…"`, participles `"wylogowany/a"`. Spell out irregular feminines in full (e.g. `"usunął/usunęła"`, never `"usunął/a"`). Do **not** use impersonal/passive dodges (`"Poproszono…"`, `"Wylogowano Cię"`).
- **Tests** render English: `web/src/test/setup.ts` imports `../i18n` and forces `en`, and English keys resolve byte-identically to the old literals, so text-based assertions keep working. Every test `MantineProvider` (the shared `src/test/render.tsx` wrapper and each file-local one) must pass **`env="test"`** — since Mantine 9.4 the Popover/Combobox dropdown is `display: none` until Floating UI's `hide` middleware sees a real bounding box, which never happens in happy-dom, so Select-option clicks silently fail without it. The language switcher is `web/src/components/LanguageSwitcher.tsx` (header) — a Mantine `Menu` of NATIVE language names (`NATIVE_LANGUAGE_NAMES`, deliberate constants: readable before switching, and `Intl.DisplayNames` yields lowercase forms); choice persists in `localStorage` (`lettuce.lang`) and updates `<html lang>`.
- **Scope:** frontend chrome is translated, and both **feedback history events** and **notifications** are localized client-side — the server stores them structurally (`type` + `params`), with no rendered string (see `.claude/docs/features/feedbacks.md` / `.claude/docs/features/notifications.md`). No server-generated user-facing text remains English.
