# Feature tutorials (v3.14.0, `web/`)

Moved out of `web/CLAUDE.md` so it is read on demand; `web/CLAUDE.md` keeps a mandatory-read pointer here.

Dedicated per-feature guided walkthroughs on demand, built on the same Joyride machinery as the whirlwind tour (`tourSupport.ts`). **Since v3.23.0 the whirlwind tour is a menu presentation only** — 24 steps (23 for a non-manager): the welcome, one step per left-nav leaf/group in navbar order (Succession manager-only, each feature leaf carrying its nav gate), the four header icons and the help/replay icon; no step navigates, and feature depth belongs to the tutorials. The whirlwind's e2e walk (`tour.spec.ts`) pins the step totals and the landmark order. A **tutorial** is a short, role-filtered, read-only step list that only NAVIGATES and SPOTLIGHTS stable chrome (tabs, header buttons, form controls, nav links) — it never clicks, never opens a real record, and never mutates. Tutorial infrastructure lives in `web/src/tutorials/` (`types.ts` holds the `TutorialId` union + the `TutorialDef` type; each tutorial is a `TutorialDef` value in its own file like `feedbacks.tsx`; `index.ts` only aggregates them into the `TUTORIALS` record) and is launched on demand via `TutorialButton` in the feature hub's `PageHeader` actions (`useTour().startTutorial(id)`; no auto-start, no seen flag of its own — `markSeen` is whirlwind-only, with one v4.4.1 addition: a tutorial started over the RUNNING whirlwind marks the whirlwind seen, since it replaces it before the whirlwind's own Finish/Abandon can — otherwise the first-login auto-start came back on the next sign-in). **Since v4.4.0 the account menu lists them too** (`components/TutorialsSubmenu.tsx`, a left-opening `Menu.Sub` — the menu hangs off the header's right edge): "Quick app tour" (the whirlwind) plus every tutorial in `TUTORIAL_MENU_ORDER` (`tutorials/index.ts`, navbar order) that passes its nav leaf's gates — the def's `feature` and the optional `managerOnly` (succession). A menu entry calls `useTour().launchTutorial(id)`, which opens the tutorial's `home` first and starts it once that pathname shows (any tab counts); the launch is held as pending against the location key it left from, so the first route change settles it — home starts it, anywhere else (e.g. the discard guard held the navigation and the user then left elsewhere) drops it. Unit tests driving the submenu click items with `fireEvent` (a userEvent click never reaches a submenu item's onClick under happy-dom); the real click path is `e2e/tests/tutorials-menu.spec.ts`. The tutorial builder spreads `READ_ONLY_STEP_DEFAULTS` (`blockTargetInteraction: true, overlayClickAction: false, dismissKeyAction: false` — react-joyride 3.x leaves elements clickable by default) into each step so the UI is inert; finish and abandon navigate to the tutorial def's `home` page. Step render props may carry rich content (the lifecycle step embeds `FeedbackLifecycle`, passed as `render: (text) => <Stack gap="sm"><Text size="sm">{text}</Text><FeedbackLifecycle /></Stack>`); `data-tour="<area>-<thing>"` naming pins the spotlights to stable anchors never data rows. Localized in `locales/{en,pl}/tutorials.json` (`tutorials.<id>.steps.*`, `tutorials.<id>.launch`). To add the next tutorial: create a `TutorialDef` file under `tutorials/`, extend the `TutorialId` union in `tutorials/types.ts`, the `TUTORIALS` record and `TUTORIAL_MENU_ORDER` (the account-menu listing) in `tutorials/index.ts` — plus `managerOnly: true` on the def when its nav leaf is manager-only — add the `tutorials.<id>.*` keys in BOTH language JSON files, mount a `TutorialButton` in that feature hub's `PageHeader`, add any new `data-tour` anchors to stable chrome (the anchor smoke test and the e2e walk both fail on a missing one), write a test file (audience count, navTo table, render-page anchor smoke test, never-mutates fetch pin), and contribute a read-only e2e scenario — provider/tooltip/builder need no changes.
