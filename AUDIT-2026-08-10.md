# Repository audit handoff — 2026-08-10

This document is an implementation handoff for the repository-wide review performed on
2026-08-09/10. It records findings only; the audit itself made no production-code changes.

The repository was clean when this document was created. Before acting on an item, follow
`AGENTS.md`, `CLAUDE.md`, the relevant `.claude/docs/features/*.md` document, and, for web work,
`web/CLAUDE.md`. API changes must follow `api-guidelines/API-GUIDELINES.md` and keep route/service
behavior, focused tests, OpenAPI, generated TypeScript schema, and conformance checks synchronized.

## Executive summary

The codebase has high aggregate test coverage, broad feature-level E2E coverage, a strongly checked
OpenAPI contract, and structurally synchronized English and Polish resources. It is in good overall
condition, but it is not exhaustive or free of architectural debt.

The highest-risk finding is that a business mutation, its history event, and its in-app
notifications do not share one transaction. A later event or notification failure can therefore
return an error after the business state has already changed, and notification fan-out can be
partial. The next material design gap is the lack of a documented lost-update defense for ordinary
full-document writes.

Other findings concern deliberate E2E omissions, stale documentation/tutorial coverage, frontend
duplication and responsibility hotspots, a small amount of confirmed unused code, and incomplete
visual/responsive/accessibility assurance.

## Prioritized findings

### AUD-001 — Mutation, event, and notification persistence is not atomic

**Priority:** High

**Status:** Confirmed architectural/reliability gap

**Evidence**

- Goal transitions commit through `goalService.transition(...)`, then create each notification and
  the history event separately in
  [`server/src/main/kotlin/goals/GoalRoutes.kt`](server/src/main/kotlin/goals/GoalRoutes.kt).
- The same route-side orchestration pattern is used by feedback and other event-producing features.
- [`server/src/main/kotlin/infra/db/EventLog.kt`](server/src/main/kotlin/infra/db/EventLog.kt) opens a
  new `suspendTransaction` for every event.
- [`server/src/main/kotlin/notifications/NotificationService.kt`](server/src/main/kotlin/notifications/NotificationService.kt)
  opens a separate transaction for notification insertion. Ordinary multi-recipient fan-out calls
  it once per recipient; pulse has a dedicated batch path.
- The email mirror intentionally runs after the notification commit and is best-effort. That part
  is not the issue; the concern is durable domain state, event history, and in-app notifications.

**Risk**

- A request can return `500` after its business mutation has committed.
- Durable history can be missing for a state change.
- Multi-recipient in-app notification fan-out can be partially persisted.
- A client retry may encounter an already-completed transition and receive a different error.

**Required decision**

Define the intended consistency model. Likely options include a transaction-aware unit of work for
domain mutation plus event/in-app notification records, or a transactional outbox with explicit
delivery semantics. Do not silently treat durable history as best-effort unless product and audit
requirements are changed and documented.

**Acceptance criteria**

- The transaction boundary is documented for domain mutation, history, in-app notification, and
  email delivery.
- A forced event/notification persistence failure cannot leave an undocumented partial outcome.
- Multi-recipient behavior is all-or-nothing or explicitly outbox-driven and retryable.
- Focused integration tests prove failure and retry behavior.
- Relevant feature, notification, persistence, and observability documentation is updated.

### AUD-002 — Full-document writes have no general lost-update defense

**Priority:** Medium–high

**Status:** Confirmed API design gap

**Rule:** API-CACHE-003

**Evidence**

There is no `If-Match`, entity-tag conditional write handling, `412 Precondition Failed`, version
field, or generally documented alternative for ordinary full-document `PUT`/`DELETE` operations.
Domain state-machine guards protect some transition endpoints but do not prevent two simultaneously
valid edits from overwriting one another.

**Risk**

Users can unknowingly overwrite a newer edit with stale form data.

**Acceptance criteria**

- Inventory concurrency-sensitive `PUT` and `DELETE` operations.
- For each one, document and implement either conditional requests/version checks or a justified
  domain-level alternative.
- Stale writes have a deterministic response and focused tests.
- If the HTTP contract changes, update OpenAPI, regenerate `web/src/api/schema.ts`, update clients,
  and run the API review/conformance workflow.

### AUD-003 — E2E coverage is strategic rather than exhaustive

**Priority:** Medium

**Status:** Test-strategy gap; not evidence of broken behavior

There are 33 Playwright specifications, and every major product feature has at least one journey.
[`e2e/README.md`](e2e/README.md) deliberately excludes login lockout, token refresh/expiry, the
exhaustive authorization/visibility matrix, and the backend-only `DRAFT -> WITHDRAWN` transition.
Those choices have lower-layer coverage and are reasonable when kept explicit.

Current UI capabilities without clear browser-level coverage include:

- email-notification preferences;
- notification deletion;
- performance-review revert-to-draft and draft deletion;
- days-off rejection and unpaid variants;
- actually toggling and asserting dark mode;
- the three admin-only guided-tour steps.

The Playwright configuration uses Desktop Chrome only. No mobile/tablet project, cross-browser
matrix, visual regression suite, or automated accessibility scan was found.

**Acceptance criteria**

- Decide which listed paths warrant browser coverage and which remain intentionally lower-layer.
- Record every deliberate omission in `e2e/README.md` with its compensating test layer.
- At minimum, add E2E coverage for any path whose integration risk is not exercised elsewhere.
- Decide whether responsive, accessibility, and dark-theme verification are release requirements;
  if so, encode them in repeatable tests rather than relying only on manual inspection.

### AUD-004 — Product and architecture documentation contains concrete drift

**Priority:** Medium

**Status:** Confirmed documentation defect

**Evidence**

- [`CLAUDE.md`](CLAUDE.md) calls the migration catalog V1–V50; migrations and the catalog reach V52.
- The module order described in `CLAUDE.md` differs from
  [`server/src/main/resources/application.yaml`](server/src/main/resources/application.yaml),
  including dashboard placement.
- [`README.md`](README.md) describes a small peer-feedback application and omits major current
  capabilities such as 1:1s, goals, KPIs, reviews, days off, pulse, Kudos, MFA, alerts, and feature
  controls.
- [`web/README.md`](web/README.md) is a setup/API-types document, not a feature or end-user guide.
- `e2e/README.md` refers to a “serial suite” although the current configuration uses multiple
  projects/workers with serialized special phases.
- The measured frontend coverage comment in `web/vite.config.ts` is materially higher than the
  current result.

**Acceptance criteria**

- Documentation agrees with executable configuration and the migration directory.
- The root README accurately summarizes the current product scope without duplicating feature
  deep-dives.
- Coverage comments either reflect reproducible current data or avoid embedding volatile figures.
- E2E execution wording describes the actual concurrency model.

### AUD-005 — The guided tour is a navigation tour, not a complete functional tutorial

**Priority:** Medium–low

**Status:** Product-documentation gap

The guided tour has 51 steps and provides broad navigation coverage. It introduces surfaces and
tabs but does not teach the create/edit/transition/approval workflows within them. It also omits the
email-notification preferences entry present in the account menu: compare
[`web/src/App.tsx`](web/src/App.tsx) with
[`web/src/components/tourSupport.ts`](web/src/components/tourSupport.ts).

Only the manager-oriented tour is substantially exercised in E2E; admin-only, HR, non-manager, and
feature-disabled variants primarily rely on unit tests.

**Acceptance criteria**

- Explicitly define whether the feature is a navigation tour or an end-user tutorial.
- If it remains a navigation tour, cover every intended navigation item or document exclusions.
- If it is meant to teach functionality, add task-oriented guidance for the major lifecycle flows
  and role/feature variants.
- Keep EN and PL tour content synchronized.

### AUD-006 — Frontend duplication and large responsibility hotspots

**Priority:** Medium

**Status:** Confirmed maintainability debt

**Evidence**

- The clone scan found 9.90% duplicated TSX lines.
- Goal and Team KPI detail/action flows have substantial parallel structure, for example
  [`web/src/pages/ViewGoal.tsx`](web/src/pages/ViewGoal.tsx) and
  [`web/src/pages/ViewTeamKpi.tsx`](web/src/pages/ViewTeamKpi.tsx).
- Similar filter/pagination/table blocks occur across alerts, feedbacks, goals, performance reviews,
  team KPIs, and 1:1 pages.
- Similar mutation-form flows occur in password, team, template, user, notification-preference, and
  feature-setting screens.
- Approximate large-file hotspots:
  - `web/src/api/client.ts`: 1,755 lines; session/token behavior plus all feature API wrappers
  - `web/src/App.tsx`: 632 lines; shell, routing, menus, feature gates, account actions, and tour
  - `OneOnOneService.kt`: 794 lines
  - `DaysOffService.kt`: 767 lines
  - `FeedbackService.kt`: 655 lines

The backend package boundaries and feature-local routing are coherent. This is not a recommendation
to abstract every repeated line: extract only stable domain/UI patterns with at least two real
consumers and preserved accessibility/i18n behavior.

**Acceptance criteria**

- Identify repeated structures that change together and are genuinely the same abstraction.
- Split the API client by concern without changing its public behavior or refresh/session
  guarantees.
- Prefer focused hooks/components/helpers over configuration-heavy generic components.
- Preserve semantic tables, labels, `data-tour` anchors, query invalidation, and inline error/toast
  conventions.
- Refactors retain or improve focused coverage and reduce measured duplication.

### AUD-008 — Generic unique-conflict responses do not identify the existing resource

**Priority:** Low

**Status:** Partial API guideline gap

**Rule:** API-ERR-007

[`server/src/main/kotlin/plugins/ErrorHandling.kt`](server/src/main/kotlin/plugins/ErrorHandling.kt)
maps a generic database unique violation to `409 Resource already exists` without the conflicting
resource URI in `ProblemDetail.instance`. Some domain-specific conflict paths already provide more
useful context, but generic unique conflicts cannot.

**Acceptance criteria**

- Inventory unique conflicts that can safely identify an existing caller-visible resource.
- Populate `instance` for those cases, while preserving existence-disclosure and authorization
  rules from API-ERR-006.
- Keep a generic non-disclosing response where identifying the record would leak inaccessible state.
- Update focused response tests and OpenAPI examples if the documented shape changes.

### AUD-009 — Aggregate coverage is high but frontend margins and local hotspots are narrow

**Priority:** Low

**Status:** Assurance gap

The configured coverage gates pass, but frontend statements exceed their floor by only 0.39
percentage points and functions by 0.44. Low line-coverage files include pulse charts/results/cycles,
the action-items editor, alert form fields, goal-close behavior, create-team, and days-off budget
components. Backend branch coverage exceeds its floor by 2.22 points; much of its uncovered branch
count is generated serialization/boot/error behavior rather than core service logic.

**Acceptance criteria**

- Prioritize meaningful state, permission, error, and boundary tests in low-covered active features.
- Avoid tests whose only purpose is raising a percentage without asserting behavior.
- Refresh or remove stale “current actual” comments.
- Raise floors only after coverage has enough headroom to avoid unrelated-change churn.

### AUD-010 — Localization is structurally synchronized, but semantic parity is not gated

**Priority:** Open point

**Status:** No confirmed defect; residual quality risk

- EN and PL each have 22 locale area files.
- Approximately 1,538 English leaf keys were inspected.
- [`web/src/locales/parity.test.ts`](web/src/locales/parity.test.ts) checks file parity,
  plural-aware key parity, placeholders, and empty strings.
- Static usage review found no confirmed unused translation keys; apparent candidates were dynamic
  context/key-prefix use.
- Notification email prose is maintained separately in Kotlin, creating a possible semantic drift

**Acceptance criteria**

- Retain structural parity tests.
- Decide whether release review requires a bilingual human/content pass.
- For notification wording, either document the intentionally separate UI/email copy or introduce a
  parity mechanism appropriate to the two delivery channels.
- Preserve the repository's inclusive Polish forms and established terminology.

## API review summary

The API specification is strongly aligned with tested implementation behavior:

- all 132 declared operations were exercised by runtime conformance;
- responses, content types, methods, paths, and status codes are validated for shared test clients;
- generated frontend types match the committed contract;
- Spectral has no errors.

Limits that must not be mistaken for full proof:

- only 558/782 declared operation/status pairs were exercised;
- after excluding generic declared `500` responses, 92 non-500 variants remain unexercised;
- request bodies are deliberately not fully validated by the runtime plugin;
- tests using the default Ktor test client can bypass the conformance plugin; see
  [`server/src/test/kotlin/OpenApiConformance.kt`](server/src/test/kotlin/OpenApiConformance.kt).

Manual checklist result, counted per stable rule ID:

- pass: 41
- new fail/partial: 2 (`API-CACHE-003`, `API-ERR-007`)
- registered-gap rules: 9
- not applicable: 1 (`API-VER-004`, because there are no deprecated operations)

Registered gaps remain accepted project gaps rather than new findings: correlation response headers,
validators and general cache policy, `Retry-After`/rate-limit headers, idempotency keys, HTTP/1.1
edge behavior, SLA/terms metadata, and some inline schema documentation.

## UI/UX assessment

Source-level conventions are coherent:

- theme-wide styling is centralized;
- success mutations use the shared fixed-vocabulary toast pattern;
- errors remain inline;
- semantic tables, labels, and stable tour anchors are broadly tested;
- list, query invalidation, and link patterns are shared in many areas;
- build output remains code-split below Vite's 500 kB warning threshold.

No concrete visual inconsistency was confirmed. However, without a fresh rendered walkthrough or
repeatable responsive/accessibility/visual tests, visual coherence is supported by implementation
discipline rather than fully certified.

## Suggested implementation order

Do not combine every item into one change. A practical sequence is:

1. **Design decision:** AUD-001 consistency model. Implement separately because it affects multiple
   features and persistence semantics.
2. **API design decision:** AUD-002 concurrency semantics, followed by contract and client changes.
3. **Low-risk truth fixes:** AUD-004 documentation and AUD-007 unused code.
4. **Test strategy:** AUD-003 and AUD-009; add only the journeys and branches selected as valuable.
5. **Incremental refactors:** AUD-006, one stable duplication family or responsibility boundary per
   change.
6. **Product/content decisions:** AUD-005 and AUD-010.
7. **Small API improvement:** AUD-008, after reviewing disclosure implications per resource.
