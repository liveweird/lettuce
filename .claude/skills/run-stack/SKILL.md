# Running, packaging, and deploying the lettuce stack

## Packaging

Package the server for deployment with `./gradlew :server:installDist` (output under `server/build/install/server/`, launcher `bin/server`). **Do not use `:server:buildFatJar`** — the shadow plugin collapses the duplicate `META-INF/services/org.flywaydb.core.extensibility.Plugin` descriptors and the fat JAR NPEs at startup inside Flyway's plugin registry. `installDist` keeps each dependency JAR separate, so Flyway's `ServiceLoader` discovery works exactly as under `:server:run`.

## JVM footprint tuning

JVM footprint tuning is baked into the `application {}` block in `server/build.gradle.kts` via `applicationDefaultJvmArgs` = `-XX:+UseSerialGC -Xmx256m -XX:TieredStopAtLevel=1`, so it flows into both `bin/server` (→ Docker image) and `:server:run` (the Gradle `test` task is unaffected). Measured on a 512 MiB Linux container: baseline G1 drifts **~345→410 MiB RSS** as it grows its heap, vs a steady, deterministic **~270 MiB** with these flags (**~25% lower and predictable**); startup is ~1.6 s either way, so the win is memory, not startup. SerialGC removes G1's per-heap overhead (~75 MiB); `-Xmx256m` caps a heap that holds no large caches (drop to `192m` to trim ~25 MiB more); C1-only (`TieredStopAtLevel=1`) trims code-cache + C2-compiler memory (~50 MiB) at the cost of peak CPU-bound throughput (irrelevant here — **remove that flag if the service ever runs hot**). Override per-deploy with `JAVA_OPTS`/`SERVER_OPTS` (the launcher appends both). Container ceilings match: `mem_limit: 512m` in `docker-compose.yaml`, `resources.limits.memory: 512Mi` (request `320Mi`) in `k8s/app-deployment.yaml`. This was evaluated instead of a GraalVM native-image migration, which the reflection/ServiceLoader-heavy stack (Ktor config modules, Flyway, Exposed, OTel, Logback, java-jwt) makes costly for little benefit on a long-running internal service.

## Running the full stack

Two ways to run, sharing the same `docker-compose.yaml`:

- **One command (clone & run / demo):** `docker compose up --build` builds the SPA, builds the server, starts PostgreSQL, runs Flyway on boot, and serves everything at `http://localhost:8080` (Swagger at `/openapi`); a Mailpit mail catcher runs alongside — outbound email (password resets, welcome mails, the v2.3.0 notification mirror, v2.4.0 MFA sign-in codes) is readable at `http://localhost:8025` (API: `GET :8025/api/v1/messages`). Tear down with `docker compose down` (add `-v` to drop the DB volume).
- **Local development (hot reload, unchanged):** `docker compose up postgres` + `./gradlew :server:run` + `cd web && npm run dev` (Vite on `:5173`, proxying `/api` → `:8080`).
- **Local Kubernetes (OrbStack):** the deployment is written for a TLS-terminating **ingress-nginx** front door at a real hostname (`k8s/templates/app-ingress.yaml`). ⚠ **Community ingress-nginx was RETIRED in March 2026** (https://kubernetes.io/blog/2026/01/29/ingress-nginx-statement/) — no further security patches; this manifest is the LOCAL-PROOF reference only, and any real production deployment MUST migrate to a maintained controller or the Gateway API (a behavior migration — re-verify the proxy contract: `HTTP_PROXY_HOPS`, the narrowed `XForwardedHeaders` list, the 308/HSTS/XFF-replacement assumptions, and `ProductionHttpTest`). Order: (1) `docker build -t lettuce-app:latest .`; (2) install the controller once — `kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v1.15.1/deploy/static/provider/cloud/deploy.yaml` then `kubectl wait -n ingress-nginx --for=condition=ready pod -l app.kubernetes.io/component=controller --timeout=180s` (its admission webhook rejects Ingresses until the pod is Ready); read its LoadBalancer EXTERNAL-IP (`kubectl get svc -n ingress-nginx ingress-nginx-controller` — OrbStack hands every LB the node IP) and pick the host `lettuce.<that-ip>.nip.io` (resolves without touching /etc/hosts; the Mac also resolves `<svc>.<ns>.svc.cluster.local` / `.k8s.orb.local` via the system resolver — `dscacheutil -q host -a name …`, NOT `dig`); (3) create the out-of-band config BEFORE applying — the two Secrets `lettuce-secrets` (command in `k8s/templates/secret.yaml`) and the TLS cert `lettuce-tls` (self-signed recipe with the host as SAN in `k8s/templates/tls-secret.yaml`; cert-manager in real deployments), plus the ConfigMap that carries the public URL: `kubectl create configmap lettuce-config --from-literal=MAIL_APP_URL=https://$HOST`; (4) apply the host-agnostic workloads with `kubectl apply -f k8s/` (deployment/service/postgres/PVC — non-recursive on purpose so `k8s/templates/` is skipped: `kubectl apply` over an existing Secret REPLACES its values, and re-applying a placeholder would swap the real `JWT_SECRET` for the burned one and fail the app closed on its next restart — verified with a server dry-run, 2026-09-04), then the Ingress from its template: `sed "s#lettuce.example.com#$HOST#g" k8s/templates/app-ingress.yaml | kubectl apply -f -`. **The Ingress lives in `k8s/templates/` on purpose** so the directory apply can never revert its substituted host, and the deployment carries NO baked hostname (`MAIL_APP_URL` comes from the `lettuce-config` ConfigMap) — so `kubectl apply -f k8s/` is safe to re-run without clobbering per-deployment values (the pre-hardening recipe re-applied `app-ingress.yaml`/`app-deployment.yaml` from the directory after the sed, silently reverting the host + `MAIL_APP_URL` to the placeholder). The three per-deployment values that must agree: the Ingress host (twice), the `lettuce-config` `MAIL_APP_URL`, and the cert SAN. Then browse `https://$HOST/` (self-signed → accept the warning; curl `-k`). `kubectl get ingress app` shows the host/address. The `k8s/` manifests are kompose-derived from `docker-compose.yaml` with these fixes baked in: the app image is the locally built `lettuce-app:latest` with `imagePullPolicy: IfNotPresent` (OrbStack's cluster shares the Docker image store — no push needed), the postgres healthcheck is a proper argv-list exec probe (kompose emits it as one unrunnable string) doubling as the readiness gate, the app Service is `ClusterIP` behind the Ingress (was `LoadBalancer` until v3.6.2 — switching a LIVE Service can be rejected because of the allocated nodePort: `kubectl delete svc app` first, then apply; `kubectl port-forward svc/app 8081:8080` for pod-direct debugging), and the app exposes dedicated health endpoints (`plugins/Health.kt`): **`/healthz`** (liveness — process-alive only, never hits the DB, so a DB outage does not restart-storm the pod) and **`/readyz`** (readiness — a cheap DB round-trip; 503 while the DB is unreachable). A **`startupProbe` on `/healthz`** gives JVM boot + Flyway up to ~150s before the liveness clock starts. **Every probe still sends `X-Forwarded-Proto: https`** — the header the ingress sets; without it production mode answers the plain-HTTP probe with a 301 to `https://<pod-ip>/` that the kubelet FOLLOWS (same host) into a refused `:443`, so probes never pass and the pod crash-loops (the v3.6.1 incident). After rebuilding the image, `kubectl rollout restart deployment/app` picks it up. **What the ingress does for you (ingress-nginx defaults):** plain `http://$HOST/` answers a 308 to https at the edge (the app's own 301 fires pod-direct only), `X-Forwarded-For` is REPLACED with the real client IP (raise `HTTP_PROXY_HOPS` only for an APPENDING chain — see `application.yaml` `http.proxyHops`), and `Strict-Transport-Security` is overwritten by the controller (HSTS policy = its configmap). **Pod-direct access in production mode** (port-forward) gets the app's 301 to `https://<host>/` — for API checks send `-H 'X-Forwarded-Proto: https'` (trusted because of `HTTP_BEHIND_PROXY=true`). **Running the e2e suite against the cluster** needs a DEVELOPMENT-mode app with pristine seeds, and a production boot purges the seeds for good (demo users soft-deleted, admin rotated whenever `ADMIN_INITIAL_PASSWORD` is set — nothing restores them): `kubectl scale deployment app postgres --replicas=0`, delete + re-apply `k8s/postgres-data-persistentvolumeclaim.yaml`, scale postgres up, `kubectl set env deployment/app KTOR_DEVELOPMENT=true MAIL_TRANSPORT=log ADMIN_INITIAL_PASSWORD-`, scale app up, keep `docker compose` DOWN (a host Mailpit on :8025 makes the three mail specs time out — they skip without it), then `cd e2e && E2E_BASE_URL=https://$HOST E2E_INSECURE_TLS=1 npm test` (expect 100 passed + 3 skipped). Back to production: re-apply the deployment from the manifest (restores the `ADMIN_INITIAL_PASSWORD` secretKeyRef) and `kubectl rollout status deployment/app`. **Teardown:** `kubectl delete -f k8s/` removes the workloads *including the DB volume* (the `local-path` storageclass reclaim policy is Delete) — the Secrets and the ingress controller stay (`kubectl delete secret lettuce-secrets lettuce-tls`, `kubectl delete -f <the controller manifest>` if wanted); to stop the workloads but keep the data, `kubectl scale deployment app postgres --replicas=0` instead. **Database only:** apply just the three `postgres-*` manifests — but the Service is ClusterIP, so host access needs `kubectl port-forward svc/postgres 5432:5432`; for local dev `docker compose up postgres` remains the preferred path (never run both against host `:5432` — they are separate databases with separate volumes). **Secrets:** both deployments consume the `lettuce-secrets` Secret via `secretKeyRef` (`JWT_SECRET`, `POSTGRES_USER`/`POSTGRES_PASSWORD`, `ADMIN_INITIAL_PASSWORD`, `DATA_ENCRYPTION_KEY`, optional `SMTP_USER`/`SMTP_PASSWORD`); never apply the templates (the JWT placeholder is on the burned list, so the app fail-closes at startup). The app deployment runs production mode (`KTOR_DEVELOPMENT=false`, `HTTP_BEHIND_PROXY=true`, `HTTP_PROXY_HOPS=1`, and `MAIL_APP_URL` from the `lettuce-config` ConfigMap); for throwaway plain-HTTP browser testing without the ingress, flip `KTOR_DEVELOPMENT` to `"true"` in `k8s/app-deployment.yaml` (HTTPS redirect/HSTS off, seed credentials tolerated, exactly like the compose demo).

The root `Dockerfile` is a 3-stage build: (1) `node` builds `web/dist`, (2) `eclipse-temurin:21-jdk` runs `:server:installDist`, (3) `eclipse-temurin:21-jre` runtime bundles the install image **and** the built SPA, sets `WEB_STATIC_DIR=/app/web`, and runs `bin/server`. The runtime JRE matches the build stage and the Gradle toolchain (`jvmToolchain(21)`) so the app ships on the LTS JVM the test suite runs against — bump all three together to move JVMs. The `app` Compose service points the `POSTGRES_*` env vars at the `postgres` service host and waits on its healthcheck. `.dockerignore` keeps build outputs / `node_modules` out of the build context; `.git` is **included** on purpose — the SPA build stage reads the commit sha/timestamp from it for the version stamp (see "Build version stamp" in `web/CLAUDE.md`).
