# Running, packaging, and deploying the lettuce stack

## Packaging

Package the server for deployment with `./gradlew :server:installDist` (output under `server/build/install/server/`, launcher `bin/server`). **Do not use `:server:buildFatJar`** — the shadow plugin collapses the duplicate `META-INF/services/org.flywaydb.core.extensibility.Plugin` descriptors and the fat JAR NPEs at startup inside Flyway's plugin registry. `installDist` keeps each dependency JAR separate, so Flyway's `ServiceLoader` discovery works exactly as under `:server:run`.

## JVM footprint tuning

JVM footprint tuning is baked into the `application {}` block in `server/build.gradle.kts` via `applicationDefaultJvmArgs` = `-XX:+UseSerialGC -Xmx256m -XX:TieredStopAtLevel=1`, so it flows into both `bin/server` (→ Docker image) and `:server:run` (the Gradle `test` task is unaffected). Measured on a 512 MiB Linux container: baseline G1 drifts **~345→410 MiB RSS** as it grows its heap, vs a steady, deterministic **~270 MiB** with these flags (**~25% lower and predictable**); startup is ~1.6 s either way, so the win is memory, not startup. SerialGC removes G1's per-heap overhead (~75 MiB); `-Xmx256m` caps a heap that holds no large caches (drop to `192m` to trim ~25 MiB more); C1-only (`TieredStopAtLevel=1`) trims code-cache + C2-compiler memory (~50 MiB) at the cost of peak CPU-bound throughput (irrelevant here — **remove that flag if the service ever runs hot**). Override per-deploy with `JAVA_OPTS`/`SERVER_OPTS` (the launcher appends both). Container ceilings match: `mem_limit: 512m` in `docker-compose.yaml`, `resources.limits.memory: 512Mi` (request `320Mi`) in the rendered `k8s/templates/app-deployment.yaml`. This was evaluated instead of a GraalVM native-image migration, which the reflection/ServiceLoader-heavy stack (Ktor config modules, Flyway, Exposed, OTel, Logback, java-jwt) makes costly for little benefit on a long-running internal service.

## Backup and restoration

Follow `.claude/docs/backup-and-restore.md` for the isolated rehearsal procedure,
verification evidence, and separate encryption-key recovery requirements. A successful
local rehearsal does not establish off-host retention or point-in-time recovery.

## Running the full stack

Choose the workflow that matches the environment:

- **One command (clone & run / demo):** `docker compose up --build` builds the SPA, builds the server, starts PostgreSQL, runs Flyway on boot, and serves everything at `http://localhost:8080` (Swagger at `/openapi`); a Mailpit mail catcher runs alongside — outbound email (password resets, welcome mails, the v2.3.0 notification mirror, v2.4.0 MFA sign-in codes) is readable at `http://localhost:8025` (API: `GET :8025/api/v1/messages`). Tear down with `docker compose down` (add `-v` to drop the DB volume).
- **Local development (hot reload, unchanged):** `docker compose up postgres` + `./gradlew :server:run` + `cd web && npm run dev` (Vite on `:5173`, proxying `/api` → `:8080`).
- **Kubernetes (release application image):** release deployments accept only a registry-published content digest. A full commit SHA tag is useful metadata but remains mutable and is not a deployment identity. Obtain and verify the registry-reported digest after the authorized publication step, then set an operator-local variable such as `IMAGE_REF=registry.example/organization/lettuce@sha256:<verified-64-lowercase-hex-digest>`. No publication target or application digest is configured by default. Render and review the Deployment without contacting a cluster: `scripts/render-app-deployment.sh "$IMAGE_REF" > release-app-deployment.yaml`. The renderer is deterministic and fail-closed: missing values, tags (including full-commit tags), malformed or uppercase digests, local image names, and a changed template sentinel all fail without emitting a manifest. Run `scripts/test-render-app-deployment.sh` after changing the renderer or template. Validate the reviewed output against the target cluster with `kubectl apply --dry-run=server -f release-app-deployment.yaml`; after the required deployment checks and backup rehearsal, apply that same file with `kubectl apply -f release-app-deployment.yaml` and watch `kubectl rollout status deployment/app`. Never substitute or apply `k8s/templates/app-deployment.yaml` directly.

- **Kubernetes infrastructure and front door:** `kubectl apply -f k8s/` applies only the host-agnostic app Service and PostgreSQL resources. The app Deployment, Ingress, and secret examples live under `k8s/templates/`, so a directory apply cannot revert the reviewed application digest, hostname, or secrets. Create `lettuce-secrets`, `lettuce-tls`, and the `lettuce-config` ConfigMap out of band before deploying; keep the Ingress host, `MAIL_APP_URL`, and certificate SAN aligned. Render the Ingress host from `k8s/templates/app-ingress.yaml` and apply it separately. Never recursively apply `k8s/templates/`: the placeholders are deliberately unusable, and replacing an existing Secret with the committed example would make the application fail closed. Deleting `k8s/` deletes the PostgreSQL Deployment, Service, and PVC but no longer deletes the app Deployment; delete `deployment/app` separately only when teardown is intended. Deleting the PVC destroys the database because the local-path storage class uses a Delete reclaim policy.

- **Local Kubernetes proof environment:** the manifests model a TLS-terminating front door and production-mode app. Community ingress-nginx was retired in March 2026 and is only the historical local-proof reference; production must use a maintained controller or Gateway API and re-verify the proxy contract in `.claude/docs/security.md`. The application Deployment still requires a published, verified digest even on a local cluster. There is no local `lettuce-app:latest` exception because a Docker image ID is not a registry manifest digest. Use root Compose for clone-and-run development. The app remains a ClusterIP Service behind the front door. Its startup, readiness, and liveness probes send `X-Forwarded-Proto: https` so production HTTPS enforcement does not redirect kubelet to an unavailable pod port 443; `/healthz` is process-only and `/readyz` checks PostgreSQL. Pod-direct production checks must likewise send `X-Forwarded-Proto: https`. The Deployment runs with `KTOR_DEVELOPMENT=false`, `HTTP_BEHIND_PROXY=true`, `HTTP_PROXY_HOPS=1`, and the integration API disabled by default.

- **Temporary cluster test mutations:** e2e testing against Kubernetes requires a disposable development-mode deployment and pristine seed database. Production startup permanently neutralizes the demo accounts. If a test rehearsal mutates the Deployment with `kubectl set env`, restore production by re-applying the previously reviewed digest-pinned `release-app-deployment.yaml`, then wait for `kubectl rollout status deployment/app`. Do not restore from the template or use `kubectl rollout restart` as an image update; every release changes the rendered digest reference.

The root `Dockerfile` is a 3-stage build: (1) `node` builds `web/dist`, (2) `eclipse-temurin:21-jdk` runs `:server:installDist`, (3) `eclipse-temurin:21-jre` runtime bundles the install image **and** the built SPA, sets `WEB_STATIC_DIR=/app/web`, and runs `bin/server`. The runtime JRE matches the build stage and the Gradle toolchain (`jvmToolchain(21)`) so the app ships on the LTS JVM the test suite runs against — bump all three together to move JVMs. The `app` Compose service points the `POSTGRES_*` env vars at the `postgres` service host and waits on its healthcheck. `.dockerignore` keeps build outputs / `node_modules` out of the build context; `.git` is **included** on purpose — the SPA build stage reads the commit sha/timestamp from it for the version stamp (see "Build version stamp" in `web/CLAUDE.md`).
