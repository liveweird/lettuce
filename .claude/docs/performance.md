### Performance measurement (on demand — NOT imported)

**Measurement only.** Nothing in this programme changes a query, index, pool setting, SPA fetch or schema; anything that looks like a fix is a *finding* (recorded in `perf/baselines/…/FINDINGS.md`), never a commit. Goal: a repeatable way to see DB time, back-end round trips and (later) front-end rendering at the target capacity — 500 users, 4 hierarchy levels, 5 years — against the local container. Status: **M1 shipped** (the perf compose project, the dataset generator, the per-request DB metrics, snapshot/restore + pg_stat_statements windows, the first k6 scenario `reviews-team-view` and its first committed baseline); **M2 done: the generator covers every feature (dataset v2), one k6 scenario per screen plus the mixed 50-VU run, the compare tool (`scripts/perf_compare.py`), `perf/run.sh all|report|baseline`**; query budgets in CI, traces/profiles and the front-end runner are later steps of the plan. **Dataset v2 is not comparable with the v1 baseline** (`2026-10-04-feb13b52`): the same screens now read a database 4–5× larger.

#### The perf stack (`perf/`)

`perf/run.sh up [service…] | down [--wipe] | status | seed | snapshot | restore | pgss | k6` (flows below) drives ONE compose project, `lettuce-perf` (`docker compose -p lettuce-perf -f docker-compose.yaml -f perf/docker-compose.perf.yaml …`), so the dev stack's containers and its `lettuce_postgres-data` volume are never touched (the perf volume is `lettuce-perf_postgres-data`; `down` keeps it, only the confirmed `down --wipe` deletes it). Containers `lettuce-perf-*`; loopback ports app **18080**, postgres **15432** (no mail catcher, no Teams stub — see "Isolation"). Differences from the demo stack: postgres runs `pg_stat_statements` + `auto_explain` (JSON plans ≥ 50 ms in the log, `auto_explain.log_timing=off` — see "Observer effects") + `track_io_timing` + `log_min_duration_statement=250ms` + `log_parameter_max_length=0` (bind values, which carry emails, never reach the log), `mem_limit 1g`, `cpus 2`; the app runs the **application.yaml dev encryption key** (the generator encrypts with the same constant — a different key means `AEADBadTagException` on every seeded read), `JWT_ACCESS_EXPIRES_IN_SECONDS=7200`, `PERF_SERVER_TIMING=true`, the SHIPPED JVM flags (SerialGC, `-Xmx256m`, C1-only; `PERF_JAVA_OPTS="-XX:TieredStopAtLevel=4"` turns C2 on for a variant run), `mem_limit 512m`, `cpus 2`; development mode (HSTS/redirect off, login bucket 1000/min — none of it on the measured path). Record the machine and limits with every baseline.

#### The dataset (`./gradlew :server:perfSeed`)

A deterministic generator in the **test source set** (`server/src/test/kotlin/perf/`: `SeedMain`, `Spec`, `Rng`, `Sinks`, `Seeded`, one `Seed<Feature>.kt` per feature; the generator itself never part of `check`, its guard tests are). It runs Flyway, then writes through the services' **Exposed table objects** with `batchInsert` (1 000 rows/statement, explicit ordered ids, serial sequences advanced afterwards) and the **real `FieldCipher`** — every encrypted column is an `enc:v1:` envelope, so the app's boot `encryptLegacyRows` backfill rewrites nothing. Events and notifications follow written rules and reuse the routes' pure builders (`oneOnOneCreationNotifications`, `goalTransitionNotifications`, `feedbackTransitionNotifications`, `reviewTransitionNotifications`, `…Event` descriptors) so shapes cannot drift. Settings come from `-Pperf.<name>`: `r2dbcUrl`/`jdbcUrl`/`user`/`password` (default the perf stack, 127.0.0.1:15432), `key`, `anchor` (default the first day of the CURRENT month — **it moves every month, so pin `-Pperf.anchor=YYYY-MM-01` for a reproducible dataset**; it is the frozen "now": every timestamp precedes it), `seed` (1), `scale` (1.0; smaller shrinks org and history for smoke runs), `out`, `force`, `allowTarget`. `PERF_SEED_PASSWORD` / `PERF_SEED_KEY` in the environment win over `-P` (keep secrets off command lines). **Guards (before Flyway or any connection, `SeedTarget.kt`):** the JDBC and R2DBC URLs must name the same host/port/database; port 5432 (the dev stack) is refused; and only a loopback host on the perf port 15432 is accepted (anything else — another throwaway Postgres — needs `-Pperf.allowTarget=host:port`); `force` skips ONLY the occupancy check (a database that already holds generated feature data is refused — the explicit ids would collide: seed a fresh volume, `perf/run.sh down --wipe`, `up postgres`). A perf-seeded database holds well-known accounts (the shared password) — never point a production-mode app at it (production boot would refuse or soft-delete the demo accounts; the loopback-only rule keeps the generator from writing to a real database in the first place). **`DATASET_VERSION`** (`Spec.kt`) is bumped on every change to what the generator writes; each run writes `perf/results/seed-<version>.json` (row counts, scale, anchor, generation seconds). **Determinism means identical plaintext, ids, row counts and shapes — not identical bytes:** the bcrypt hash has a random salt and every AES-GCM envelope a random nonce. **Known gaps (the dataset is not the product's full behaviour):** feedback `expires_on` and the `REQUEST_EXPIRED` sweep are not represented; goal `PROGRESS_UPDATED`/`MILESTONE_COMPLETED` events and 1:1 `ACTION_ITEM_RESOLVED` events are built by hand in the seeders (no pure builder exists for them — they follow the documented param shapes); 1:1 action items are created unresolved-or-resolved in one step and a `…RESOLVED` event is minted for each resolved one; impact-log `UPDATED` events reproduce the documented `changed` param shape without the builder (it needs two full documents); **mass shares are not generated** (`document_shares.batch_id` stays NULL, no `…_BATCH_SHARED` notices) and neither is the per-(sharer, sharee) daily share-notification cap; days-off allowance edits after the first grant, pool archiving and the ADMIN pool-kind lifecycle are absent; the newest pulse cycle is OPEN with ~50 % answered (older cycles 80–100 %).

*Shape (scale 1.0):* 1 CEO → 10 directors (one team) → 70 leads (10 teams) → 430 ICs (70 teams) = 511 users + one HR auditor, 81 teams (`team_members` + `teams.manager_id`; every non-CEO belongs to exactly the team their manager runs). Emails `perf-ceo@`, `perf-dir-01..10@`, `perf-lead-001..070@`, `perf-ic-0001..0430@`, `perf-hr@perf.lettuce.local` (never containing `e2e`, which the e2e residue sweep deletes); ONE shared password **`perf-pass-2026`** (one bcrypt-12 hash); the admin stays the V6 seed. *Fidelity pass (2026-10-04, `acd9d3ed`, `DATASET_VERSION` stays 2 — timestamps changed dataset-wide, so numbers taken before the reseed are not comparable).* **The spread/jitter rule:** a timestamp that would lie after the anchor ("booking ahead", a late lifecycle step) is not clamped to `anchor − 1` — that stacked thousands of rows on one millisecond — but drawn uniformly over the last `SPREAD_DAYS` (30) days before the anchor and never before the story's earlier step (`SeedContext.spreadMillis(rng, raw, floor)`); every `millis(...)`/`rawMillis(...)` additionally carries a sub-minute jitter (0–59.999 s, one shared stream) so the many rows a seeder places at the same date/hour/minute (every weekly 1:1, every monthly goal) never share a millisecond, while a story's one-minute steps stay strictly ordered. **New `verify.sql` checks** (92 in all): a single-day days-off entry has no end half-day (`DaysOff.kt` rejects `start = end AND end_half`); a succession candidate is never the plan's owner nor anyone above the seat's person; `users.last_login_at` equals the newest `SIGNED_IN` of the account (0 when none — sign-ins consistent with `account_events`); and **same-millisecond groups**: for every events/shares/entries table's `created_at` (and `withdrawn_at`, `last_reviewed_at`) the largest group of rows sharing one millisecond is at most 20 (notifications: per (moment, type), the pulse fan-outs excluded, which are one moment by design). **Hand-built shapes** (`Seeded.kt` lists them; they are the only event/notification params without a production builder, so the only ones that can drift from the app — a change to any means updating the generator and bumping `DATASET_VERSION`): `goal_events` `PROGRESS_UPDATED{from,to}` and `MILESTONE_COMPLETED{position}`; `performance_review_events` `RATING_CHANGED{category}` / `SUMMARY_CHANGED{category}`; `one_on_one_events` `ACTION_ITEM_RESOLVED{position}`; `impact_log_events` `UPDATED{changed}`; `account_events` `SIGNED_IN{mfa:"false"}` / `SIGNED_OUT{}`; and the notification `TEAM_KPI_VALUE_RECORDED_TO_MEMBER{date,value}`. Re-seeded numbers: 443 s of generation, 92 checks green, **675 MB** after `VACUUM (ANALYZE)` (the restored database), a 258 MB dump, restore 7–18 s, app boot 2–3 s.

**Keeping the generator in step with the schema.** `Seeded.kt` is the registry: `Seeded.tables` (what the generator writes), `NOT_SEEDED` (every other `public` table, each with a reason) and `ENCRYPTED_COLUMNS` (the `EncryptedAtRest` registrants' columns). `PerfSeedCoverageTest` fails when a table is in neither set (so a migration adding a table fails CI until classified) or when `perf/pg/verify.sql` does not check a registered encrypted column; `PerfSeedSmokeTest` runs the generator at `scale=0.02` into a throwaway database inside the Testcontainer (~5 s — catches a new NOT NULL column, CHECK or FK the generated rows break), requires a row in every seeded table, and requires the ten boot backfills to find nothing to rewrite. **Convention: a change to a feature's event or notification rules, or a new feature, updates the generator and bumps `DATASET_VERSION`; baselines compare only within one dataset version.**

**Personas** (all `perf-pass-2026`): CEO (level 1, ~510 transitive reports), a director (~50), a team lead (6–7 direct), an IC, `perf-hr` (HR auditor, no team), admin (seed).

**Verify.** `perf/pg/verify.sql` (psql, `ON_ERROR_STOP`) fails loudly unless: every encrypted column of every registrant is an envelope (0 plaintext), the partial-unique invariants hold (one active review per (subordinate, period), `uq_users_email_active`, gapless periods), org consistency (a review's/goal's/1:1's manager is the subordinate's team manager), the 1:1 rules (one meeting per pair+date, carry-over copies an unresolved item of the pair's earlier meeting, exactly one CREATED event), the feedback rules (position-0 anchor, provider ∉ recipients, ≤ 4 recipients, requested = one recipient + requester, visibility/requester coherence, no duplicate open row), the goal type rules, and that the serial sequences are at or beyond `max(id)`; since v2 also: pulse (one non-terminal cycle, `closed_at` ⇔ CLOSED, every cycle has participants, every response belongs to a participant), team KPIs (the current value/date equal the max-dated data point, percentages in 0..100, creator = team manager, one CREATED event), days off (positive cost, one calendar year, no overlap per person, every PAID entry has an active grant of its pool, per-(person, pool, year) cost ≤ 2 × allowance, event counts match the entries), impact log (period order, one entry per (person, month), one CREATED event), succession (the seat is in the owner's transitive chain via a recursive CTE, candidate ≠ seat, ≤ 1 primary, one OPEN plan per (owner, person)), shares (the sharer is the document's author per kind, `details` present, no duplicate (document, sharee)), career-position events name a position of their owner, and the sign-in history is owner = actor within its 90-day window. Run: `docker compose -p lettuce-perf exec -T postgres psql -U lettuce -d lettuce -v ON_ERROR_STOP=1 -f - < perf/pg/verify.sql`.

#### The one-command flow, snapshots and statistics windows

```
perf/run.sh seed --wipe        # fresh perf volume (asks to confirm) -> up postgres -> ./gradlew :server:perfSeed (pinned anchor 2026-10-01, seed 1, scale 1.0)
                               #   -> perf/pg/verify.sql -> VACUUM (ANALYZE) -> snapshot            (~5 min once the test classes compile)
perf/run.sh restore            # stop app -> dropdb/createdb -> pg_restore --exit-on-error -> ANALYZE -> up app -> wait for /readyz  (seconds)
perf/run.sh k6 reviews-team-view --persona ceo-all --vus 1 --iterations 3 --run <id>
perf/run.sh pgss reset | dump <label> [--run <id>] [--since 1h|<RFC3339>]      # what `k6` wraps around every run
```

`seed` flags: `--wipe`, `--anchor YYYY-MM-DD` (default the pinned **2026-10-01** — never the moving "first of the current month", so a re-seed reproduces the dataset), `--seed N`, `--scale X`. `snapshot` writes `perf/snapshots/lettuce-perf-v<DATASET_VERSION>-<anchor>-s<seed>-x<scale>.dump` (`pg_dump --format=custom`, redirected on the host, mode 600, git-ignored — the redirect-on-host form of `.claude/docs/backup-and-restore.md`); `restore [file]` takes the newest dump by default. A restored database is the reproducible starting point of every run: **`restore` before a baseline** (a fresh JVM, a fresh buffer cache). `down` keeps the volume and the snapshot; `perf/snapshots/` and `perf/results/` are git-ignored.

**`pgss reset`** zeroes `pg_stat_statements` and the table statistics (`pg_stat_reset()` — so the window's `seq_scan` numbers are deltas; `n_live_tup` is zeroed too, which is why the table CSV reports `pg_class.reltuples` as `est_rows`). **`pgss dump <label>`** writes three files into `perf/results/<run>/`: `<label>.pgss.csv` (the 50 costliest statements by total time **union** the 50 most frequent by calls — repetition is what a per-row loop looks like and never tops a by-time list; `rank_total`/`rank_calls`, `calls`, total/mean/max exec ms, `rows`, `shared_blks_hit/read`, the normalized query, never a bind value), `<label>.tables.csv` (`seq_scan`, `seq_tup_read`, `idx_scan`, tuples, `est_rows`, size — tables touched in the window) and `<label>.auto_explain.ndjson` (the JSON plans `auto_explain` logged in the window: `perf/pg/extract-auto-explain.py` over `docker compose logs postgres --since`; **an empty file means no statement reached the 50 ms threshold**). The dump waits 11 s first (`PERF_STATS_FLUSH_WAIT`): PostgreSQL flushes an idle backend's per-table counters lazily (~10 s), `pg_stat_statements` is immediate. `--since` bounds the `auto_explain` log read (default the last hour; `k6` passes its own start time). Run ids, labels and personas must match `[A-Za-z0-9._-]+` (they become file names). The `k6` container writes into `perf/results/<run>/` as uid 12345 — fine on OrbStack/Docker Desktop; **on native Linux Docker make that directory writable for uid 12345** (`chmod o+w`). A pgss window is per run, so divide `calls` by the iteration count for per-screen numbers.

#### Scenario `reviews-team-view` (k6)

`perf/run.sh k6 <scenario> [--persona P] [--vus N] [--iterations N | --duration D] [--think MIN MAX] [--run ID] [--label L] [--raw] [--no-pgss]` runs `perf/k6/<scenario>.js` in the **digest-pinned `grafana/k6` image** (`K6_IMAGE` in `perf/run.sh`, recorded in `.claude/docs/container-images.md`; no k6 or npm dependency enters the repo) on the `lettuce-perf_default` network against `http://app:8080`, resets pgss before and dumps it after (`--no-pgss` skips), and writes `<label>.summary.json` (everything k6 knows, per-persona/per-endpoint sub-metrics included), `<label>.table.md` (the readable table, also printed) and, with `--raw`, `<label>.raw.json.gz` into `perf/results/<run>/`. Label default `<scenario>.<persona>.vu<N>`. Setup logs the personas in once (bcrypt ≈ 250 ms each).

*What it replays — Performance → Team's performance* (`web/src/pages/ReviewsDashboard.tsx`, `api/teams.ts` / `reviews.ts` / `users.ts` `listAll*`, `hooks/useIsManager.ts`): `teams?page=1&pageSize=1&managerId=<me>` (the managed-teams probe) · `review-periods` (then picks the period containing today, else the newest — the SPA rule) · the three career dictionaries · the **roster chain**: `teams/members?view=managed[&includeIndirect=true]&page=i&pageSize=100` page after page until `total` (HR, auditor scope: `users?page=i&pageSize=100&sort=id` instead, after one `stray-roster` request the SPA's first render issues) · the **reviews chain**: `performance-reviews?view=managed&periodId=<current>&includeIndirect=true&page=i&pageSize=100` until `total` (HR: `view=all&periodId=…`). Personas (`lib/auth.js`; `PERSONA=` env/flag): `ceo-all` (the SPA's "all reports" scope, ~510 transitive), `ceo-direct`, `director-all` (~50), `lead` (`perf-lead-001`, 6–7), `lead-2` (`perf-lead-042`, under another director), `hr` (auditor, no team); `mixed` = VU n takes `[ceo-all, director-all, lead, lead-2, hr][(n−1) mod 5]`; `all` = one iteration walks every persona (warm-up). **There is deliberately no IC persona:** an IC never sees this tab (`Performance.tsx`: `showManagedTab = isManager || auditor`), so replaying the chain for one would describe a screen that does not exist — ICs get their own screens in the M2 scenarios. **Replay discipline:** every iteration is a **cold screen load** (no client cache — in the SPA periods and dictionaries have a 5-minute `staleTime`, so a repeat visit skips them); each chain is sequential like `listAll*`; the browser additionally runs the roster chain and `periods → reviews` *concurrently* (React Query fires every enabled query at once), which k6 cannot do inside an iteration — so every screen load reports both the **sequential sum** (`screen_wall_ms`) and an **estimated critical path** (`screen_critical_ms` = max(roster chain [+ probe for HR], periods + reviews chain); no browser connection or CPU effects). HR's replay assumes the managed-teams probe resolves before the periods do; if it does not, the SPA may also issue one stray `view=managed` reviews page 1 before switching to `view=all` (a race, unverified, not replayed). Not replayed: the Distribution/Quadrants views (client-side), the notification bell and the other shell requests.

*Metrics* (all tagged `persona`, per-endpoint ones also `endpoint` ∈ probe, periods, dictionaries, members, users, reviews): `req_wall_ms` (k6's request duration), `req_db_ms` / `req_app_ms` / `req_stmt` / `req_tx` (parsed from `Server-Timing`), `req_bytes`; per chain `chain_wall_ms/requests/stmt/tx`; per screen load `screen_wall_ms`, `screen_critical_ms`, `screen_db_ms`, `screen_requests`, `screen_stmt`, `screen_tx`; `server_timing_missing` (an authenticated response without the header — must be 0). Thresholds are **informational** (`p(95)>=0` only keeps the sub-metrics in the summary) except `http_req_failed < 0.1 %` and `checks > 99.9 %`. `THINK_MIN/THINK_MAX` default 0: the 50-VU runs are a **closed-loop saturation test**, not a realistic user mix (the mixed 3-VU-think-time scenario is the plan's M2 `mixed-50vu`). The pool's `maxSize` 20 is a measured constraint — never raised here.

#### Scenarios of the full set (`perf/k6/*.js`, M2)

One k6 file per screen, all built on `perf/k6/lib/replay.js`: a **screen** is a function replaying what the SPA's page component fires on first load — requests React Query enables together go out through `http.batch` (really simultaneous, capped at k6's 6 per host like the browser), a dependent query or a `listAll*` loop goes one after the other — and `s.end()` records elapsed wall time, summed request time, DB time, statements and transactions per load (`screen_wall_ms`, `screen_seq_ms`, `screen_db_ms`, `screen_requests`, `screen_stmt`, `screen_tx`, tagged `persona` + `screen`; per request `req_*` additionally `endpoint`). Every first load includes the **Shell's four queries** every authenticated page mounts (`shell-user`, `shell-probe` = the isManager probe, `shell-alerts`, `shell-bell`); a tab click does not repeat them. **Personas only load screens they can actually reach** (the M1 review's rule — each scenario's `personaScreens` follows the SPA's gating: feature flag, `isManager`, auditor; an IC never loads a manager tab, HR/admin have no reports, `succession` has no IC/admin rows because its nav leaf is manager-only, and a k6 init error stops a persona that cannot reach a scenario). Ids are derived from earlier responses (a list row, the visible-teams response, a persona's `userId`), the one pinned id pair being the 6-link carry-over chain of `one-on-ones/detail-chain` (dataset v2: meeting 97111, item 314699 — re-pick on a `DATASET_VERSION` bump). Statuses a screen EXPECTS (pulse's fill-gate 403, `my-response` 404) are declared per request and are not failures.

`--ramp-up D` (env `RAMP_UP`) turns the constant-VU run into 0→N over D then hold for `--duration`. **The mixed run writes into the perf database** (feedbacks + their events/notifications, 1:1 meetings with carried-over items, goal progress) — it touches only the perf stack, and `perf/run.sh all` ends with a `restore`; run `restore` yourself before the next baseline otherwise. A created 1:1's `meetingDate` is one day per 10 minutes since a fixed epoch — non-decreasing in real time, so it holds across UTC midnight and across a second run on the same database; a 409 would mean something else wrote the pair, and `write_<action>_<201|204|409|failed>` counters keep outcomes apart. **Naming note:** `screen_wall_ms` means the REAL elapsed time of a load in the per-screen scenarios, but in `reviews-team-view` (sequential chains, no overlap in k6) it is the SUM of its request durations — the per-screen scenarios' `screen_seq_ms` equivalent; compare across scenarios only through `screen_seq_ms`/`screen_stmt`/`screen_tx`. `reviews-team-view` keeps its own sequential-chain accounting (`chain_*`, `screen_critical_ms`) and is not in the mix (a CEO reloading its 1 190 statements every few seconds would drown the rest — run it with `--persona`).

**`perf/run.sh all`** = **build the app image once from the current checkout** (`restore` only starts the already-built image; `run.json` records the git commit, the uncommitted-file count, the app image id and the dataset) → `up postgres` → `restore` (or `seed` when there is no snapshot) → `run.json` → warm-up (every persona over every scenario, unrecorded) → per scenario × persona: 3 iterations at 1 VU with a pgss window each → `reviews-team-view` (6 personas at 1 VU; 50 VUs: mixed 3 m, ceo-all 2 m, director-all/lead/hr 1 m) → `login` (1 VU ×5; 50-VU storm) → `restore` (the sign-ins and 1-VU runs wrote) → `mixed-50vu` with `docker stats` sampled every 4 s (`saturation-docker-stats.txt`) → `restore` → `report`; an EXIT trap kills the sampler and restores the snapshot if the run aborts. A run that crosses a k6 threshold is listed at the end instead of aborting the rest. **`perf/run.sh baseline <run>`** copies the small files (summary reduced to the metrics the compare tool reads, `table.md`, `pgss.csv`, `tables.csv`; no raw output, no warm-up) into `perf/baselines/<date>-<sha>/` and refuses if a JWT-shaped string slipped in; `meta.json` is written by hand.

**`perf/run.sh report <run> [--baseline DIR]`** runs `scripts/perf_compare.py` (stdlib only, tested by `scripts/test_perf_compare.py`, which CI's unittest step picks up) and writes `perf/results/<run>/report.md`: per k6 label a table of every `screen_*` / `req_wall_ms` / `req_stmt` / `req_tx` sub-metric (baseline vs current, Δ %), the top statements joined on normalized query text (calls, total ms) and the per-table `seq_scan` counts. **Milliseconds** are flagged at ±10 % *and* more than 2 ms apart (`p(95)`), **counts are exact** — a changed `screen_stmt`, `screen_tx`, `screen_requests` or — in `*.vu1` (fixed-replay) labels only — a statement's `calls` is flagged at any size, a sub-metric present on one side only is `NEW`/`MISSING`, `warmup.*` labels are skipped — a run with failed requests or responses without `Server-Timing` is marked "RUN NOT CLEAN". Without `--baseline` it picks the newest `perf/baselines/*` whose `meta.json` carries the same `datasetVersion` (a run's `run.json` records its own); across versions it refuses unless `--force` ("baselines compare only within one dataset version"). `--fail-on-regression` makes the exit code 1 when anything is flagged.

**Repeatability pins in the overlay.** The app's two real-clock purges are switched off on the perf stack because the dataset's anchor is pinned: `ACTIVITY_ACCOUNT_RETENTION_DAYS=0` (the sign-in-history purge would hard-delete part of the seeded `account_events` once a restore happens more than 90 days after the anchor) and `NOTIFICATION_RETENTION_DAYS=0` (the on-mint notification purge, which the mixed run triggers). The feedback expiry sweep stays on — it is part of the measured read path and a restore resets what it flips.

#### Query budgets (`QueryBudgetTest`, M3 — runs in CI)

`server/src/test/kotlin/QueryBudgetTest.kt` is the regression guard for the statement/transaction counts this programme measures. For each list/read endpoint it seeds 1 row, then 50 (the same caller, `pageSize` 100), reads `stmt`/`tx` from the `Server-Timing` header (development mode sends it to every authenticated response, which is what the tests run in) and asserts: the count does not grow with the rows (the slope is 0) and it stays within the endpoint's row of the **`BUDGETS` table at the top of that file** (one line per endpoint, the measured `stmt/tx` at 1 → 50 rows in the comment). The page's reported `total` is asserted too, so an empty page cannot pass. About 20 s in the Backend job; every test builds its own users (unique `qb…` tag), so it coexists with the rest of the suite in the shared container.

- **Update rule.** A deliberate optimisation lowers its budget row **in the same PR** (a count that merely fell below its budget still passes, so the next person would otherwise inherit the slack). A feature that adds a statement raises the row and says why in the PR; one that adds a per-row query fails and has to batch it instead.
- **Already-O(n) endpoints are pinned, not fixed.** Their row carries `dStmt`/`dTx`, the measured `stmt(50) − stmt(1)`: a regression and an improvement both fail the test, so whoever changes the code updates the pin and the matching finding in `perf/baselines/FINDINGS.md`. Today: `teams/members?view=managed` (+2 statements per row, F1/F10 — the latest 1:1 and the latest review lookups), `…&includeIndirect` (the same), `teams/members?view=managers` (+1 per row, F17), `one-on-ones?view=managed` with and without `latestOnly` (+1 per distinct (manager, subordinate) pair on the page, F17). Every other budgeted endpoint is O(1) in rows.
- **The pulse trend** is O(cycles) (F7) and its absolute count depends on how many closed cycles the shared test container already holds, so only its slope is pinned (`PULSE_TREND_PER_CYCLE` = 2 statements + 2 transactions per closed cycle; the test adds 9 closed cycles and expects exactly +18/+18).
- **Not covered:** the per-screen request fan-outs of the SPA (F8's one `GET /teams/{id}` per team, F9's users pool) — they are many cheap requests, not a per-row query inside one; `/teams/{id}` itself is budgeted at O(1). Measure those with `perf/run.sh`.

#### Traces (M4 step 12: DB spans, Jaeger in the perf overlay)

The application always creates one SERVER span per request (Ktor instrumentation); **when a traces exporter other than `none` is configured** it also creates one CLIENT span per SQL statement (the R2DBC pool is wrapped by `R2dbcTelemetry`, `infra/db/Database.kt`) — the within-request waterfall the counters of `Server-Timing` cannot give (WHERE in the request the time sits: which statement, how long between statements, how long after the last one). **The wrapper is gated, not always on, because it is not free even with nothing exported or with the sampler at `always_off`: +24 % wall on the CEO's 1 190-statement screen at 1 VU and −36 % throughput at 50 VUs (FINDINGS F18).** With the default exporter (`none`) the pool is NOT wrapped — byte-for-byte the pre-M4 path, so the committed baselines stay valid; export and wrapping are one env switch.

- **`perf/run.sh traces <scenario> [--run ID] [--keep] [--limit N] [k6 flags]`** starts Jaeger (the compose profile `traces`: `jaegertracing/jaeger` v2 all-in-one pinned by digest, in-memory storage, UI on **`http://127.0.0.1:16686`**, OTLP receivers on the compose network only), recreates the app with `OTEL_TRACES_EXPORTER=otlp`, `OTEL_TRACES_SAMPLER=always_on`, `OTEL_EXPORTER_OTLP_ENDPOINT=http://jaeger:4318`, `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf` (the overlay's `PERF_OTEL_TRACES_*` variables), runs the k6 scenario (ONE iteration unless you pass `--iterations`/`--duration`; the pgss window is skipped), waits for the batch span processor, then exports the traces (Jaeger v2 `GET /api/v3/traces`, OTLP JSON) to `perf/results/<run>/<scenario>.traces.json` and writes `<scenario>.traces.md` (`perf/profile/trace-summary.py`: one row per `/api/` request — wall ms, DB span count, sum of DB span ms, the non-DB remainder, the slowest statement — then a per-route median table). An EXIT trap puts the app back with the export off and stops Jaeger (`--keep` leaves it running for browsing the UI). The k6 `setup()` logins are traces too (bcrypt shows as non-DB time on `POST /api/v1/login`).
- **Reading a trace.** Statement spans carry the sanitised statement text only (`db.query.text` with literals replaced — bind values never appear) and `db.namespace`/`server.address`. Gaps between sibling DB spans under one SERVER span are application time between statements (row mapping, decryption, JSON building) or a pool acquire (the validation `SELECT 1` and the acquire wait are below the wrapper and **not** spans: a request's `wall − Σ(DB spans)` includes them). A request with a high statement count and short statements is a round-trip problem; one with few statements and a long non-DB remainder is a CPU problem (then take a JFR, below).
- **Overhead and statement counts.** The wrapper adds NO statements: the `Server-Timing` counters and `QueryBudgetTest` read the same numbers with and without it (1 190 statements / 84 transactions per CEO screen). Its CPU cost sits in r2dbc-proxy's per-statement/per-result proxies (F18) — which is why `perf/run.sh traces` numbers are inflated against an untraced run: read the SHAPE of a trace, take milliseconds from `Server-Timing`/k6. `TracingTest` pins parent/child linkage with an in-memory exporter (the Ktor instrumentation puts the OTel context into the coroutine, r2dbc-proxy reads it when the statement executes) and that the default boot does NOT wrap the factory.
- **Production** keeps `otel.traces.exporter=none` (so no wrapper). **WARNING — before exporting traces from a real deployment** (`OTEL_TRACES_EXPORTER=otlp` + an endpoint): SERVER spans carry the request's **query string (`url.query` — emails in list filters) and the user agent**; statement text in DB spans is sanitised, but the query strings are not. Treat a trace store like logs, never commit an export, and review what a deployment ships before pointing it at a shared collector.
- **Dependency note.** `opentelemetry-r2dbc-1.0` is versionless (the alpha BOM in `core` pins it) and brings `io.r2dbc:r2dbc-proxy`; the lock/verification entries and their PGP provenance are recorded in `gradle/libs.versions.toml` (`opentelemetry` note) and `gradle/verification-metadata.xml`.

#### CPU profiles (M4 step 13: JFR, async-profiler)

**`perf/run.sh jfr <scenario> [--c2] [--heap Nm] [--run ID] [k6 flags]`** recreates the app with `-XX:StartFlightRecording=filename=/perf-out/<file>.jfr,settings=profile,dumponexit=true,maxsize=256m` appended to the shipped JVM flags (JFR ships in the JRE image; the launcher appends `JAVA_OPTS`), runs the k6 scenario (its pgss window as usual), stops the app gracefully (`dumponexit` needs the JVM to exit through its shutdown hooks) and writes into `perf/results/<run>/`: the recording, `jfr summary` (`.jfr.summary.txt`) and `<file>.cpu.md` (`perf/profile/jfr-summary.py` over `jfr print --events jdk.ExecutionSample`: samples per thread group, the top self frames and **inclusive family shares** — AES-GCM, kotlinx.serialization, bcrypt, Netty, Ktor, Exposed, the R2DBC driver and pool, Reactor, OpenTelemetry, compression, the Lettuce packages). It needs a `jfr` tool on the host (any JDK 21+). The app is put back with the shipped flags afterwards. A sample is ~10 ms of ONE thread on CPU; the shares answer "where does CPU go", not "where does wall time go" (waiting on the database is invisible to it — that is what traces and `pg_stat_statements` are for).

- **Variants.** Default = the shipped flags (SerialGC, `-Xmx256m`, C1-only — what production runs). `--c2` appends `-XX:TieredStopAtLevel=4` (C2 on; the last flag wins) to size what C1-only costs. `--heap 512m` appends `-Xmx512m` and lifts the container limit to heap + 256m for that run. Record the variant in the run's `meta.json`/FINDINGS entry; compare only like with like.
- **JMC.** Open the `.jfr` in JDK Mission Control for the flame graph/call tree: look at `com.sun.crypto.provider.GaloisCounterMode` (field decryption — reviews decrypt 5 ratings per row), `kotlinx.serialization` (response JSON), `at.favre.lib.bcrypt` (login), `io.netty` (I/O) and `jdk.GCPhasePause`/`jdk.GarbageCollection` for the 256 MB heap's collection cost.
- **async-profiler (optional, documented only — no repo artifact).** It samples native frames and avoids JFR's safepoint bias. Mount the Linux agent (`libasyncProfiler.so` from the project's release) into the app container with an extra `volumes:` entry and add `-agentpath:/perf-out/libasyncProfiler.so=start,event=cpu,file=/perf-out/prof.html,flamegraph` to `PERF_JAVA_OPTS`; stop the app gracefully to flush. Do not commit the agent.
- **Overhead.** `settings=profile` adds a low single-digit percent CPU and makes the file ~tens of MB; do not use JFR runs for latency baselines — they are for "where does CPU go", measured separately from the committed numbers.

#### Reading the numbers

**`Server-Timing`** (`plugins/RequestTiming.kt`, "Per-request DB metrics" in `.claude/docs/observability.md`): `db;dur=<ms>;desc="stmt=<n> tx=<m>", app;dur=<ms>` on every **authenticated** response (development mode or `PERF_SERVER_TIMING=true`; browsers show it per request in DevTools → Network → Timing). **It is never sent on an anonymous response, in any mode** — login, `/login/mfa`, refresh, password reset, the 401 challenge, health probes and the SPA carry no header: statement counts there are an account-enumeration oracle (`POST /login` was `stmt=3` for an unknown email, `5` for a known one). Integration-API calls (API-key auth) get none either. A production boot with `PERF_SERVER_TIMING=true` logs one WARN; switch it off after the measurement window (anyone holding a valid token sees DB time and statement counts of their own requests). `stmt` = SQL statements Exposed dispatched, `tx` = transactions (each is a pool acquire plus a REMOTE validation round trip — "Connection pool" in `.claude/docs/persistence.md`), `db;dur` = the sum of statement *windows* (dispatch to the next boundary on the transaction — an upper bound on database time; Exposed's `afterExecution` fires before the server answers, so a before/after pair would read ~10 ms for a 300 ms statement — spike 2026-10-03), `app;dur` = Setup phase to response commit. `wall − db` is where pool queueing and non-DB CPU show up — **but only at low load: when the application itself is CPU-saturated (50 VUs on the 2-CPU container) `db;dur` also contains the application's scheduling delay between a statement's dispatch and its completion, and tracks wall time although PostgreSQL stays mostly idle** (FINDINGS F4); there compare `pgss` execution time with the `db` window instead. **Statement counts are exact and comparable across runs; milliseconds are not (OrbStack ≠ production) — compare them relatively and record the machine.** The slow-request log (`PERF_SLOW_REQUEST_MS`, default 1000) prints one `request.slow` line on `ch.nokillswit.perf` with the route path (no query string), `wallMs`/`dbMs`/`stmt`/`tx` and the slowest statement's SQL template. **What a window includes:** the Kotlin work that runs inside a transaction between two statements (row mapping, decrypting) — it is an upper bound on pure database time — and it excludes the COMMIT round trip and the pool acquire/validation (those show up in `wall − db`; `tx` counts them). The SQL template is rendered only when a statement becomes the request's slowest so far (it needs the open transaction, so it cannot be deferred to the log).

**Where the element lives (the `:server:run` zeros).** Under `./gradlew :server:run` Ktor's dev-mode reload loads the application's classes in a child class loader (`OverridingClassLoader$ChildURLClassLoader`) while Exposed instantiates its `GlobalSuspendStatementInterceptor` providers in the application loader. A context element defined in `server` therefore existed twice, the interceptor's `coroutineContext[RequestDbMetrics]` key never matched the plugin's, and every counter read 0. The element (`RequestDbMetrics`, stdlib-only) now lives in the `core` jar, which both loaders resolve through the parent, so there is one copy; verified 2026-10-03 against a throwaway Postgres (`:server:run` → `stmt=8 tx=2`, login anonymous). `RequestTimingTest` pins that the interceptor is registered and sees the plugin's element class, and `configureRequestTiming` logs one WARN if Exposed did not pick the interceptor up (instead of emitting zeros).

**Observer effects.** `auto_explain.log_timing=off` (per-node timing is the dominant `auto_explain` overhead; plans keep row counts, buffers and total duration — their per-node milliseconds are absent) and `log_analyze=on` still instrument every statement, so **absolute database milliseconds on the perf stack are inflated a little; statement counts are unaffected.** `Server-Timing`'s own cost is negligible next to a ~ms statement (a few allocations and one SQL render per running-maximum statement).

#### Isolation (the perf stack talks to nobody)

All external communication is **disabled**, not routed to a local catcher: `MAIL_TRANSPORT=disabled`, `TEAMS_TRANSPORT=disabled` (both accepted in development mode — they publish a null sender and refuse nothing), `INTEGRATION_ENABLED=false`, the inherited `SMTP_*`/`TEAMS_*` credentials and base URLs are removed, and `mailpit`/`teams-stub` carry compose `profiles: ["never"]` so the perf project never starts them (the app has no `depends_on` on either; their ports are reset so a force-started one cannot collide with the dev stack). `PerfSeedCoverageTest` fails if the overlay stops setting both transports to `disabled`, integration to `false`, or the two services to the `never` profile. Consequences: the notification email/Teams background mirrors find a null sender and skip their recipient lookups entirely — they run off the request path, so screen timings are unaffected — and the generated `@perf.lettuce.local` addresses are undeliverable anyway; password reset answers 503 (mail disabled). The traces exporter stays `none` (M4's traces go only to a local Jaeger inside the project). Nothing in the perf project opens an outbound connection except to its own Postgres.

#### Deliberately NOT measured

Real production hardware, network latency, TLS, the reverse proxy and ingress, a production-sized shared PostgreSQL (the perf database is 1 GB / 2 CPUs on a laptop), email/Teams mirror delivery (disabled — see "Isolation"), browser rendering in M1 (planned in M5), and any concurrency beyond the single local app instance. No production access exists, so no number here is a production number.
