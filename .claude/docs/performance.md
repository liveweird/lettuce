### Performance measurement (on demand — NOT imported)

**Measurement only.** Nothing in this programme changes a query, index, pool setting, SPA fetch or schema; anything that looks like a fix is a *finding* (recorded in `perf/baselines/…/FINDINGS.md`), never a commit. Goal: a repeatable way to see DB time, back-end round trips and (later) front-end rendering at the target capacity — 500 users, 4 hierarchy levels, 5 years — against the local container. Status: **M1 shipped** (the perf compose project, the dataset generator, the per-request DB metrics, snapshot/restore + pg_stat_statements windows, the first k6 scenario `reviews-team-view` and its first committed baseline); the remaining dataset features, the other scenarios, the compare tool, query budgets in CI, traces/profiles and the front-end runner are later milestones of the plan.

#### The perf stack (`perf/`)

`perf/run.sh up [service…] | down [--wipe] | status | seed | snapshot | restore | pgss | k6` (flows below) drives ONE compose project, `lettuce-perf` (`docker compose -p lettuce-perf -f docker-compose.yaml -f perf/docker-compose.perf.yaml …`), so the dev stack's containers and its `lettuce_postgres-data` volume are never touched (the perf volume is `lettuce-perf_postgres-data`; `down` keeps it, only the confirmed `down --wipe` deletes it). Containers `lettuce-perf-*`; loopback ports app **18080**, postgres **15432** (no mail catcher, no Teams stub — see "Isolation"). Differences from the demo stack: postgres runs `pg_stat_statements` + `auto_explain` (JSON plans ≥ 50 ms in the log, `auto_explain.log_timing=off` — see "Observer effects") + `track_io_timing` + `log_min_duration_statement=250ms` + `log_parameter_max_length=0` (bind values, which carry emails, never reach the log), `mem_limit 1g`, `cpus 2`; the app runs the **application.yaml dev encryption key** (the generator encrypts with the same constant — a different key means `AEADBadTagException` on every seeded read), `JWT_ACCESS_EXPIRES_IN_SECONDS=7200`, `PERF_SERVER_TIMING=true`, the SHIPPED JVM flags (SerialGC, `-Xmx256m`, C1-only; `PERF_JAVA_OPTS="-XX:TieredStopAtLevel=4"` turns C2 on for a variant run), `mem_limit 512m`, `cpus 2`; development mode (HSTS/redirect off, login bucket 1000/min — none of it on the measured path). Record the machine and limits with every baseline.

#### The dataset (`./gradlew :server:perfSeed`)

A deterministic generator in the **test source set** (`server/src/test/kotlin/perf/`: `SeedMain`, `Spec`, `Rng`, `Sinks`, `Seeded`, one `Seed<Feature>.kt` per feature; the generator itself never part of `check`, its two guard tests are). It runs Flyway, then writes through the services' **Exposed table objects** with `batchInsert` (1 000 rows/statement, explicit ordered ids, serial sequences advanced afterwards) and the **real `FieldCipher`** — every encrypted column is an `enc:v1:` envelope, so the app's boot `encryptLegacyRows` backfill rewrites nothing. Events and notifications follow written rules and reuse the routes' pure builders (`oneOnOneCreationNotifications`, `goalTransitionNotifications`, `feedbackTransitionNotifications`, `reviewTransitionNotifications`, `…Event` descriptors) so shapes cannot drift. Settings come from `-Pperf.<name>`: `r2dbcUrl`/`jdbcUrl`/`user`/`password` (default the perf stack, 127.0.0.1:15432), `key`, `anchor` (default the first day of the CURRENT month — **it moves every month, so pin `-Pperf.anchor=YYYY-MM-01` for a reproducible dataset**; it is the frozen "now": every timestamp precedes it), `seed` (1), `scale` (1.0; smaller shrinks org and history for smoke runs), `out`, `force`, `allowTarget`. `PERF_SEED_PASSWORD` / `PERF_SEED_KEY` in the environment win over `-P` (keep secrets off command lines). **Guards (before Flyway or any connection, `SeedTarget.kt`):** the JDBC and R2DBC URLs must name the same host/port/database; port 5432 (the dev stack) is refused; and only a loopback host on the perf port 15432 is accepted (anything else — another throwaway Postgres — needs `-Pperf.allowTarget=host:port`); `force` skips ONLY the occupancy check (a database that already holds generated feature data is refused — the explicit ids would collide: seed a fresh volume, `perf/run.sh down --wipe`, `up postgres`). A perf-seeded database holds well-known accounts (the shared password) — never point a production-mode app at it (production boot would refuse or soft-delete the demo accounts; the loopback-only rule keeps the generator from writing to a real database in the first place). **`DATASET_VERSION`** (`Spec.kt`) is bumped on every change to what the generator writes; each run writes `perf/results/seed-<version>.json` (row counts, scale, anchor, generation seconds). **Determinism means identical plaintext, ids, row counts and shapes — not identical bytes:** the bcrypt hash has a random salt and every AES-GCM envelope a random nonce. **Known gaps (the dataset is not the product's full behaviour):** feedback `expires_on` and the `REQUEST_EXPIRED` sweep are not represented; goal `PROGRESS_UPDATED`/`MILESTONE_COMPLETED` events and 1:1 `ACTION_ITEM_RESOLVED` events are built by hand in the seeders (no pure builder exists for them — they follow the documented param shapes); 1:1 action items are created unresolved-or-resolved in one step and a `…RESOLVED` event is minted for each resolved one.

*Shape (M1, scale 1.0):* 1 CEO → 10 directors (one team) → 70 leads (10 teams) → 430 ICs (70 teams) = 511 users + one HR auditor, 81 teams (`team_members` + `teams.manager_id`; every non-CEO belongs to exactly the team their manager runs). Emails `perf-ceo@`, `perf-dir-01..10@`, `perf-lead-001..070@`, `perf-ic-0001..0430@`, `perf-hr@perf.lettuce.local` (never containing `e2e`, which the e2e residue sweep deletes); ONE shared password **`perf-pass-2026`** (one bcrypt-12 hash); the admin stays the V6 seed. Career dictionaries topped up to 6/12/8 entries, 1–2 `user_career_positions` per person. `review_periods`: half-years from the first Jan/Jul at or after the window start to the one containing the anchor (10 rows). Reviews: every non-CEO × every period (past = PUBLISHED, current = 30/20/50 % DRAFT/CALIBRATION/PUBLISHED); 1:1s weekly per manager–report pair (510 pairs × 260 weeks) with 3 notes + 3 new action items + carried-over unresolved items (unresolved rate 7.5 % — chosen so items total ≈ 430k as the capacity spec says); goals and feedbacks 1/person/month over 60 months. Notifications are **retention-shaped** (`notifications.retentionDays` 30): everything minted in the 30 days before the anchor exists (70 % seen), older rows only if unseen (5 %). Later steps add pulse, KPIs, days off, impact log, succession, shares and the remaining event trails (the plan's M2).

*Full run (re-seeded 2026-10-04 after the `REQUESTED_THEN_REJECTED` content fix, scale 1.0, anchor 2026-10-01, seed 1, `DATASET_VERSION` 1, Apple M5 Max under OrbStack):* **247 s** of generation (267 s for the `perfSeed` command incl. the Gradle test compile; reviews 10 s, 1:1s 187 s, goals 33 s, feedbacks 17 s), database **547 MB** after the seed (508 MB after a `pg_restore` — fresh indexes/no bloat), a 193 MB custom-format dump, **restore in ~5 s**, app boot against it **~1.1 s** (the ten `encryptLegacyRows` scans find nothing to rewrite). Rows: users 522 (511 + HR + the V6/V9 seeds), teams 84 (81 + the V9 demo teams), `user_career_positions` 782, `review_periods` 10, `performance_reviews` 5 100 (+ 65 265 events), `one_on_one_meetings` 132 600 (notes 397 800, action items 429 868, events 530 291), `goals` 30 600 (milestones 45 680, events 166 720), `feedbacks` 30 660 (subjects 41 166, events 50 721), `notifications` 34 132 kept of 524 907 minted (the retention shape). The M1 slice is ~0.55 GB; the plan's 2–4 GB is the full M2 dataset.

**Keeping the generator in step with the schema.** `Seeded.kt` is the registry: `Seeded.tables` (what the generator writes), `NOT_SEEDED` (every other `public` table, each with a reason) and `ENCRYPTED_COLUMNS` (the `EncryptedAtRest` registrants' columns). `PerfSeedCoverageTest` fails when a table is in neither set (so a migration adding a table fails CI until classified) or when `perf/pg/verify.sql` does not check a registered encrypted column; `PerfSeedSmokeTest` runs the generator at `scale=0.02` into a throwaway database inside the Testcontainer (~2 s — catches a new NOT NULL column, CHECK or FK the generated rows break), requires a row in every seeded table, and requires the ten boot backfills to find nothing to rewrite. **Convention: a change to a feature's event or notification rules, or a new feature, updates the generator and bumps `DATASET_VERSION`; baselines compare only within one dataset version.**

**Personas** (all `perf-pass-2026`): CEO (level 1, ~510 transitive reports), a director (~50), a team lead (6–7 direct), an IC, `perf-hr` (HR auditor, no team), admin (seed).

**Verify.** `perf/pg/verify.sql` (psql, `ON_ERROR_STOP`) fails loudly unless: every encrypted column of every registrant is an envelope (0 plaintext), the partial-unique invariants hold (one active review per (subordinate, period), `uq_users_email_active`, gapless periods), org consistency (a review's/goal's/1:1's manager is the subordinate's team manager), the 1:1 rules (one meeting per pair+date, carry-over copies an unresolved item of the pair's earlier meeting, exactly one CREATED event), the feedback rules (position-0 anchor, provider ∉ recipients, ≤ 4 recipients, requested = one recipient + requester, visibility/requester coherence, no duplicate open row), the goal type rules, and that the serial sequences are at or beyond `max(id)`. Run: `docker compose -p lettuce-perf exec -T postgres psql -U lettuce -d lettuce -v ON_ERROR_STOP=1 -f - < perf/pg/verify.sql`.

#### The one-command flow, snapshots and statistics windows

```
perf/run.sh seed --wipe        # fresh perf volume (asks to confirm) -> up postgres -> ./gradlew :server:perfSeed (pinned anchor 2026-10-01, seed 1, scale 1.0)
                               #   -> perf/pg/verify.sql -> VACUUM (ANALYZE) -> snapshot            (~5 min once the test classes compile)
perf/run.sh restore            # stop app -> dropdb/createdb -> pg_restore --exit-on-error -> ANALYZE -> up app -> wait for /readyz  (seconds)
perf/run.sh k6 reviews-team-view --persona ceo-all --vus 1 --iterations 3 --run <id>
perf/run.sh pgss reset | dump <label> [--run <id>] [--since 1h|<RFC3339>]      # what `k6` wraps around every run
```

`seed` flags: `--wipe`, `--anchor YYYY-MM-DD` (default the pinned **2026-10-01** — never the moving "first of the current month", so a re-seed reproduces the dataset), `--seed N`, `--scale X`. `snapshot` writes `perf/snapshots/lettuce-perf-v<DATASET_VERSION>-<anchor>-s<seed>-x<scale>.dump` (`pg_dump --format=custom`, redirected on the host, mode 600, git-ignored — the redirect-on-host form of `.claude/docs/backup-and-restore.md`); `restore [file]` takes the newest dump by default. A restored database is the reproducible starting point of every run: **`restore` before a baseline** (a fresh JVM, a fresh buffer cache). `down` keeps the volume and the snapshot; `perf/snapshots/` and `perf/results/` are git-ignored.

**`pgss reset`** zeroes `pg_stat_statements` and the table statistics (`pg_stat_reset()` — so the window's `seq_scan` numbers are deltas; `n_live_tup` is zeroed too, which is why the table CSV reports `pg_class.reltuples` as `est_rows`). **`pgss dump <label>`** writes three files into `perf/results/<run>/`: `<label>.pgss.csv` (the 50 costliest statements by total time **union** the 50 most frequent by calls — repetition is what a per-row loop looks like and never tops a by-time list; `rank_total`/`rank_calls`, `calls`, total/mean/max exec ms, `rows`, `shared_blks_hit/read`, the normalized query, never a bind value), `<label>.tables.csv` (`seq_scan`, `seq_tup_read`, `idx_scan`, tuples, `est_rows`, size — tables touched in the window) and `<label>.auto_explain.ndjson` (the JSON plans `auto_explain` logged in the window: `perf/pg/extract-auto-explain.py` over `docker compose logs postgres --since`; **an empty file means no statement reached the 50 ms threshold**). The dump waits 11 s first (`PERF_STATS_FLUSH_WAIT`): PostgreSQL flushes an idle backend's per-table counters lazily (~10 s), `pg_stat_statements` is immediate. `--since` bounds the `auto_explain` log read (default the last hour; `k6` passes its own start time). Run ids, labels and personas must match `[A-Za-z0-9._-]+` (they become file names). The `k6` container writes into `perf/results/<run>/` as uid 12345 — fine on OrbStack/Docker Desktop; **on native Linux Docker make that directory writable for uid 12345** (`chmod o+w`). A pgss window is per run, so divide `calls` by the iteration count for per-screen numbers.

#### Scenario `reviews-team-view` (k6)

`perf/run.sh k6 <scenario> [--persona P] [--vus N] [--iterations N | --duration D] [--think MIN MAX] [--run ID] [--label L] [--raw] [--no-pgss]` runs `perf/k6/<scenario>.js` in the **digest-pinned `grafana/k6` image** (`K6_IMAGE` in `perf/run.sh`, recorded in `.claude/docs/container-images.md`; no k6 or npm dependency enters the repo) on the `lettuce-perf_default` network against `http://app:8080`, resets pgss before and dumps it after (`--no-pgss` skips), and writes `<label>.summary.json` (everything k6 knows, per-persona/per-endpoint sub-metrics included), `<label>.table.md` (the readable table, also printed) and, with `--raw`, `<label>.raw.json.gz` into `perf/results/<run>/`. Label default `<scenario>.<persona>.vu<N>`. Setup logs the personas in once (bcrypt ≈ 250 ms each).

*What it replays — Performance → Team's performance* (`web/src/pages/ReviewsDashboard.tsx`, `api/teams.ts` / `reviews.ts` / `users.ts` `listAll*`, `hooks/useIsManager.ts`): `teams?page=1&pageSize=1&managerId=<me>` (the managed-teams probe) · `review-periods` (then picks the period containing today, else the newest — the SPA rule) · the three career dictionaries · the **roster chain**: `teams/members?view=managed[&includeIndirect=true]&page=i&pageSize=100` page after page until `total` (HR, auditor scope: `users?page=i&pageSize=100&sort=id` instead, after one `stray-roster` request the SPA's first render issues) · the **reviews chain**: `performance-reviews?view=managed&periodId=<current>&includeIndirect=true&page=i&pageSize=100` until `total` (HR: `view=all&periodId=…`). Personas (`lib/auth.js`; `PERSONA=` env/flag): `ceo-all` (the SPA's "all reports" scope, ~510 transitive), `ceo-direct`, `director-all` (~50), `lead` (`perf-lead-001`, 6–7), `lead-2` (`perf-lead-042`, under another director), `hr` (auditor, no team); `mixed` = VU n takes `[ceo-all, director-all, lead, lead-2, hr][(n−1) mod 5]`; `all` = one iteration walks every persona (warm-up). **There is deliberately no IC persona:** an IC never sees this tab (`Performance.tsx`: `showManagedTab = isManager || auditor`), so replaying the chain for one would describe a screen that does not exist — ICs get their own screens in the M2 scenarios. **Replay discipline:** every iteration is a **cold screen load** (no client cache — in the SPA periods and dictionaries have a 5-minute `staleTime`, so a repeat visit skips them); each chain is sequential like `listAll*`; the browser additionally runs the roster chain and `periods → reviews` *concurrently* (React Query fires every enabled query at once), which k6 cannot do inside an iteration — so every screen load reports both the **sequential sum** (`screen_wall_ms`) and an **estimated critical path** (`screen_critical_ms` = max(roster chain [+ probe for HR], periods + reviews chain); no browser connection or CPU effects). HR's replay assumes the managed-teams probe resolves before the periods do; if it does not, the SPA may also issue one stray `view=managed` reviews page 1 before switching to `view=all` (a race, unverified, not replayed). Not replayed: the Distribution/Quadrants views (client-side), the notification bell and the other shell requests.

*Metrics* (all tagged `persona`, per-endpoint ones also `endpoint` ∈ probe, periods, dictionaries, members, users, reviews): `req_wall_ms` (k6's request duration), `req_db_ms` / `req_app_ms` / `req_stmt` / `req_tx` (parsed from `Server-Timing`), `req_bytes`; per chain `chain_wall_ms/requests/stmt/tx`; per screen load `screen_wall_ms`, `screen_critical_ms`, `screen_db_ms`, `screen_requests`, `screen_stmt`, `screen_tx`; `server_timing_missing` (an authenticated response without the header — must be 0). Thresholds are **informational** (`p(95)>=0` only keeps the sub-metrics in the summary) except `http_req_failed < 0.1 %` and `checks > 99.9 %`. `THINK_MIN/THINK_MAX` default 0: the 50-VU runs are a **closed-loop saturation test**, not a realistic user mix (the mixed 3-VU-think-time scenario is the plan's M2 `mixed-50vu`). The pool's `maxSize` 20 is a measured constraint — never raised here.

#### Reading the numbers

**`Server-Timing`** (`plugins/RequestTiming.kt`, "Per-request DB metrics" in `.claude/docs/observability.md`): `db;dur=<ms>;desc="stmt=<n> tx=<m>", app;dur=<ms>` on every **authenticated** response (development mode or `PERF_SERVER_TIMING=true`; browsers show it per request in DevTools → Network → Timing). **It is never sent on an anonymous response, in any mode** — login, `/login/mfa`, refresh, password reset, the 401 challenge, health probes and the SPA carry no header: statement counts there are an account-enumeration oracle (`POST /login` was `stmt=3` for an unknown email, `5` for a known one). Integration-API calls (API-key auth) get none either. A production boot with `PERF_SERVER_TIMING=true` logs one WARN; switch it off after the measurement window (anyone holding a valid token sees DB time and statement counts of their own requests). `stmt` = SQL statements Exposed dispatched, `tx` = transactions (each is a pool acquire plus a REMOTE validation round trip — "Connection pool" in `.claude/docs/persistence.md`), `db;dur` = the sum of statement *windows* (dispatch to the next boundary on the transaction — an upper bound on database time; Exposed's `afterExecution` fires before the server answers, so a before/after pair would read ~10 ms for a 300 ms statement — spike 2026-10-03), `app;dur` = Setup phase to response commit. `wall − db` is where pool queueing and non-DB CPU show up — **but only at low load: when the application itself is CPU-saturated (50 VUs on the 2-CPU container) `db;dur` also contains the application's scheduling delay between a statement's dispatch and its completion, and tracks wall time although PostgreSQL stays mostly idle** (FINDINGS F4); there compare `pgss` execution time with the `db` window instead. **Statement counts are exact and comparable across runs; milliseconds are not (OrbStack ≠ production) — compare them relatively and record the machine.** The slow-request log (`PERF_SLOW_REQUEST_MS`, default 1000) prints one `request.slow` line on `ch.nokillswit.perf` with the route path (no query string), `wallMs`/`dbMs`/`stmt`/`tx` and the slowest statement's SQL template. **What a window includes:** the Kotlin work that runs inside a transaction between two statements (row mapping, decrypting) — it is an upper bound on pure database time — and it excludes the COMMIT round trip and the pool acquire/validation (those show up in `wall − db`; `tx` counts them). The SQL template is rendered only when a statement becomes the request's slowest so far (it needs the open transaction, so it cannot be deferred to the log).

**Where the element lives (the `:server:run` zeros).** Under `./gradlew :server:run` Ktor's dev-mode reload loads the application's classes in a child class loader (`OverridingClassLoader$ChildURLClassLoader`) while Exposed instantiates its `GlobalSuspendStatementInterceptor` providers in the application loader. A context element defined in `server` therefore existed twice, the interceptor's `coroutineContext[RequestDbMetrics]` key never matched the plugin's, and every counter read 0. The element (`RequestDbMetrics`, stdlib-only) now lives in the `core` jar, which both loaders resolve through the parent, so there is one copy; verified 2026-10-03 against a throwaway Postgres (`:server:run` → `stmt=8 tx=2`, login anonymous). `RequestTimingTest` pins that the interceptor is registered and sees the plugin's element class, and `configureRequestTiming` logs one WARN if Exposed did not pick the interceptor up (instead of emitting zeros).

**Observer effects.** `auto_explain.log_timing=off` (per-node timing is the dominant `auto_explain` overhead; plans keep row counts, buffers and total duration — their per-node milliseconds are absent) and `log_analyze=on` still instrument every statement, so **absolute database milliseconds on the perf stack are inflated a little; statement counts are unaffected.** `Server-Timing`'s own cost is negligible next to a ~ms statement (a few allocations and one SQL render per running-maximum statement).

#### Isolation (the perf stack talks to nobody)

All external communication is **disabled**, not routed to a local catcher: `MAIL_TRANSPORT=disabled`, `TEAMS_TRANSPORT=disabled` (both accepted in development mode — they publish a null sender and refuse nothing), `INTEGRATION_ENABLED=false`, the inherited `SMTP_*`/`TEAMS_*` credentials and base URLs are removed, and `mailpit`/`teams-stub` carry compose `profiles: ["never"]` so the perf project never starts them (the app has no `depends_on` on either; their ports are reset so a force-started one cannot collide with the dev stack). `PerfSeedCoverageTest` fails if the overlay stops setting both transports to `disabled`, integration to `false`, or the two services to the `never` profile. Consequences: the notification email/Teams background mirrors find a null sender and skip their recipient lookups entirely — they run off the request path, so screen timings are unaffected — and the generated `@perf.lettuce.local` addresses are undeliverable anyway; password reset answers 503 (mail disabled). The traces exporter stays `none` (M4's traces go only to a local Jaeger inside the project). Nothing in the perf project opens an outbound connection except to its own Postgres.

#### Deliberately NOT measured

Real production hardware, network latency, TLS, the reverse proxy and ingress, a production-sized shared PostgreSQL (the perf database is 1 GB / 2 CPUs on a laptop), email/Teams mirror delivery (disabled — see "Isolation"), browser rendering in M1 (planned in M5), and any concurrency beyond the single local app instance. No production access exists, so no number here is a production number.
