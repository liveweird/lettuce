### Security posture: development vs production mode

`ktor.development` is env-overridable (`$KTOR_DEVELOPMENT:true`): local `:server:run`/tests default to development mode; **the Docker image ships `KTOR_DEVELOPMENT=false`** (production mode), and `docker-compose.yaml` explicitly sets it back to `true` because it is the local plain-HTTP demo. Production mode activates HSTS + HTTPS redirect and six **fail-closed startup checks**:

- **JWT secret** (`plugins/Security.kt`): blank, the placeholder `"secret"`, the repo-committed compose demo key (`dev-only-9f3c…`), or the `k8s/templates/secret.yaml` template placeholder → warn in development, **refuse to start** in production. Set a strong private `JWT_SECRET`.
- **Data encryption key** (`infra/crypto/Crypto.kt`): blank or one of the two repo-committed dev keys → warn in development, **refuse to start** in production; a malformed key (not 64 hex chars) refuses to start in **any** mode. Set a strong private `DATA_ENCRYPTION_KEY`. See "Encryption at rest" below.
- **Teams transport** (`infra/teams/Teams.kt`, v4.5.0): `teams.transport=log` is refused in production; `botframework` with blank credentials refuses to start in **any** mode; in production the three Microsoft base URLs must be the defaults. See "Outbound Microsoft Teams" in `.claude/docs/security-details.md`.
- **Mail transport** (`infra/mail/Mail.kt`): `mail.transport=log` writes outbound email (including generated passwords) into the application log — permitted with a warning in development, **refuse to start** in production; `smtp` with a blank host refuses to start in **any** mode. See "Outbound email" in `.claude/docs/security-details.md`.
- **Seed passwords** (`infra/db/Bootstrap.kt`, module `configureBootstrap`, runs after `configureDatabase`): in production mode the V9 demo users are **soft-deleted at startup**, and if any active account still carries the well-known `changeme` bcrypt hash the app **refuses to start**. Setting `ADMIN_INITIAL_PASSWORD` (config `bootstrap.adminInitialPassword`) rotates the V6 seed admin's password at startup — idempotent: only applied while the admin still has the seed hash, so an admin-chosen password is never overwritten. **In development mode only** (v4.1.0), the same bootstrap also seeds a relationship-less HR demo account (`hr@lettuce.local` / `changeme`) — see "Default admin & demo seed" in `.claude/docs/security-details.md` for the full shape and its production-mode neutralization. Covered by `BootstrapTest`; seed-mutating tests restore state via `TestSeedState.restoreSeedAccounts()` (`TestEnvironment.kt`).
- **Numeric config knobs are boot-validated** (checkup #36/C5, #37/C2, v4.5.2): every numeric knob (the auth-security lockout/MFA/password-reset values, the JWT TTLs, the notification/feedback-sweep retention and interval knobs, the rate-limit values) is range-checked at boot via `requireConfigInt`/`requireConfigLong`/`optionalConfigInt` in `infra/config/Config.kt`, and a malformed or out-of-range value **refuses to start in EVERY mode** (a config error, not a runtime concern; the `security.encryption.key` malformed-key precedent). The per-knob ranges live in `.claude/docs/security-details.md` ("Config range checks") — a new numeric knob joins the same helpers. Covered by `SecurityConfigTest`.

**Request body size cap (v4.14.1):** `http.maxBodyBytes` (413 problem, 4 MiB) — see "Request body size cap" in `security-details.md`.

**Server-Timing (perf measurement, 2026-10).** `Server-Timing` (DB ms, statement/transaction counts) is sent only on authenticated responses, and only in development or with `PERF_SERVER_TIMING=true` (production WARNs at boot); anonymous responses never carry it — `POST /login` was `stmt=3` unknown email vs `5` known, an enumeration oracle (`RequestTimingTest` sweeps every `security: []` operation).

**Request payload validation (convention — API-SEC-003/API-ERR-005).** Mutating routes validate payloads up-front and throw `BadRequestException` (→ `400` + `ProblemDetail`) instead of letting oversized/blank values die in the DB as `500`s: users `name` ≤50/`email` ≤254 + `'@'` + non-blank (`validateNameAndEmail`), the unique id non-blank ≤50 (`validateUniqueId`, v2.19.0), the language ∈ `SUPPORTED_LANGUAGES` (`validateLanguage`, v2.21.0) — all three in `users/Validation.kt` — password ≥ `MIN_PASSWORD_LENGTH` chars AND ≤ 71 UTF-8 bytes (`validatePassword`, `users/UserRoutes.kt` + `MAX_PASSWORD_BYTES` in `auth/Passwords.kt` — the bcrypt ceiling, v2.18.1), team/template `name` non-blank ≤100 (feature-local `validate*` helpers — teams in `teams/TeamRoutes.kt`, templates in `templates/Template.kt`) and the team roster cap `MAX_TEAM_MEMBERS = 200` (`teams/TeamRoutes.kt` — fires before the deactivated-users IN query), and — since v2.18.0, closing the last unbounded `text` columns — feedback `content` ≤5000 + `requesterMessage` ≤1000 (`validateFeedbackTexts`, `feedbacks/Feedback.kt`, checked in `FeedbackService.validate`/`editContent`) and template `content` ≤5000 (`validateTemplateContent`, `templates/Template.kt`), and the impact-log title non-blank ≤200 (v2.37.0/V66) + the four sections non-blank ≤5000 + the strict ISO period pair with start ≤ end (`validateImpactEntry`, `impactlog/ImpactLog.kt`, v2.36.0), and the succession lists ≤20 items × non-blank ≤200 chars + bench depth 1–10 + ≤100 goal links + the duplicate-goal-id 400 (`validateSuccessionPlanFields`/`validateNomination`, `succession/SuccessionPlan.kt`, v2.42.0). All limits are declared as `maxLength` in the OpenAPI spec and mirrored by the SPA's input caps + live character counters (`web/src/components/CharCount.tsx`), so a well-behaved client never reaches these 400s. Keep new validators feature-local and enforce them **after** the authz guard (403 wins over 400 for non-admins). Mass share's list shape (1–200 documents × 1–20 sharees, no duplicates — `validateShareBatchShape`, `sharing/Share.kt`) is schema-declared, so it is the malformed-body 400 class. Covered by `PayloadValidationTest`.

**Security details (on demand).** The login/session flows (password verification, lockout, the per-IP buckets, deactivated accounts, password reset, email MFA, last-login), the sharing rate limit and notification cap, outbound email and Microsoft Teams, the Swagger gate, integration API keys, canonical email and single-line identity fields, CORS/CSRF and the reverse-proxy contract, and the admin/demo/HR seeds live in **`.claude/docs/security-details.md`** — a MANDATORY read before touching `auth/`, `infra/mail/`, `infra/teams/`, `plugins/Http.kt`, `plugins/Security.kt`, `infra/db/Bootstrap.kt`, rate limits, proxy/probe/header policy, or the seeds.

### Encryption at rest (feedback content)

`feedbacks.content` and `feedbacks.requester_message` are encrypted **by the application** before they reach PostgreSQL (AES-256-GCM, fresh random nonce per value, envelope `enc:v1:<base64(nonce||ciphertext+tag)>`). Threat model: a database-level attacker — SQL access, a `pg_dump`/backup, a stolen volume — sees only ciphertext; the key lives with the app (env/k8s Secret), never in the DB. It does **not** protect against compromise of the app host/env (the key is there) or an attacker holding valid API credentials. Infra-level encryption (disk/TDE) would not address the DB-level threat at all — it is transparent to SQL.

- **Implementation**: `infra/crypto/FieldCipher.kt` (the cipher; plain JDK `javax.crypto`, no deps) + `infra/crypto/Crypto.kt` (`configureCrypto`, publishes `FieldCipherKey`; registered before `configureDatabase`). `FeedbackService` encrypts on write (`create`, `editContent`) and decrypts on read (`toFeedback()`, the list preview) — nothing above the service ever sees ciphertext, so routes/spec/SPA are untouched. Neither column is filtered/sorted/searched in SQL (the preview is `.take(200)` in Kotlin), so queries are unaffected; **never add a SQL-level filter/sort on these columns** — it would silently operate on ciphertext. Two registered content-neutral exceptions: the backfills' `notLike "enc:v1:%"` envelope-marker predicates (idempotence detection, every `EncryptedAtRest` service), and `PulseResponses.comment.isNotNull()` in `commentsForScope` (NULL-ness only — blank comments normalize to NULL before encryption, so the predicate is correct over ciphertext).
- **Key**: `DATA_ENCRYPTION_KEY` (config `security.encryption.key`), 64 hex chars (`openssl rand -hex 32`). The application.yaml default and the compose value are committed, therefore **burned** (constants in `Crypto.kt`; production refuses them — see the fail-closed list above). **Losing the key means losing all feedback content permanently** — back it up separately from (never inside) the DB backups.
- **Legacy plaintext / backfill**: `decrypt` passes non-enveloped values through unchanged, and `configureBootstrap` runs `FeedbackService.encryptLegacyRows()` at every boot — pre-encryption plaintext rows (including soft-deleted ones) are encrypted once, idempotently.
- **Rotation**: set the new key as `DATA_ENCRYPTION_KEY` and the old one as `DATA_ENCRYPTION_KEY_PREVIOUS` (decrypt-only fallback), boot once — the backfill re-encrypts **every** row under the current key — then remove the previous key.
- **Tests**: `FieldCipherTest` (unit) + `FeedbackEncryptionTest` (raw-column assertions, backfill, rotation, fail-closed). Production-mode boot tests must override `security.encryption.key` with `strongEncryptionKey()` (`TestEnvironment.kt`), since the dev default is burned — and `mail.transport` with `"disabled"`, since the dev-default `log` transport is likewise refused in production. `TestServices.feedbacks` shares the dev-default cipher so service-level writes interoperate with the booted app's reads.
- Encrypting more fields elsewhere: reuse `FieldCipher` via `attributes[FieldCipherKey]` and follow the same write/read wrap pattern; notification/event `params` (party names, enum values) are deliberately **not** encrypted — `users.name` is plaintext anyway.
- **Also encrypted (rule for new columns)**: the full per-column list (every encrypted column of the ten registrants, and the plaintext-on-purpose siblings like `goals.title`) lives in `.claude/docs/security-details.md` ("Encrypted columns"). The rule: reuse `FieldCipher` via `attributes[FieldCipherKey]` with the same write/read wrap; a newly encrypted feature implements `infra/crypto/EncryptedAtRest`, is registered in THE list in `configureBootstrap` (`infra/db/Bootstrap.kt` — the rotation backfill iterates it; never remove an entry), and writes its `encryptLegacyRows` as a one-liner over `FieldCipher.reencryptRows(table, columns, reencryptAll)` (`infra/crypto/Reencrypt.kt`); **never add a SQL-level filter/sort/aggregate on an encrypted column**; event `params` carry positions/dates/numbers/enum names only — **never item/description/summary/comment/list text, and review params no rating values** (pinned by `OneOnOneEncryptionTest`/`GoalEncryptionTest`/`PerformanceReviewEncryptionTest`).
