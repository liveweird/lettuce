# Telemetry (v4.20.0)

The process's own vital signs: a bounded Dropwizard registry and log reporter, a sampler that persists them into two tables (V95), and — landing in the following commits of the v4.20.0 branch — an ADMIN read API and a side panel. Ported from Toadie 2.28.0 (`~/Sources/toadie`, PR #172, itself from Flow 1.17.0); this doc grows with each part. Numbers and labels only, never person or document data (see "Never recorded").

## Sampler

- **Module.** `configureTelemetry` (`telemetry/Telemetry.kt`, registered right after `configureBootstrap`) validates `telemetry.*` on EVERY boot, enabled or not (`TelemetryConfig.kt`, ranges in "Config range checks", `.claude/docs/security-details.md`), then on `ApplicationStarted` builds one `TelemetrySampler` (published as `TelemetrySamplerKey`) and starts its loop. `TELEMETRY_ENABLED=false` starts none. `ApplicationStopping` cancels the scope and joins it for at most 2 s, BEFORE the pool is disposed on `ApplicationStopped`. It reads `R2dbcDatabaseKey`, `ConnectionPoolKey` and `MetricRegistryKey` — attribute keys, never the packages behind them.
- **Cadence.** The first tick lands 5 s after start (so a fresh process shows up at once), then one per interval aligned to the clock: `telemetry.sampleIntervalSeconds` (env `TELEMETRY_SAMPLE_INTERVAL_SECONDS`, default 300, 60..1800 and a divisor of 3600 so an hour's samples tile it). That value is the stored raw `resolution` and, capped at 300 s, the request timers' window.
- **A tick** runs under `interval / 2`: every per-process collector (JVM, cgroup, pool, requests) in `catchingFailures`, isolated from the others (one WARN per failing collector per episode — "Telemetry collector <name> failed: …", the exception's `toString` through `safeForLog` so a database failure shows only its class chain and SQLSTATE, at most 300 characters, never a stack — and one INFO "recovered"); the process row's `last_seen` stamp (re-registering if an operator pruned the row); the readings written as multi-row `INSERT … ON CONFLICT DO NOTHING` statements, one per power-of-two chunk, in one transaction (98 rows go out as 64 + 32 + 2; `infra/db/MultiRowInsert.kt`; non-finite values dropped); then the collectors' COMMIT steps; then the CLUSTER section. The process identity (`HOSTNAME`, else a resolver lookup that can block for seconds) is resolved inside the sampler's coroutine, never in the synchronous startup handler. These are operational log lines, not audit events (nothing person-related is read or mutated).
- **Delta baselines advance only for what was stored.** The collectors that difference a cumulative figure (requests: `previous`) keep their baseline until the sampler has durably inserted the tick's readings and then calls the collector's `commit` (`ProcessCollector.commit`): a failed insert (a database outage) loses no interval — the next tick reports both intervals' 5xx and 429s. Each collector commits on its own, and one that threw is not committed, so no collector consumes another's baseline. A tick whose bucket is not newer than the newest one stored (the wall clock stepped back, or a second tick in the same bucket) is skipped before it collects and before the cluster section, because its insert would write nothing (`ON CONFLICT` keeps the first row) yet commit the baselines: its deltas roll into the next bucket. `JvmProbe`'s CPU and GC deltas and `mem.old_gen_peak` (reset on read) still advance when read, so a failed insert loses them. **Delivery is at-least-once:** an insert whose outcome is unknown (a lost reply to COMMIT, or the tick budget cancelling while it awaits it) is not committed, so if the rows were in fact stored the next tick counts that interval again. Pinned by `TelemetryCommitTest`. The baselines live in memory per process (`.claude/docs/persistence.md` "Per-instance by design").
- **The cluster section** runs in ONE short transaction under `pg_try_advisory_xact_lock(TELEMETRY_LOCK_KEY)` (below), skipped when the `telemetry.cluster_ms` marker already sits at this bucket (another replica served it): the retention (hourly rollup of every complete hour that ended at least `max(10 min, interval / 2)` ago, in a savepoint, then the prune only after a rollup that inserted), then the decision which heavy collectors are due, then the marker. A failed section is retried in the next bucket.
- **The heavy phase** (budget `2/5 interval`, so the light phase plus the heavy one always fit in an interval). The cluster section only DECIDES that a heavy collector is due (its marker `telemetry.storage_ms` is absent or at least `storageIntervalSeconds` old) and CLAIMS the run by writing that marker with value 0, committed with the cheap readings; the run itself starts AFTER that transaction, so a scan never sits inside the lock transaction. It reads through a `HeavyReader`: every statement a SHORT transaction of its own (no lock held across scans, so a deploy's `ALTER` is never queued behind them), then one more transaction inserts the readings and sets the marker to the run's duration (at least 1 ms). A run is attempted at most once per interval whatever its outcome: a failing collector is one WARN per episode, a run that outruns the budget is cancelled with one WARN (collector "heavy"), and a marker still at 0 is a claim that did not complete — not retried before the next interval. The only heavy collector is the database storage run. No statement carries a `queryTimeout` of its own: the global `postgres.statementTimeoutSeconds` (`.claude/docs/persistence-details.md`) and the budget bound it.
- **The lock.** `TELEMETRY_LOCK_KEY = 0x4C65747454656C65L` (the ASCII bytes of "LettTele"), the single-`bigint` form. It is disjoint from the other advisory locks: MFA's single-`bigint` keys are user ids, and the share and team locks use the two-`int` form (PostgreSQL's two keyspaces never overlap). One process per bucket holds it, so a second replica never repeats the rollup, the prune or a heavy claim — the mechanism even with one replica. A row lock cannot do the job (no row exists until the work was done). The per-process rows (JVM, cgroup, pool, requests) are written by every replica, attributed to its own `telemetry_processes` row.

## Storage and retention

- **Tables (V95).** `telemetry_processes` — one row per JVM run (`instance` = the pod/container name, `started_at`, `last_seen` stamped every tick, optional `build_version`/`build_commit`, `processors`, `heap_max_bytes`, `container_limit_bytes`; unique on `(instance, started_at)`). `telemetry_samples` — ONE narrow table for every metric: `resolution` (the sample's width in seconds; a raw sample stores the sampler's REAL interval, a divisor of 3600 from 60 up; 3600 = an hourly rollup), `ts`, `process_id` (`ON DELETE CASCADE`), `metric`, `label`, `n`, `avg`, `max`; primary key `(resolution, metric, ts, process_id, label)`. A new metric is a line in `TelemetryMetrics.kt`, never a migration. Every raw-tier predicate is `resolution IN (RAW_RESOLUTIONS)` (equality prefixes on the key, not a range); `TelemetryStoreTest` pins that list against the V95 CHECK.
- **Hourly rollup.** `n` = the raw samples folded in, `avg` their n-weighted mean, `max` the largest raw max, so a 5-minute peak survives; a DELTA's `avg * n` is the hour's total. Idempotent (`ON CONFLICT DO NOTHING`), one statement that returns whether it inserted.
- **Retention (hard delete — the registered exception in `.claude/docs/persistence.md` "Soft delete").** Raw samples 7 days, hourly rows 90 days, processes silent for 90 days (their samples cascade). A row exactly at its cutoff stays. The prune runs only after a rollup that inserted (once an hour in steady state, never while the rollup keeps failing). Both tables are regenerated observations: the perf generator seeds neither (`NOT_SEEDED`), a backup may skip their rows (`.claude/docs/backup-and-restore.md`).
- **Footprint.** About 100 rows per tick for a typical process, ~206 B per row measured on Toadie's PostgreSQL 18 (heap 90 + indexes 116): tens of MB at steady state for one quiet process; a busy one with many active route labels (~200 rows per tick) approaches ~80 MB raw over 7 days plus a similar hourly volume over 90 days. Lettuce's own figures arrive after the first week; the per-route labels (below) scale with ACTIVE routes (~3 rows each per tick).

## Metrics

`TelemetryMetrics.kt` is the registry of every name a sampler may write; each has a kind (GAUGE — the instantaneous value; DELTA — the change over the interval; PERCENTILE — a quantile of the interval's window), a unit and a group (`MetricGroup { MEMORY, JVM, REQUESTS, DATABASE, TELEMETRY }` — the panel's sections and the read API's `group`, in the following commits).

- `mem.*` (MEMORY): heap used/committed, the old generation's peak since the previous sample, non-heap, direct buffers; and, from the cgroup (`CgroupProbe`, cgroup v2 and v1, Linux only — a figure the host cannot tell is no row), current, anon, working set (`current - inactive_file`, what the kubelet evicts on), the lifetime peak and `VmRSS`.
- `jvm.*` (JVM): `cpu_ratio`, `threads` (the MXBean count, never a dump), `gc_count`/`gc_time_ms` per collector (deltas).
- `pool.*` (DATABASE): `acquired`/`idle`/`pending`/`allocated` of the R2DBC pool, read from r2dbc-pool's own `metrics` through `ConnectionPoolKey` — the RAW pool, published before the optional `R2dbcTelemetry` wrapper, so the figures stay readable with DB spans on (`ConnectionPoolTest` pins `metrics` present for r2dbc-pool 1.0.2). `ConnectionPool.figures()` lives in `Telemetry.kt`.
- `http.*` (REQUESTS): `count`, `5xx`, `429` (deltas) and `p50`/`p95` (percentiles, milliseconds), per label.
- `db.size`, `db.group.size`, `db.rows` (DATABASE): the database sections' storage figures.
- `telemetry.cluster_ms`, `telemetry.storage_ms` (TELEMETRY): the cluster section's duration and the heavy run's duration — also their markers (above).
- There is NO pressure section: Lettuce has no in-process bounded things (no read ledger, jq/fetch pools, admission permits); 429s sit in Requests, the pool in Database.

## Requests

`LatencyCollector.kt` reads Ktor's `ktor.calls.<route>.timer` and `.<status>` series out of the registry (`MetricRegistryKey`; never a gauge) into `http.count`/`http.5xx`/`http.429` (DELTAS of the cumulative counts against the last COMMITTED read, kept in memory, the first tick counting since start) and `http.p50`/`http.p95` (the timers' windowed snapshots, merged per label so the total's percentile is a real one, not a mean of percentiles).

- **Labels.** `*` is the total: every routed `/api/` and `/integration/` template except the telemetry API itself (`/api/v1/telemetry*`; `/healthz`, `/readyz` and the static/SPA routes are not API traffic). EVERY such template also gets a label of its own (`isLabelled = isCounted`, decision D4 — Lettuce's heavy routes are the list roots, so no suffix rule can pick them). Bounded by the routing tree: 125 templates today (longest 56 characters of the 120-character column); the registry names instruments per routed LEAF (path + method — a few hundred), a meter, a timer and one per status seen, so the worst case (ten statuses per leaf) stays under the 5 000-name cap of `TelemetryRegistry` — past the cap a route first hit later would drop out of the total, not just its label, `{id}` stays literal, and a label writes rows only in an interval that saw something. `LatencyCollectorTest` walks the real routing tree and fails when the labelled set stops being the counted set, a template outgrows the column, or the leaf count would crowd the registry cap.
- **Normalisation.** `normaliseRoute` strips every parenthesised selector from the name Ktor 3.6 writes (`/(authenticate "default")/api/v1/users/(method:GET)` becomes `/api/v1/users`) and collapses doubled and trailing slashes. Pinned by `LatencyCollectorTest` against the names Ktor really writes, so an upgrade that renames the series fails a test instead of silently emptying the panel.
- **No 429 correction.** Ktor marks the RateLimit plugin's bodiless 429 and StatusPages' re-answer of it; the second answer lands in the routed name's `429` meter a second time only on a route whose name equals its URI (no selector, no path parameter, no query string). Every rate-limited Lettuce route carries the `(RateLimit x)` selector, so the re-answer falls back to a URI name `TelemetryRegistry` refuses: each rejection counts once, with or without a query string. `LatencyCollectorTest` drives the login route past a lowered limiter, refresh (30/min), password reset (5/min) and the MFA step (10/min) at their fixed buckets, the per-caller `shares` and `shares-batch` buckets and `/integration/graphql` + `/schema` through the shared integration bucket, and asserts the `429` count equals the rejections and `http.count` the requests sent. A hand-written bare `/api/` route answering a bodiless 429 itself would double-count — none exists; throw `TooManyRequestsException` instead, which is answered once.
- **Unrelated to `Server-Timing`.** `plugins/RequestTiming.kt` counts a request's DB statements for the perf harness and does not touch the registry.

## Database

`StorageCollectors.kt` (the heavy phase): `db.size` (`pg_database_size`), `db.group.size` per hand-listed table group (the sum of `pg_total_relation_size` — heap, TOAST and indexes — of its tables) and `db.rows` per counted table. The groups cover every `public` base table (relkind r/m of `pg_class`, Flyway's history aside) exactly once; the `teams_current` and `team_members` views (V93) are no storage relations and are excluded by construction. `StorageCollectorsTest` fails when a migration adds a table that is in no group or two, so a new table must be assigned here.

**Counted tables (14):** `db.rows` is the non-deleted rows (`NOT marked_as_deleted` — a deactivated user still counts) of users, teams, feedbacks, one_on_one_meetings, goals, team_kpis, performance_reviews, days_off_requests, impact_log_entries, succession_plans, and ALL rows of pulse_responses, notifications, document_shares and telemetry_samples (retained history or regenerated observations: pulse responses are never deletable, shares are never removed, and a soft-deleted notification is still stored until the retention purge — the table's size is the point). The only identifiers interpolated into SQL are the fixed `COUNTED_TABLES` names, guarded by a plain-name check (the group names are only map lookups and labels). Catalog sizes plus `count(*)` only — no content column is ever selected, so the encrypted-at-rest columns are never touched.

## Never recorded

The one home of this list: JVM arguments, environment variables (only `HOSTNAME`, `LETTUCE_BUILD_VERSION`, `LETTUCE_BUILD_COMMIT` are read), system properties, request paths with identifiers (route templates only, `{id}` literal), query strings, document or person content of any kind (no content column is ever selected), user, client or token identity, the integration API keys, labels longer than 120 characters. The probes read counters and sizes only — never a thread dump.

## Build identity

The process row carries the image's optional `LETTUCE_BUILD_VERSION`/`LETTUCE_BUILD_COMMIT` (Dockerfile runtime-stage `ARG` → `ENV`, declared after every `COPY`/`RUN`; `docker-compose.yaml` passes `build.args`; unset or blank = `NULL` columns; control characters stripped, 64 characters at most). `ProcessIdentityTest` pins that nothing else is read.

## Layering

`telemetry/` is the TOP layer, an observer of every lower one: it reaches the registry, the database and the pool through attribute keys and nothing outside it imports it (`TelemetryLayeringTest`; `application.yaml`'s module line is not a source import). Lower layers that the sampler needs expose seams instead — `plugins/Monitoring.kt` owns the telemetry sample-interval bound because the registry's timer window is derived from it.

## Tests

`TelemetryConfigTest`, `TelemetryMetricsTest`, `TelemetryStoreTest` (the registry, idempotent insert, rollup, prune boundaries, cascade, the lock), `TelemetrySamplerTest`, `TelemetryCommitTest`, `TelemetryLifecycleTest` (the real application samples itself; the loop is completed after stop), `HeavyCollectorsTest`, `StorageCollectorsTest`, `LatencyCollectorTest`, `JvmProbeTest`, `CgroupProbeTest` (the Linux parsing against fake roots), `ProcessIdentityTest`, `TelemetryLayeringTest`, plus C1's `TelemetryRegistryTest`/`MonitoringReporterConfigTest`/`RoutingNamesTest`. The suite default is `telemetry.enabled=false`; the telemetry tests own the two tables (`.claude/docs/testing.md`).

## Registry & reporter

- **Where.** `plugins/Monitoring.kt`. `configureMonitoring` installs Ktor's `DropwizardMetrics` over a `TelemetryRegistry` (a `MetricRegistry` subclass) and publishes it as `MetricRegistryKey`; the telemetry sampler reads the request timers from that attribute, so nothing below `telemetry/` imports it. `CallId` (the `X-Request-Id` header) is installed in the same function and is unrelated to the registry.
- **Sliding-window timers.** Route timers (`ktor.calls.<route>.timer`) keep a TRUE sliding window (`SlidingTimeWindowArrayReservoir`) of `min(telemetry.sampleIntervalSeconds, 300)` seconds instead of Dropwizard's decaying reservoir, whose percentiles lag a burst for minutes — the sampler reads p50/p95 of the window since its previous tick. Ktor's global `ktor.calls.duration` timer keeps the default reservoir (nothing reads it windowed). Memory price: about 16 B per update held for the window, ~10 MB at a sustained 2 000 requests/s against the 256 MiB heap.
- **Bounded names.** Ktor names an UNROUTED call's instruments after the raw request URI (query string included), and a registered instrument is never evicted, so an anonymous client could mint one per distinct URL. `TelemetryRegistry` therefore (1) never registers a `ktor.calls.` name containing `?`; (2) past the fixed global names, registers a family name only when it is a route's `.meter` (only a ROUTED call creates one) or its route's `.meter` is already registered; (3) caps the family at 5 000 names with one WARN (sized from the routing tree's leaves, see "Labels"). Past any of these the caller gets a detached instrument that dies with the call. Pinned by `TelemetryRegistryTest` (floods of unrouted and rate-limited URLs register nothing new).
- **The `?` rule's tripwire.** A ROUTED call is named after its `RoutingNode.toString()`; a route name with a `?` (an optional query field of a `@Resource`, an optional path parameter) would silently lose its metrics. `RoutingNamesTest` walks the real routing tree and fails when one appears — revisit the rule BEFORE adding such a field.
- **No JVM gauge sets.** `registerJvmMetricSets = false`: Dropwizard's thread-states gauge dumps every thread on each reporter run; the sampler reads the MXBeans itself.
- **The reporter.** `monitoring.reporterIntervalSeconds` (`METRICS_REPORT_INTERVAL_SECONDS`, default 300): `0` = off (metrics are still collected), else `30..3600`; anything else (or non-numeric) refuses startup in every mode (`requireConfigInt`). Was a fixed 10 s. The `Slf4jReporter` (logger `metrics`) filters out any name with a `?` (defence in depth) and stops with the application (`MonitoringTest`: no leaked scheduler thread). `MetricsReporterKey` (a `StartedReporter` with its period) is published only when the reporter runs — `MonitoringReporterConfigTest`'s seam.
- **Not related:** `plugins/RequestTiming.kt` (`Server-Timing`, `request.slow`) counts a request's DB statements for the perf harness and does not touch the registry.
- **Config.** The `telemetry:` block (`enabled`, `sampleIntervalSeconds`, `storageIntervalSeconds`) in `application.yaml`; `sampleIntervalSeconds` is read twice — by the registry's window (`plugins/Monitoring.kt`) and by `TelemetryConfig`. Ranges in "Config range checks", `.claude/docs/security-details.md`. The perf overlay sets `TELEMETRY_ENABLED=false` so `pg_stat_statements` windows stay request-only.
