### Dictionaries (global ordered value lists)

> v2.0.0 added a FOURTH dictionary: `PULSE_ROTATING_QUESTION("pulse-rotating-questions")` — the pulse survey's Q6 bank (V50 seed). Same generic machinery; entries must read as statements answerable on the five-point agreement scale; cycles snapshot the picked entry's text (both languages since V53), so renames never rewrite a past cycle (see "Pulse surveys" in `.claude/docs/features/pulse-surveys.md`).

Three **global dictionaries** (v1.31.0) — **career paths**, **career specializations**, **seniority levels** — each an admin-curated **ordered** list of short text values with hidden stable ids — **bilingual since V53 (v2.6.0): every entry holds an English AND a Polish value** (`value_en`/`value_pl`), unique per language within the dictionary, and clients render the viewer's language. One shared table `dictionary_entries` (`V31`): enum-name discriminator column (`Dictionary` in `dictionaries/Dictionary.kt` is the whitelist — slugs `career-paths`/`career-specializations`/`seniority-levels` are its URL forms), `position` (rewritten from payload order on every save; soft-deleted rows keep stale positions — reads filter active), `value_en`/`value_pl` ≤100 each (stored **trimmed**; plaintext), standard soft-delete, and the per-language partial unique index pair freeing a deleted entry's values (see "Soft delete" in `.claude/docs/persistence.md`). Implementation in `server/src/main/kotlin/dictionaries/` (`Dictionary.kt` DTOs + shared `validateDictionaryUpdate`, `DictionaryService.kt`, `DictionaryRoutes.kt`). Defaults are seeded by `V32` (v1.31.1) — additive and idempotent (`ON CONFLICT` targeting the then-single partial unique index; the seeds run before the V53 rename, so their checksums are untouched), so admin-curated values are never overwritten; `V53` backfills Polish (real translations for still-unrenamed seed values — seniority levels/language names keep the market-standard English loanwords — and copy-EN for everything else).

- **API — two operations only** (`/api/v1/dictionaries/{dictionary}`; unknown slug → 404): `GET` (any authenticated) returns the **unpaged** ordered `{items:[{id,valueEn,valuePl}]}` (`position ASC, id ASC` — the `/alerts/visible` shape; deliberately NOT a standard list endpoint, ≤200 entries by validation). `PUT` (ADMIN only, guard before slug resolution, `204`) is a **whole-document replace** — the 1:1 `replaceNotes`/`requirePayloadIds` idiom adapted to soft-delete: an item with an `id` renames/repositions that active entry in place (rename keeps identity), an id-less item inserts, an active entry missing from the payload is **soft-deleted**. The active-rows-only snapshot makes a soft-deleted id a foreign id (400 — no resurrection; re-adding the value mints a new id), and **soft-deletes run before upserts** so remove+re-add and rename-onto-a-removed-value work in one save. Validation (400): blank/oversized values in either language, payload-duplicate values **per language** (case-sensitive, trimmed — the same string may be one row's English and another's Polish), duplicate/foreign ids, >200 items; a clash with a surviving active value (e.g. **swapping two values in one save** — per-statement unique index, documented limitation; workaround is a two-save rename) → 23505 → 409. Empty `items` clears the dictionary. Audit: one `dictionary.updated` per successful save. No events table, no notifications, no encryption (short public-ish labels).

- **Career progression (v2.15.0; the career profile joined in v1.32.0)** — every user has a **timeline of positions** (position = the dictionary-backed triple career path / career specialization / seniority level — ALL THREE required on writes since v2.15.1; pre-v2.15.1 rows may be partial and still read fine, completing on their first correction), stored in `user_career_positions` (`V57`, which also DROPPED the V33 `users.career_*_id` columns with **no seed** — histories started empty by decision, there being no truthful start date to invent). **Start-only model**: rows store only `start_date` (strict zero-padded ISO in a VARCHAR — lexicographic == chronological, the V34 idiom, partial unique `(user_id, start_date)` over active rows); a position's `endDate` is DERIVED at read time — the day before the user's next active position starts — and the latest position is open-ended, so the timeline is continuous and non-overlapping **by construction**. Refs are entry ids resolved at read time (renames propagate; a **soft-deleted referenced entry keeps resolving**; newly-assigned ids validated ACTIVE via the `requireActiveEntries` changed-refs idiom — a date-only correction never trips over a stale ref).
