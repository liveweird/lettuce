### Team KPIs

A **team KPI** (v1.27.0) is set by a manager for a **team they manage** and tracked over time — the goals feature re-shaped from a (manager, subordinate) pair to a (manager, team) pair: a plaintext `title` (≤200 — lists sort/substring-filter on it), an encrypted `description` (≤4000), a `type` limited to **`NUMBER`/`PERCENTAGE`** (no PLAN — the target is always required/finite, 0–100 for PERCENTAGE, and there are no milestones), a NOT NULL **`target_direction`** (v2.41.0/`V67`, the goals `TargetDirection` enum imported from `goals/Goal.kt` — AT_LEAST (default; pre-V67 rows backfilled) or AT_MOST; request-side it defaults in the DTO, a flip mints `TARGET_DIRECTION_CHANGED{from,to}`), **no due date**, a series of **data points** (v1.29.0 — see below), and an encrypted `summary` recorded at archiving. Tables `team_kpis` (`V28`, standard soft-delete) + `team_kpi_values` (`V30`, hard-delete detail), audit table `team_kpi_events` (`V29`). Implementation in `server/src/main/kotlin/teamkpis/` (`TeamKpiService`, `TeamKpiEventService`, pure `TeamKpiEvents.kt`/`TeamKpiNotifications.kt` builders, `TeamKpiRoutes.kt`) — cloned from the goals package; where this section is silent, the goals behavior applies.

- **The current-manager derivation (the defining difference)**: the KPI row stores **`team_id` and — since V62 — `created_by`, never a manager id**. The manager in every response (`managerId`/`managerName`) is resolved from `teams.manager_id` **at call time** through the service's `joined()` — so a reassigned team's new manager takes over its KPIs (write access included) and the old manager, unless still a member or in the chain, loses everything — **even as the KPI's stored creator** (v2.26.0 user decision: `created_by` is INFORMATIONAL ONLY — the Creator column/field, `creatorId`/`creatorName`/`creatorDeleted` resolved through a second `creator_users` alias; no right ever keys on it). `TeamKpiService.isTeamMember` / `managesTeam` (both filter soft-deleted teams) are the membership predicates; `managesManagerOf` wraps `isInManagementChain` (the chain rules), and `managesTeamOrChain` backs the create gate. **Capability flags (v2.26.0 — the FIRST server-computed capabilities in the codebase)**: `TeamKpiResponse.canManage`/`canRecordValues` and `TeamKpiListItem.canManage` state the CALLER's rights (stamped by the routes on GET/POST, by the list via one per-request `transitiveSubordinateIds` walk) — the SPA gates every affordance on them and never compares `managerId` to the session user anymore (it cannot walk chains). Since v2.34.0 the per-TEAM create entry point is covered too: `TeamResponse.canManageKpis` (computed from the same predicate at the teams single GET/create) drives the TeamKpis drill-down's New button — the last KPI-area client-side inference is gone.
- **Status machine**: the goals shape — `DRAFT ↔ ACTIVE ↔ ARCHIVED` (`TeamKpiStatus`; goals matched the ARCHIVED terminal state in v1.41.0), four action endpoints `POST …/{id}/activate|deactivate|archive|reopen`, archive is the only bodied one — `{summary}` required non-blank ≤4000, kept on reopen. No due date ⇒ **no activate gate** (the goals stale-draft 400 has no analogue). Creation always lands in DRAFT with no data points (`currentValue = 0.0`, `currentValueDate = null`) — **createable by the team's current manager OR any manager in the chain above them** (v2.26.0, `managesTeamOrChain`; the caller is stamped `created_by`); a DRAFT-only definition PUT (a type change **wipes all data points** — the recompute then yields 0.0/null), DELETE DRAFT-only (non-draft → `400`), wrong-status mutations `409` inside the service transaction. **Every definition/lifecycle write (PUT, DELETE, the four transitions) is manager-or-chain** (`requireTeamKpiManage` via the route preamble `manageGuardedKpi`) — members never, ADMIN/HR never.
- **Data points (v1.29.0 — replaced the v1.28 progress PUT)**: the collected measurements are first-class rows — `team_kpi_values(team_kpi_id, value_date, value)`, strict ISO date (today or the past, plus ONE day of timezone tolerance since v2.26.1 — clients submit their browser-local date while the server runs UTC; `validateTeamKpiValue` with the injectable-`today` idiom), **at most one value per date** (`UNIQUE (team_kpi_id, value_date)` — a duplicate raises 23505 → the central 409 mapping, no pre-check by design). Sub-resource under the document: `GET …/{id}/values` (read-guarded like the doc; sorted `value_date DESC`, newest first), `POST …/{id}/values` (201 + Location), `PUT`/`DELETE …/{id}/values/{valueId}` — the mutations are **manager + chain + current team members** (v2.26.0, `requireTeamKpiValueWrite` via `valueGuardedKpi` — recording measurements is the team's shared work; HR's read grant carries no pen) + ACTIVE-only (`requireActiveKpi` inside the service transaction); a foreign/missing `valueId` is 404, a correct-to-occupied-date 409, and an exact no-op correction is 204 minting nothing. Every mutation ends with `recomputeCurrent` in the same transaction: the denormalized `team_kpis.current_value`/`current_value_date` always equal the **max-dated** point (0.0/null when none) — so deleting or re-dating the top point rolls Current back, which the v1.28 latest-dated-wins column could not.
- **Reads/visibility**: DRAFT is private to the **current manager + the chain above them** (v2.26.0 — the chain creates and edits drafts, so it reads them; + HR auditor, audited `hr.read` with resource `teamKpi`); current **team members** read only once out of DRAFT — see `.claude/docs/authorization.md`. There is deliberately **no HR `view=user` auditor list** (a per-TEAM resource doesn't fit the per-USER audit view; HR keeps audited single-GET access — documented in the spec).
- **List** (`GET /api/v1/team-kpis?view=own|managed`): `own` (default) = KPIs of the non-deleted teams the caller is a **member** of, `status ≠ DRAFT` (mirrors the read guard, every listed row is openable); `managed` = KPIs of the teams whose **current manager** the caller is — or, with **`includeIndirect=true`** (v2.26.0, strict boolean via `optionalIncludeIndirect`, managed-only else 400), of every team managed by anyone in the caller's transitive subtree (`Teams.managerId inList transitiveSubordinateIds(caller)+caller`, the TeamService idiom) — every status, DRAFTs included (openable: the chain reads drafts) — **soft-deleted teams included** (`teamDeleted` flag; the manager keeps a disbanded team's history, while members and the drill-down lose access automatically). Sortable `id`/`teamName`/`managerName`/**`creatorName`**/`title`/`type`/`status`/`targetValue`/`currentValue`/`createdAt`/`lastModified`, default `-createdAt`; `teamName`/`title` substring + `teamId` (the per-team drill-down)/`type`/`status` equality + `createdAt[gte]`/`lastModified[gte]` filters. Rows carry team + manager + creator names, `canManage`, title, and the value fields — never description/summary. **`GET /api/v1/teams` gained `includeIndirect` too** (only with `managerId`, else 400 — widens that equality filter to the manager's subtree; backs the create picker).

The **KPI data tab** is `components/TeamKpiValuesEditor.tsx`: the points newest-first in a table; for a `canRecordValues` caller on an ACTIVE KPI (v2.26.0 — manager, chain, or team member) an add-row (`DateField` defaulting to today, `maxIso` today as a calendar hint (v3.5.0) + value `NumberInput`) plus per-row inline edit (pencil → date/value inputs with check/X) and delete (`useDeleteConfirm` modal) — **every operation persists immediately** (there is no Save button on the screen); duplicate dates are pre-checked client-side against the loaded list (`teamKpi.validation.duplicateDate`), a racing server 409 maps to `teamKpi.error.valueConflict`; non-writers (and non-ACTIVE states, with a dimmed hint for `canRecordValues` callers) get the read-only list. - **Events**: `TeamKpiEventType` = CREATED / TITLE_CHANGED / DESCRIPTION_CHANGED / TYPE_CHANGED / TARGET_CHANGED / TARGET_DIRECTION_CHANGED (v2.41.0, `{from,to}` direction names) / **VALUE_RECORDED `{date, value}` / VALUE_CORRECTED `{fromDate, fromValue, toDate, toValue}` (always all four, even for a one-dimension change) / VALUE_REMOVED `{date, value}`** (v1.29.0 — replaced `PROGRESS_UPDATED`; the DB is recreated, so no legacy fallbacks exist anywhere) / STATUS_CHANGED / DELETED. A no-op correction mints nothing; the type-change wipe emits nothing beyond TYPE_CHANGED (the SPA wording says the points were removed). Params never carry title/description/summary text. Read via `GET /api/v1/team-kpis/{id}/events`, authorized like the single GET; persisted by the route.
- **Notifications**: every status transition notifies **all current team members + the team's current manager, minus the ACTOR** (v2.26.0 — the actor may be a chain manager or, for data points, a member; resolved inside the service transaction; the wire param key stays `manager` but carries the ACTOR's name) — the deactivate notification carries **no link** (a DRAFT is unreadable for members). Every **data-point mutation** (add/correct/remove — v1.30.0; the route resolves the actor's name via `TeamKpiService.actorName`) notifies the same audience with the value params and a view link; an exact no-op correction stays silent. See the table under "Notifications" in `.claude/docs/features/notifications.md`. Creation, definition edits, and deletion notify nobody.
