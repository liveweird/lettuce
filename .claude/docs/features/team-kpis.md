### Team KPIs

A **team KPI** (v1.27.0) is set by a manager for a **team they manage** and tracked over time — the goals feature re-shaped from a (manager, subordinate) pair to a (manager, team) pair: a plaintext `title` (≤200 — lists sort/substring-filter on it), an encrypted `description` (≤4000), a `type` limited to **`NUMBER`/`PERCENTAGE`** (no BINARY — the target is always required/finite, 0–100 for PERCENTAGE, and there is no `achieved` flag), **no due date**, a series of **data points** (v1.29.0 — see below), and an encrypted `summary` recorded at archiving. Tables `team_kpis` (`V28`, standard soft-delete) + `team_kpi_values` (`V30`, hard-delete detail), audit table `team_kpi_events` (`V29`). Implementation in `server/src/main/kotlin/teamkpis/` (`TeamKpiService`, `TeamKpiEventService`, pure `TeamKpiEvents.kt`/`TeamKpiNotifications.kt` builders, `TeamKpiRoutes.kt`) — cloned from the goals package; where this section is silent, the goals behavior applies.

- **The current-manager derivation (the defining difference)**: the KPI row stores **`team_id` only, never a manager id**. The manager in every response (`managerId`/`managerName`) is resolved from `teams.manager_id` **at call time** through the service's `joined()` — so a reassigned team's new manager takes over its KPIs (write access included) and the old manager, unless still a member or in the chain, loses everything. `TeamKpiService.isTeamMember` / `managesTeam` (both filter soft-deleted teams) are the new membership predicates — nothing like them existed before; `managesManagerOf` wraps `isInManagementChain` for the chain-read rule.
- **Status machine**: the goals shape — `DRAFT ↔ ACTIVE ↔ ARCHIVED` (`TeamKpiStatus`; goals matched the ARCHIVED terminal state in v1.41.0), four action endpoints `POST …/{id}/activate|deactivate|archive|reopen`, archive is the only bodied one — `{summary}` required non-blank ≤4000, kept on reopen. No due date ⇒ **no activate gate** (the goals stale-draft 400 has no analogue). Creation always lands in DRAFT with no data points (`currentValue = 0.0`, `currentValueDate = null`); a DRAFT-only definition PUT (a type change **wipes all data points** — the recompute then yields 0.0/null), DELETE manager-only + DRAFT-only (non-draft → `400`), wrong-status mutations `409` inside the service transaction.
- **Data points (v1.29.0 — replaced the v1.28 progress PUT)**: the collected measurements are first-class rows — `team_kpi_values(team_kpi_id, value_date, value)`, strict ISO date (today or the past, `validateTeamKpiValue` with the injectable-`today` idiom), **at most one value per date** (`UNIQUE (team_kpi_id, value_date)` — a duplicate raises 23505 → the central 409 mapping, no pre-check by design). Sub-resource under the document: `GET …/{id}/values` (read-guarded like the doc; sorted `value_date DESC`, newest first), `POST …/{id}/values` (201 + Location), `PUT`/`DELETE …/{id}/values/{valueId}` — the mutations are current-manager + ACTIVE-only (`requireActiveKpi` inside the service transaction); a foreign/missing `valueId` is 404, a correct-to-occupied-date 409, and an exact no-op correction is 204 minting nothing. Every mutation ends with `recomputeCurrent` in the same transaction: the denormalized `team_kpis.current_value`/`current_value_date` always equal the **max-dated** point (0.0/null when none) — so deleting or re-dating the top point rolls Current back, which the v1.28 latest-dated-wins column could not.
- **Reads/visibility**: DRAFT is private to the **current manager** (+ HR auditor, audited `hr.read` with resource `teamKpi`); current **team members** and **managers in the chain above the team's manager** read only once out of DRAFT — see `.claude/docs/authorization.md`. There is deliberately **no HR `view=user` auditor list** (a per-TEAM resource doesn't fit the per-USER audit view; HR keeps audited single-GET access — documented in the spec).
- **List** (`GET /api/v1/team-kpis?view=own|managed`): `own` (default) = KPIs of the non-deleted teams the caller is a **member** of, `status ≠ DRAFT` (mirrors the read guard, every listed row is openable); `managed` = KPIs of the teams whose **current manager** the caller is, every status — **soft-deleted teams included** (`teamDeleted` flag; the manager keeps a disbanded team's history, while members and the drill-down lose access automatically). No `includeIndirect`. Sortable `id`/`teamName`/`managerName`/`title`/`type`/`status`/`targetValue`/`currentValue`/`createdAt`/`lastModified`, default `-createdAt`; `teamName`/`title` substring + `teamId` (the per-team drill-down)/`type`/`status` equality + `createdAt[gte]`/`lastModified[gte]` filters. Rows carry team + manager names, title, and the value fields — never description/summary.
- **SPA**: nav **"Team KPIs"** → `/team-kpis` (`pages/MyTeamKpis.tsx`, the MyGoals shape: tab "My teams' KPIs" = the unpinned own view; manager-gated tab "KPIs I've set" = the unpinned managed view + the "New team KPI" button). Dashboard **My teams** rows (`MyTeamsTable.tsx`) carry a per-team **"Team KPIs"** button → the drill-down `/teams/:teamId/kpis` (`pages/TeamKpis.tsx`, the team-pinned drill-down shape: managed table pinned via the `teamId` filter, settings `teamKpis.team`, manager-only prefilled New button). `pages/TeamKpiTable.tsx` is the GoalTable-shaped shared list — columns Team (hidden when `teamId` pins it) / Title / Created / Status / Target / Current; filters Title, Team substring, created-window, Status; **the row action is View — except the manager's own DRAFT rows, which open the definition editor directly** (v1.29.1; ACTIVE stays View — the view screen owns the data-point editing). Both KPI pages put the "New team KPI" button in the footer below the list (the house convention). **`/team-kpis/:id/view` (`ViewTeamKpi.tsx`) is THE KPI screen**: tabs **General** (title, description, type, target + the archive summary when present — no Current here) / **KPI data** / **Graph** / **History**, the manager's lifecycle actions at the bottom (DRAFT→Activate + the Edit link, ACTIVE→Return-to-draft/**Archive** — `GoalCloseModal` with `keyPrefix="teamKpi"`, its label keys kept but reworded to Archive — ARCHIVED→Reopen), footer Close = navigate back. The **KPI data tab** is `components/TeamKpiValuesEditor.tsx`: the points newest-first in a table; for the current manager of an ACTIVE KPI an add-row (`TextInput type="date"` defaulting to today, capped at today + value `NumberInput`) plus per-row inline edit (pencil → date/value inputs with check/X) and delete (`useDeleteConfirm` modal) — **every operation persists immediately** (there is no Save button on the screen); duplicate dates are pre-checked client-side against the loaded list (`teamKpi.validation.duplicateDate`), a racing server 409 maps to `teamKpi.error.valueConflict`; non-managers (and non-ACTIVE states, with a dimmed hint for the manager) get the read-only list. `/team-kpis/new` (`CreateTeamKpi.tsx` — managed-team Select, skipped when prefilled via `utils/teamKpiLinks.ts` `teamKpiCreateLink`; the create-then-activate prompt) and `/team-kpis/:id/edit` (`EditTeamKpi.tsx` — the **DRAFT definition editor only** since v1.29.0; non-manager or non-DRAFT redirects to the view) complete the routes. **The Graph tab**: `components/TeamKpiChart.tsx` — one of the two lazy `@mantine/charts` (recharts) consumers (the other: `components/ReviewRatingDistribution.tsx`, v1.40.0) — **each imports the stylesheet in its own chunk** (`@mantine/charts/styles.css`, imported here so the CSS rides the lazy chunk — without it the tooltip renders unstyled and explodes into scattered fragments; missing v1.27.0–v1.29.0), `lazy()`-loaded so the libraries stay out of the main bundle (the org-chart precedent) — plots the data points (`utils/teamKpiChart.ts` `buildTeamKpiSeries`: one point per row at its date, sorted ascending, nothing synthesized; empty state when the KPI has no points) with the target as a dashed reference line carrying **`ifOverflow: "extendDomain"`** (recharts otherwise silently discards a target outside the data-derived y-domain) and a custom `tooltipProps.content` rendering Mantine's `ChartTooltip` with the recharts numeric-x ghost row (`dataKey === "ts"`) filtered out and the epoch-millis label formatted as a date. Status UI is `components/TeamKpiStatusBadge.tsx` + the `teamKpi.status.*` labels (split from `GoalStatusBadge` in v1.29.0 — goals keep `goal.status.*`); the value formatter stayed shared on purpose — `utils/goalValues.tsx` `formatGoalValue` renders every KPI number (tables, chart, history, notifications; its BINARY branch is goals-only), and `GoalCloseModal` is likewise shared via `keyPrefix`/`maxLength` props. i18n area `teamKpi` (files `locales/{en,pl}/teamKpis.json` — the goals filename≠area precedent); mutations invalidate through `utils/teamKpiQueries.ts` `invalidateTeamKpi` (which also covers the `["teamKpiValues", id]` query both data-consuming tabs share).
- **Events**: `TeamKpiEventType` = CREATED / TITLE_CHANGED / DESCRIPTION_CHANGED / TYPE_CHANGED / TARGET_CHANGED / **VALUE_RECORDED `{date, value}` / VALUE_CORRECTED `{fromDate, fromValue, toDate, toValue}` (always all four, even for a one-dimension change) / VALUE_REMOVED `{date, value}`** (v1.29.0 — replaced `PROGRESS_UPDATED`; the DB is recreated, so no legacy fallbacks exist anywhere) / STATUS_CHANGED / DELETED. A no-op correction mints nothing; the type-change wipe emits nothing beyond TYPE_CHANGED (the SPA wording says the points were removed). Params never carry title/description/summary text. Read via `GET /api/v1/team-kpis/{id}/events`, authorized like the single GET; persisted by the route.
- **Notifications**: every status transition notifies **all current team members** (resolved inside the service transaction) except the acting manager — even when they are a member of their own team; the deactivate notification carries **no link** (a DRAFT is unreadable for members). Every **data-point mutation** (add/correct/remove — v1.30.0) notifies the same audience with the value params and a view link; an exact no-op correction stays silent. See the table under "Notifications" in `.claude/docs/features/notifications.md`. Creation, definition edits, and deletion notify nobody.
