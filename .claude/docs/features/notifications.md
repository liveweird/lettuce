### Notifications

In-app notifications are **typed structured rows** (`recipientId`, `type`, `params`, optional `link`, `wasSeen`, `timestamp`) and there is no API to create one. Like feedback events, no rendered string is stored: `type` is a `NotificationType` (`notifications/Notification.kt` — 43 values: 13 feedback-driven, e.g. `FEEDBACK_SENT_TO_SUBJECT`, the `FEEDBACK_REQUEST_EXPIRED_TO_REQUESTER`/`_TO_PROVIDER` pair (v3.8.0 — the lazy expiry sweep, see "Feedback request expiration" in `.claude/docs/features/feedbacks.md`), the `ONE_ON_ONE_CREATED_TO_SUBORDINATE`/`_TO_MANAGER` pair — see "1:1 meetings" in `.claude/docs/features/one-on-ones.md` — the six goal values (the four transition `GOAL_*_TO_SUBORDINATE` values plus the v2.8.0 progress-update pair `GOAL_PROGRESS_UPDATED_TO_MANAGER`/`_TO_SUBORDINATE`) — see "Goals" in `.claude/docs/features/goals.md` — the seven team-KPI `TEAM_KPI_*_TO_MEMBER` values (four transitions + the three data-point mutations) — see "Team KPIs" in `.claude/docs/features/team-kpis.md` — the `PERFORMANCE_REVIEW_PUBLISHED/UNPUBLISHED_TO_SUBORDINATE` pair — see "Performance reviews" in `.claude/docs/features/performance-reviews.md` — the four days-off values (`DAYS_OFF_CREATED`/`DAYS_OFF_DELETED` — v3.9.0, the create/delete team fan-out that replaced the seven lifecycle types `DAYS_OFF_REQUESTED/CANCELLED_TO_MANAGER`, `DAYS_OFF_ACCEPTED/REJECTED/CANCELLED_TO_OWNER`, and the on-behalf pair `DAYS_OFF_RECORDED_TO_OWNER`/`_TO_MANAGER` — plus `DAYS_OFF_CORRECTED_TO_OWNER` and `DAYS_OFF_ALLOWANCE_CHANGED` (v2.32.0), both unchanged — see "Days off" in `.claude/docs/features/days-off.md`) — the four pulse values (`PULSE_CYCLE_SCHEDULED/OPENED/CANCELLED`, `PULSE_RESULTS_AVAILABLE` — see "Pulse surveys" in `.claude/docs/features/pulse-surveys.md`) — the three impact-log `IMPACT_ENTRY_CREATED/UPDATED/DELETED_TO_MANAGER` values (v2.36.0 — see "Impact log" in `.claude/docs/features/impact-log.md`) — `CAREER_POSITION_STARTED_TO_USER` (v2.15.0 — see "Career progression" in `.claude/docs/features/dictionaries.md`) — and `PASSWORD_CHANGED`) and `params` is a JSON map of the **party names** (proper nouns) the message interpolates. The SPA renders each in the viewer's language (`web/src/components/NotificationsButton.tsx` `describeNotification` → `notifications.event.*` keys; the `self` param is the generic i18next-context carrier — `"self"`/`"reflection"` for the legacy self-reflection wordings (stored rows only since v2.36.0), `"admin"`/`"reset"` on `PASSWORD_CHANGED`). The feedback-driven ones are produced by **four** sources, all side-effect-free (DB-free, so directly unit-testable) functions in `feedbacks/FeedbackNotifications.kt`; `FeedbackService` resolves party display names into `params` (plus, for SENT landings, the subject's **direct managers** via `teams/ManagementChain.kt` `directManagerIds` — they gain read access at delivery) and the route persists what they return:

- **`feedbackCreationNotifications()`** — on feedback **creation**. In `REQUESTED` status: the **provider** is told (edit link) **and** the **requester** gets a no-link confirmation (worded "about yourself" when requester == subject). Created directly as `SENT` ("save & send", no draft step): the same set as the `DRAFT → SENT` transition — subject + provider (+ requester if present) — via shared `sentTo*Note` builders, so the recipients never depend on whether a draft step happened. A `DRAFT` creation mints nothing. Persisted from `POST /api/v1/feedbacks` in `feedbacks/FeedbackRoutes.kt` (`result.notifications.forEach { notificationService.create(it) }`).
- **`feedbackTransitionNotifications()`** — on a feedback **status transition**. Persisted from the POST action endpoints (`…/{id}/send|withdraw|reject|pick-up`, shared `transitionTo` handler: `toNotify.forEach { notificationService.create(it) }`).
- **`feedbackDeletionNotifications()`** — on a (DRAFT) feedback **deletion** that has a requester. Persisted from `DELETE /api/v1/feedbacks/{id}`; the notification has no link.
- **`feedbackExpiredToRequesterNotification()`** / **`feedbackExpiredToProviderNotification()`** (v3.8.0) — on the **lazy expiry sweep** (`FeedbackService.expireOverdueRequests`, no background job — the `AlertService.visible(now)` precedent): a `REQUESTED` row whose `expiresOn` deadline has passed auto-rejects, and both notify. Persisted at the **top of `GET /api/v1/feedbacks`**, alongside the row's `REQUEST_EXPIRED` audit event — same pattern as the transition POSTs, just triggered by a GET rather than a POST (the `TokenBlocklistService` "clean up during the next call" precedent). See "Feedback request expiration" in `.claude/docs/features/feedbacks.md`.

That is the whole set — any other feedback create/transition/delete, 1:1 edit/deletion, goal create/definition-edit/deletion (progress updates DO notify since v2.8.0 — see the row above), team-KPI create/definition-edit/deletion, performance-review create/edit/deletion (and its `DRAFT ↔ CALIBRATION` transitions — invisible to the subordinate), review-period or public-holiday mutation, days-off correction edit/deletion, career-position correction/deletion (only STARTING one notifies — see the row above), pulse response submission/edit or pulse settings/date change, an impact-log no-op PUT, or user mutation (allowance changes included) produces nothing. The non-feedback notifications are the 1:1 creation pair (`oneonones/OneOnOneNotifications.kt`), the goal set (`goals/GoalNotifications.kt` — transitions subordinate-only, the manager is always the actor; progress updates counterparty-directed, either party may act since v2.8.0), the team-KPI sets (`teamkpis/TeamKpiNotifications.kt` — transitions + data-point mutations, members-only, actor excluded; the value notifications are composed route-side from the pre-mutation read + `TeamKpiService.memberIds`), the performance-review publish/unpublish pair (`reviews/PerformanceReviewNotifications.kt` — subordinate-only, the manager is always the actor), the days-off set (`daysoff/DaysOffNotifications.kt` — v3.9.0: create/delete fan out to the union of the owner's teammates + their direct managers, actor excluded, via `DaysOffService.fanoutRecipientIds`; corrections/allowance stay owner-directed; recipients resolved in the service transaction), the pulse cycle set (`pulse/PulseNotifications.kt` — pure builders, recipients resolved in the cycle service's transaction, persisted via the batch `NotificationService.createAll`; the acting admin is excluded), the career-position start (v2.15.0 — the descriptor builder in `users/CareerPosition.kt`, the manager name resolved in `CareerPositionService.create`'s transaction, persisted by `users/CareerPositionRoutes.kt`; feature mapping `null` — the users area is ungated), the impact-log set (v2.36.0 — `impactlog/ImpactLogNotifications.kt`, pure builders; recipients — the owner's direct managers — resolved in the service's mutation transaction), and `PASSWORD_CHANGED` (minted inline by `users/UserRoutes.kt`'s PUT-password handler and `auth/AuthRoutes.kt`'s reset completion — before the `password_reset.completed` audit event, which tests use as a completion barrier). For **legacy self-reflection rows** (provider == subject — no longer creatable since v2.36.0, see "Feedback lifecycle" in `.claude/docs/features/feedbacks.md`) every subject/provider-directed notification above is dropped (that recipient is the acting user); requester- and **manager**-directed ones remain, self-worded (the manager is never the actor) — so a standalone self row notifies only the author's managers, and a requested one additionally the requester. A `REQUESTED` creation yields **two** notifications (provider + requester); landing in `SENT` — whether via `DRAFT → SENT` or a direct "save & send" creation — yields **one per recipient + the provider** or, with a requester attached (single-recipient by rule), **three** (subject + provider + requester), plus one per direct manager of any recipient. **The `subject` param rule for a multi-recipient feedback (v3.1.0)**: a note addressed TO a recipient (`FEEDBACK_SENT_TO_SUBJECT`, `FEEDBACK_WITHDRAWN_TO_SUBJECT`) carries that recipient's OWN name; a MANAGER's note (`FEEDBACK_SENT_TO_MANAGER`) names only the recipients who report to THAT manager (v3.1.1 — its template says "who reports to you"; `FeedbackService.resolveSubjectManagers` hands the fan-out a manager→recipients map); every other note (provider, requester, rejected/picked-up/deleted) carries all recipients' names joined with `", "` in position order (`Feedback.subjectLabel`) — identical to today's value for one recipient, so the `notifications.event.*` templates and the email catalog interpolate unchanged. For the subject/requester `view` links the recipient must be permitted to read the feedback under its `FeedbackVisibility` (`subjectCanRead`/`requesterCanRead` in the same file) — otherwise `link` is null; the provider always owns the feedback and managers always read delivered feedback, so those links are unconditional.

**Notifications vs. the SPA's success toasts — the boundary rule.** A toast (`showSuccessToast`, see `web/CLAUDE.md`) is the **actor's** ephemeral client-side confirmation that their own mutation succeeded; a notification is persistent **counterparty** awareness of an event they wouldn't otherwise see. One event routinely produces both (the manager who activates a goal gets a toast, the subordinate a notification), and recipient sets exclude the actor as a rule. The **three** deliberate actor-directed exceptions are **durable receipts**, where a 2.5-second toast isn't enough of a record: feedback landing in `SENT` notifies the **provider** ("you sent this", with the view link), 1:1 creation notifies the authoring **manager**, and `PASSWORD_CHANGED` fires even on a self-change (a security notice is valuable precisely as a persistent row). An on-behalf days-off recording used to be a fourth exception (the acting manager got a receipt); v3.9.0 retired it along with the lifecycle — the acting manager is now just excluded from the fan-out like any actor. A new notification type directed at the acting user must justify itself the same way; otherwise the actor's toast is the whole confirmation.

**Email mirror (v2.3.0; independent of IN_APP suppression since v4.0.0).** Every minted notification is ALSO considered for email — sent to the recipient's email address independently of whether its IN_APP row was itself suppressed at mint (see "Preferences" below: the two channels are independent switches, so a type a recipient muted in-app can still arrive by email, and vice versa). The hook is the mint chokepoint itself: `NotificationService.create`/`createAll` insert the row(s) (or skip the insert for a type the recipient disabled IN_APP), then hand the ORIGINAL batch to `notifications/NotificationEmailer.kt` (constructed in `configureDatabase`; `configureMail` runs earlier, so the transport and `mail.appUrl` are readable), which fires **one fire-and-forget launch on the Application scope** per batch — never on the request path; a send failure is only logged (`ch.nokillswit.mail` logger; no queue/retry/outbox, the house mail posture). Inside that launch, `dispatch` reads the whole batch's per-type `EMAIL`-channel disabled set **once** (`NotificationPreferenceService.disabledFor`, one `IN` query) before looping over recipients — not one read per send. The wording lives in `notifications/NotificationEmail.kt` — a pure, DB-free per-language catalog mirroring the SPA's `notifications.event.*` strings, rendered in the RECIPIENT'S language since v2.21.0 (V61 `users.language`, read fresh at send time; EN fallback). Every text is an `infra/mail/LocalizedText(en, pl)` — the exhaustive `when` means **a new NotificationType will not compile without wording**, and the LocalizedText constructor arity means **a new language will not compile without translating every email text**. Per-area single-language subjects, the i18next context variants replicated (`self`/`reflection`, `admin`/`reset`, ADD/SUBTRACT), raw ISO dates/values (documented simplification — the SPA formats per locale), and the deep link appended as `mail.appUrl + link` only when both exist. Send-time skip rules, checked in this order against a fresh `UserService.read` per recipient:

| Condition | Effect |
|---|---|
| `mail.transport=disabled` (null mailer — the k8s default) | no emails at all, silently (email is a side effect, never 503) — checked once per batch, before the per-recipient loop |
| recipient soft-deleted or deactivated | skipped |
| `NotificationType.lockedOn` (`PASSWORD_CHANGED`) | the three rows below are ALL bypassed — a locked type is emailed regardless of the V51 master opt-out, its feature, or its own `EMAIL` preference |
| recipient opted out (`users.email_notifications_enabled = false`, V51) | skipped (bypassed for a locked type) |
| the type's `feature` ∈ the recipient's disabled set | skipped (mirrors the list read-filter; minting itself is never suppressed — bypassed for a locked type) |
| the recipient disabled the type's `EMAIL` channel (v4.0.0 per-type preferences) | skipped (bypassed for a locked type) |
| catalog returns null (`PASSWORD_CHANGED` with `self="reset"` — the reset email IS the notice) | skipped |

The V51 opt-out is **on by default** and self-service: `PUT /api/v1/users/{id}/email-notifications` `{enabled}` (target user or ADMIN — `requireSelfOrAdmin`, the self-service sibling of the ADMIN-only features PUT; idempotent; deactivated target allowed; audited `user.email_notifications_changed` on an actual change), surfaced as `UserResponse.emailNotificationsEnabled`. **The settings UI is the Notification preferences page** (`pages/NotificationPreferences.tsx`, `/users/:id/notification-preferences` — the header account-menu item; the old `/users/:id/email-notifications` URL redirects there since v4.0.0), which renders the master switch alongside the per-type IN_APP/EMAIL matrix (see "Preferences" below) — there is no longer a standalone email-only screen. The flag is read **at send time**, so a change takes effect immediately — deliberately unlike the JWT-riding feature flags. Tests: `NotificationEmailTest` (catalog), `NotificationEmailDeliveryTest` (skip matrix, deterministic via a joined coroutineScope + one route-level pass), `UserEmailNotificationsTest` (endpoint), `NotificationPreferencesTest` (the per-type matrix, the locked-type bypass of every gate including V51, and the batched per-batch `EMAIL` read). The compose demo delivers these to Mailpit (`http://localhost:8025`).

Reading/managing notifications goes through `notifications/NotificationRoutes.kt`, all under `authenticate` and scoped to the recipient via `requireNotificationRecipient` (recipient-only, no bypasses): `GET /api/v1/notifications` (list; sortable `id`,`timestamp`, default `-timestamp`; optional `wasSeen` filter), `GET /api/v1/notifications/{id}`, `POST /api/v1/notifications/{id}/seen`, `POST /api/v1/notifications/{id}/unseen`, `POST /api/v1/notifications/seen-all` (marks all the caller's unseen as seen; caller-scoped via `markAllSeen(recipientId)`), `DELETE /api/v1/notifications/{id}`. The endpoints are documented in `documentation.yaml`; the `notifications` table is created by `V13__create_notifications.sql`.

**Retention — the on-mint purge (v3.12.0).** Notifications are ephemeral UX, not a record — the audit log and the `*_events` tables are the trail. After minting, `NotificationService.create`/`createAll` run `purgeStale()` to hard-delete rows that are seen or user-deleted and older than `notifications.retentionDays` (env `NOTIFICATION_RETENTION_DAYS`, default 30; 0 disables it); the purge is org-wide (every recipient's rows, not just the mint's) and guarded by a per-instance `AtomicLong` compare-and-set gate (the feedback expiry sweep's gate; the `LoginThrottle.reserveAttempt` write-path-prune idiom — garbage only appears when rows are minted, so pruning on mint bounds the table without a scheduler or a write on any GET) that runs at most once per `notifications.purgeIntervalSeconds` (env `NOTIFICATION_PURGE_INTERVAL_SECONDS`, default 3600; 0 = every mint, the test suite pins it). Unseen rows are never purged. Hard delete is a registered exception to the soft-delete convention — notifications have no FK dependents, the email mirror already fired at mint, and a notification is not a record (the audit log and the `*_events` tables are). There is no `seen_at` column, so age is measured on `created_at`. A prune failure only WARN-logs and never fails the mint; the deleted count is INFO-logged when > 0. Replica-safe because DELETE is idempotent. The partial index `idx_notifications_purge` (V82) matches the predicate (`where was_seen OR marked_as_deleted`) to speed the scan. Tests: `NotificationPurgeTest` (seen/unseen/boundary/user-deleted/`createAll`/retention-0/gate cases, asserting on raw row counts).

**Per-user feature flags (V46, v1.53.0).** The list (rows AND `total`) excludes notifications whose type belongs to one of the recipient's disabled features — the SPA's unread badge is the `total` of a pageSize-1 unseen query, so this one predicate keeps both honest. The type→feature mapping is the exhaustive `NotificationType.feature` extension in `notifications/Notification.kt` (`PASSWORD_CHANGED` and `CAREER_POSITION_STARTED_TO_USER` → `null` = never filtered — both ride ungated areas; the `when` forces every future type to pick a side — a `FeatureFlagsTest` case pins the values). The flags come from the caller's JWT claim (same ≤15-min staleness as route gating). **Deliberately unfiltered**: `GET /{id}`, seen/unseen, `seen-all` (may mark hidden rows seen — accepted), `DELETE`, and minting everywhere — a re-enabled feature reveals its backlog, still unseen unless a `seen-all` touched it.


**Preferences (V84, v4.0.0).** Per-user, per-channel on/off switches, independent of the V51 master email opt-out and the V46 feature flags: every `NotificationType` has its own `IN_APP`/`EMAIL` switch, all **on by default** (`notifications/NotificationPreferences.kt`, `NotificationPreferenceService`). Storage is `user_notification_preferences(user_id, notification_type, channel)` — the **DISABLED** pairs, the `user_disabled_features` shape: no row means every type is enabled on both channels, so the feature ships with no seed and no backfill. `NotificationType.lockedOn` is `true` only for `PASSWORD_CHANGED` — a security receipt that cannot be silenced on either channel; `NotificationPreferenceService.replace` rejects a PUT that tries with `400`, and both suppression points below skip their check outright for a locked type.

- **IN_APP suppression happens at mint, not at read.** `NotificationService.create`/`createAll` read the recipient's disabled `IN_APP` set **inside the same insert transaction** (`disabledForInTransaction` queries `NotificationPreferenceService.UserNotificationPreferences` directly — the `GoalService`/`ImpactLogService` cross-feature table-read shape in `.claude/docs/persistence.md`, never through `NotificationPreferenceService`'s own methods, which would open a second transaction) and simply skip the `INSERT` for a disabled type — no row, no bell entry, nothing for `seen`/`delete`/the list to act on. `createAll` reads the whole batch's disabled sets in one query and inserts only the kept rows; an all-suppressed batch is a no-op insert, never an error. **The email mirror is dispatched unconditionally** regardless of IN_APP suppression — the two channels are independent switches, so a type disabled in-app can still arrive by email.
- **EMAIL suppression happens at send.** `NotificationEmailer.sendOne` adds one more skip rule alongside the existing ones (deactivated, V51 opt-out, feature-disabled): if the type's `EMAIL` channel is in the recipient's disabled set, skip. Since v4.0.0 `dispatch` reads the whole batch's disabled `EMAIL` set **once** (`disabledFor(allRecipientIds, EMAIL)`, one `IN` query inside the launched coroutine) rather than once per send, and passes it into `sendOne`. `PASSWORD_CHANGED` with `self="reset"` stays catalog-null, unchanged; every other `lockedOn` type bypasses the V51 opt-out, the feature check, AND this per-type `EMAIL` check outright — see the "Email mirror" skip table above for the full order.
- **Routes**: `GET`/`PUT /api/v1/users/{id}/notification-preferences` (`users/UserRoutes.kt`, beside `email-notifications`) — `requireSelfOrAdmin`, ungated by feature like every other users route, deactivated target allowed. `GET` returns `{emailEnabled, items: [{type, feature, inApp, email, locked}]}` — `emailEnabled` is the V51 master switch riding along so a single page renders both; `items` covers every `NotificationType` including ones whose feature is currently disabled for the target (the client hides those groups, the data stays real). `PUT` wholesale-replaces the disabled set (`{disabled: [{type, channel}]}`); a locked type, an unknown type/channel name, or a **duplicate `(type, channel)` pair** (v4.0.3 — the route rejects it with `400` rather than silently folding it via `toSet()`, the succession duplicate-goal-id precedent) is `400`; idempotent; audited `user.notification_preferences_changed` only on an actual change.
- **Concurrent saves serialize per user (v4.0.3).** `NotificationPreferenceService.replace` locks the user row (`SELECT … FOR NO KEY UPDATE`, not `pg_advisory_xact_lock` — MFA already keys its lock on the bare user id) and reads the previous disabled set inside that same lock, before the delete/insert. Two concurrent PUTs for one user therefore serialize rather than interleave — under plain READ COMMITTED without the lock, the second's `DELETE` could not see the first's still-uncommitted `INSERT`s, so disjoint concurrent sets used to persist as their union and overlapping ones could race a 23505 into a spurious `409`. With the lock, the second waits for the first to commit and then cleanly **last-writer-wins**; the route's audit `from` is read under that same lock, so it always reflects the actually-committed pre-write state rather than a stale pre-read that could race a concurrent PUT. `UserService.setDisabledFeatures` (the per-user feature flags, ADMIN-only) has the identical existence-check-then-replace shape and the same theoretical race, but is deliberately left unlocked — nobody has reported contention there and it wasn't in scope for this fix.
- **The open-set rule (v3.25.3) applies to preference rows too**: `notification_type` stores the enum's NAME with no CHECK, so a row minted under a type a later release removes or renames must be handled the same way the notification rows themselves are — `disabledForInTransaction`/`NotificationPreferenceService.read` filter to known names in SQL, silently dropping an orphaned row rather than throwing. A release that removes or renames a `NotificationType` owes these preference rows the **same same-commit migration** as the minted notification rows (translate onto a successor when one exists, delete when none does) — see "Removing or renaming a notification type" below; treat `user_notification_preferences` as a second table that obligation covers, not just `notifications`.

**Removing or renaming a notification type — the upgrade rule (v3.25.3).** `notifications.notification_type` stores the enum's **NAME** (`varchar(60)`, deliberately no CHECK — the V27 idiom), and those rows outlive the release that minted them. The enum is therefore a closed set in code and an **open set in the database**, so a reader must treat an unrecognized name as data it cannot render, never as an error: `NotificationService.knownType()` filters unknown names out in SQL — in the list predicate AND in `read` — so an orphaned row is invisible exactly like a soft-deleted one (list, `total`, `GET /{id}`, seen/unseen, delete all agree), and `total` stays consistent with the rows because the filter is in the query rather than after it. Pinned by the `NotificationRoutesTest` case "a notification whose stored type this build does not know is invisible, never fatal". **This is the load-bearing rule** — it is what makes a forgotten migration a cosmetic problem instead of an outage.

On top of it, a release that removes or renames a type owes the stored rows a migration **in the same commit** (`V37` and `V83` are the precedents):

- **A successor exists** → rewrite the name and reshape `params` to the successor's shape, mirroring whatever that same migration does to the underlying records. `V83` maps the seven v3.9.0 days-off lifecycle types onto `DAYS_OFF_CREATED`/`DAYS_OFF_DELETED` by exactly the split `V77` applied to the entries themselves (kept → CREATED, soft-deleted → DELETED). For `ACCEPTED`/`REJECTED` that is a **re-labelling, not a translation** — approval no longer exists as a concept, so the honest thing to show is the state the entry is actually in.
- **No successor** (the feature is gone outright, nothing truthful to show) → soft-delete the rows and let the v3.12.0 purge reclaim them.

The same obligation applies to a type that **keeps its name but changes its params shape** — the rename case is not the only way to orphan a row. Why this is written down: v3.9.0 removed seven types, and `V77` correctly retired the affected `days_off_requests` rows while missing this table entirely; every instance upgraded past it 500-ed on its whole notification list — the badge included, since the unread count is the same call at `pageSize=1` — until v3.25.3. The SPA was already forward-compatible on both paths (`describeNotification` falls back to the raw type, `TYPE_META` to a plain bell); only the server was strict.
