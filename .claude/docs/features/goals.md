### Goals

A **goal** is set by a **manager** for a **direct report** and tracked over time: a plaintext `title` (≤200 — lists sort/substring-filter on it), an encrypted `description` (≤4000), a `type` with **type-specific progress models** (`PLAN` → an ordered list of **milestones**, see below (v2.9.0 — the rebuild of the old BINARY flag type; `V56` renamed the enum value, converted every ex-BINARY goal to a single 'Done' milestone carrying the old achieved flag, dropped `goals.achieved`, and rewrote `BINARY` in historical event params, the V37 idiom); `NUMBER`/`PERCENTAGE` → `target_value` + `current_value`, PERCENTAGE bounded 0–100; the non-applicable columns stay NULL, enforced by `validateGoalDefinition`/`validateGoalProgress` in `goals/Goal.kt`; **a fresh goal has NO recorded value** — the value field starts NULL (and a fresh PLAN's milestones all start not-done) until the first progress update (v2.8.1; `V55` reset the pre-v2.8.1 auto-zeros of goals with no progress event), and a DRAFT type change resets them back to NULL (away from PLAN it deletes the milestone rows)), a **required `dueDate`** (ISO `YYYY-MM-DD` in `VARCHAR(10)` — the 1:1 date convention, lexicographic == chronological; strict zero-padded parse + never earlier than the current server-local date, `validateGoalDueDate` in `goals/Goal.kt` with a defaulted `today` param for tests; **editable only at creation and while DRAFT** — the definition PUT is already DRAFT-only), and an encrypted `summary` recorded at archiving. Table `goals` (`V25`, standard soft-delete), audit table `goal_events` (`V26`), milestone table `goal_milestones` (`V56`, hard-delete children — the 1:1 detail-table class). Implementation in `server/src/main/kotlin/goals/` (`GoalService`, `GoalEventService`, pure `GoalEvents.kt`/`GoalNotifications.kt` builders, `GoalRoutes.kt`) — the state machine/events/notifications shape is cloned from feedbacks, the manager/subordinate authz from 1:1s, the milestone list from the 1:1 action items.

- **Milestones (PLAN, v2.9.0)**: `goal_milestones(id, goal_id FK CASCADE, position, description /*encrypted*/, done)` — each an encrypted textual `description` (non-blank ≤4000, `MAX_GOAL_MILESTONES = 100` per goal) plus a plain `done` flag; read `position ASC, id ASC`. **Defining happens in DRAFT** (part of `GoalCreateRequest`/`GoalDefinitionUpdate.milestones` — the 1:1 whole-list replace: payload order IS the order, id-matched rows keep/edit (their `done` flags PRESERVED — defining is not ticking), missing rows hard-delete, id-less rows insert not-done; duplicate/foreign ids → 400, create-time ids → 400 (`newMilestonesOnly`); `GoalService.replaceMilestones`). **Ticking happens in ACTIVE** via the progress PUT (below). There is **no whole-goal done flag** — a PLAN goal's numeric value columns stay NULL, and list rows carry the content-free tally `milestonesDone`/`milestonesTotal` instead (one flag query per page, tallied in Kotlin — `withMilestoneTallies`; NULL on the numeric types, 0/0 for a milestone-less draft). `GoalResponse.milestones` carries the full decrypted list (empty for numeric types). **Activation gate**: `POST …/activate` 400s a PLAN goal with zero milestones (route-side next to the stale-due-date recheck; reopen stays ungated — an archived PLAN always passed the gate). SPA: `GoalMilestonesEditor` (the ActionItemsEditor clone, embedded in `GoalDefinitionFields` when the type is PLAN), checkbox list on the Update screen, and **done milestones render struck-through + dimmed everywhere** (the Update checkboxes, the view's `MilestoneList` in `utils/goalValues.tsx` — the deliberate completed-state emphasis; net-new styling, no repo precedent). R2DBC gotcha pinned by the first implementation: never run the milestones select inside the goal row's still-open flow `.map` — drain (`.toList()`) first, or the shared connection deadlocks.

- **Status machine**: `DRAFT ↔ ACTIVE ↔ ARCHIVED` (CLOSED renamed in v1.41.0 — V37 migrated rows, event params, and notification types), both directions, never skipping ACTIVE — exactly four edges, one action endpoint each: `POST …/{id}/activate` (DRAFT→ACTIVE — additionally **400s while the goal's `dueDate` is in the past**, checked route-side in `transitionTo` like the archive summary; a stale draft must be given a fresh date first. **Reopen is deliberately NOT gated** — the due date is DRAFT-only editable, so gating ARCHIVED→ACTIVE would deadlock an overdue archived goal; pinned by a `GoalRoutesTest` regression), `…/deactivate` (ACTIVE→DRAFT), `…/archive` (ACTIVE→ARCHIVED — the only bodied action: `{summary}`, required non-blank ≤4000), `…/reopen` (ARCHIVED→ACTIVE). **Each endpoint names its whole edge**: `GoalService.transition(id, from, target, summary?)` 409s when the goal is not at `from` — necessary because activate and reopen share the ACTIVE target and would otherwise be interchangeable. Reopen keeps the stored summary (a record of the previous archiving, overwritten at the next archiving); deactivate keeps recorded progress. Creation (`POST /api/v1/goals`) always lands in DRAFT.
- **Per-status edit rules**: DRAFT → `PUT /{id}` (**manager only** — `requireGoalWrite`; `GoalDefinitionUpdate`: title/description/type/target/milestones; a type change re-initializes the value fields for the new type, discarding progress — away from PLAN the milestone rows are deleted — and the events explain the reset); ACTIVE → `PUT /{id}/progress` (**the pair's shared write since v2.8.0** — manager OR subordinate, `requireGoalProgressWrite`; nobody else, ADMIN/HR included; `GoalProgressUpdate`: only the type-matching field may be set — `milestones` for PLAN (the COMPLETE done-state: one `{id, done}` per milestone, ids matching the stored set exactly, else 400 — `applyMilestoneTicks`; only actually-flipped flags count) or `currentValue` — and it is **optional since v2.8.1** — absent leaves the state untouched, but a state-less update must carry a non-blank `comment` (else 400: nothing to record); a set numeric value can never be unset (un-ticking a milestone IS allowed — it's a recorded change). The optional `comment` ≤4000 — blank counts as absent — is recorded ENCRYPTED on the history event and never on the goal itself; a comment-only update with an unchanged state still records and notifies; a true no-op — same state, no comment — stays a silent 204); ARCHIVED → nothing (the summary is settable only by the archive action). The status machine, definition, and deletion stay **manager-only** (the subordinate never transitions). Wrong-status PUTs are `409`, checked **inside** the service transaction; `DELETE` is manager-only + **DRAFT-only** (non-draft → `400`, like feedback deletion), soft, no notification.
- **Reads**: manager, subordinate, and the HR auditor at every status; managers further up the subordinate's transitive chain only once the goal has left DRAFT — see `.claude/docs/authorization.md`.
- **List** (`GET /api/v1/goals?view=own|managed|team`; the HR auditor `view=user` is documented in `.claude/docs/authorization.md`): `own` (default) = caller is the subordinate; `managed` = caller is the manager — with `includeIndirect=true` widened to **also** include goals set by managers in the caller's transitive chain, excluding those managers' DRAFTs (the caller's own DRAFTs always list; backs the SPA's "Goals I've set" Reports scope, v1.22.0); `team` = goals set by the caller's direct reports as managers (`includeIndirect=true` widens to the transitive chain) AND `status ≠ DRAFT` (the chain may not see drafts — a list scope mirroring the read guard, so every listed row is openable). `includeIndirect` is valid on `managed`/`team` only (`own` → `400`). Sortable `id`/`managerName`/`subordinateName`/`title`/`type`/`status`/`targetValue`/`currentValue`/`createdAt`/`dueDate`/`lastModified` (the nullable value columns group PLAN rows at one end — DB NULL ordering, documented in the spec), default `-createdAt`; `managerName`/`subordinateName`/`title` substring + `managerId`/`subordinateId`/`type`/`status` equality + `createdAt[gte]`/`lastModified[gte]` filters (the per-manager drill-down is `view=own&managerId=X`, the feedbacks `providerId` precedent). Rows carry party names, title, the value fields, and — PLAN rows only — the `milestonesDone`/`milestonesTotal` tally — never description/summary/milestone texts (no decryption in lists).
- **SPA**: "Goals" buttons on both Dashboard grids — each "My managers" card (v1.16.0, `from=managers`) and each direct-report "My subordinates" card (v1.17.0, `from=subordinates`, same direct-scope gate as the 1:1 buttons) — lead to `/users/:userId/goals` (`pages/UserGoals.tsx` embedding the reusable `pages/GoalTable.tsx`; the origin decides the direction: managers → `view=own&managerId` (`settingsKey="userGoals"`), subordinates → `view=managed&subordinateId` (`"userGoals.managed"`), HR auditors (`?mode=audit` from the User-details Audit section) → `view=user&userId` (`"userGoals.audit"`) plus a footer **"New goal"** button (the New-1:1 pattern, `utils/goalLinks.ts` `goalCreateLink`); filters: title substring, created-window all/month/sixMonths via `createdWindowOptions` in `utils/datetime.ts`, status). `/goals/new` (`CreateGoal.tsx`) is the manager's create screen — direct-report picker (skipped when prefilled via `goalCreateLink`), the definition fields, one Create button; the goal lands as DRAFT, a prompt then asks whether to activate it immediately (Yes → the activate transition), and either answer returns to the originating screen (`back` param, default the subordinates grid). Detail screens: `/goals/:id/view` (`ViewGoal.tsx` — read-only document, History tab via `components/GoalHistory.tsx` (which renders each progress comment pre-wrap under its entry), the **manager's lifecycle actions**: DRAFT→Activate, ACTIVE→Return-to-draft (behind a `ConfirmActionModal` since v2.8.0)/Archive (summary `Textarea` modal `components/GoalCloseModal.tsx` — the summary is plain text, rendered pre-wrap, not markdown), ARCHIVED→Reopen, plus the manager's DRAFT Edit link and — ACTIVE, **both parties** — an Update link) and `/goals/:id/edit` (`EditGoal.tsx` — one route branching by status: DRAFT definition form with `MarkdownEditor` description + type-change reset warning + DRAFT-only Delete, manager-only; ACTIVE = the **Update screen** (v2.8.0), open to BOTH parties: `GoalProgressFields` (the numeric value or the PLAN milestone checkboxes — done ones struck through — + the optional comment `EmojiTextarea`) with a Close/Save-only footer — Close confirms only when dirty (the EditPerformanceReview `form.isDirty()` pattern), Save with nothing changed shows a gray "nothing to save" Alert instead of firing, and the old in-form Return-to-draft/Save-&-archive buttons are gone (lifecycle lives on the list rows and the view); non-party or ARCHIVED redirects to the view). **List-row actions** (`GoalTable.tsx`, id-derived, every view): manager+DRAFT → Edit; ACTIVE+party → Update; manager+ACTIVE additionally the **"Lifecycle ▾" `Menu`** (aria `goal.lifecycleFor`; Return to draft → `ConfirmActionModal`, Archive → `GoalCloseModal` — the DaysOffTable pending-target idiom); everyone else → View. The nav's **"Goals"** page (`/goals`, `MyGoals.tsx`; single-view "My goals" since v1.18.0, two tabs since v1.22.0) has tab "My goals" (the unpinned own view, exactly the pre-v1.22 page, settings under `goals.own`) and — for managers only (the 1:1-page gate: `listTeams({managerId})` total > 0) — tab **"Goals I've set"**: the unpinned managed view across all subordinates (`goals.managed` settings, rows return via `back=/goals?tab=managed`) with GoalTable's `withReportsScope` prop rendering the shared `ReportsScopeSelect` — direct = the caller's own goals, all = `includeIndirect=true` (see List above). GoalTable's per-view differences are declarative (`VIEW_CONFIG`, the OneOnOneTable idiom): each view names its sortable/filterable person column(s) — own/team the Manager, managed the Team member, the HR-audit `user` view both — hidden whenever a drill-down pins that party; the person cells use the shared `components/PersonCell.tsx` ("You"/deleted stay plain text). Detail screens default `backTo` to `/goals` (notification landings), `back` param overrides; the editors' field blocks are the shared `GoalDefinitionFields`/`GoalProgressFields` (create + DRAFT edit reuse the same definition block), and every goal mutation invalidates through `utils/goalQueries.ts` `invalidateGoal` (which also refreshes the dashboard card stats — the 1:1 pages mirror this via `oneOnOneQueries.ts`). i18n area `goal` (`locales/{en,pl}/goals.json`; the card-button keys live in `teams.json` for the subordinates grid and `users.json` for the managers grid); goal status colors in `components/GoalStatusBadge.tsx`; per-type value rendering **and the overdue signal** (`isGoalOverdue` — ACTIVE && dueDate < today — plus the orange `OverdueBadge`, shown next to the date in the table's Due-date column and the view/progress-edit headers) in `utils/goalValues.tsx`; the due-date input is a `TextInput type="date"` with `min={todayIsoDate()}` in `GoalDefinitionFields`, mirrored by the `dueDate` rules in `utils/goalForm.ts` (required + not-before-today ISO string compare).
- **Events**: `goalCreationEvent`/`goalDefinitionUpdateEvents` (one per changed aspect, milestone diff appended in the 1:1 removed→edited→added order; a pure reorder and a no-op PUT mint nothing)/`goalProgressUpdateEvents` (pluralized in v2.9.0 — one save may toggle several milestones)/`goalTransitionEvent`/`goalDeletionEvent` (pure, `goals/GoalEvents.kt`) → 16 `GoalEventType`s (`CREATED{type}`, `TITLE_CHANGED`, `DESCRIPTION_CHANGED`, `TYPE_CHANGED{from,to}`, `TARGET_CHANGED{from,to}`, `DUE_DATE_CHANGED{from,to}`, `PROGRESS_UPDATED{from,to}`, `ACHIEVED_CHANGED{to}` — **historical only** since v2.9.0: nothing mints the old BINARY flip anymore but stored rows still render, `MILESTONE_ADDED`/`MILESTONE_EDITED`/`MILESTONE_REMOVED`/`MILESTONE_COMPLETED`/`MILESTONE_REOPENED` (v2.9.0, all `{position}` — 1-based, the 1:1 items convention), `PROGRESS_COMMENTED` (v2.8.0 — a comment-only progress update, params `{}`), `STATUS_CHANGED{from,to}`, `DELETED`). Params are enum names, numeric strings (`""` = no value), positions, and ISO dates — **never title/description/summary/milestone/comment text**. The progress update's optional comment rides the `goal_events.comment` column (`V54`, nullable, **encrypted at rest** — `GoalEventService` implements `EncryptedAtRest` and owns the cipher; the shared `EventLogTable` exposes an opt-in `commentColumn` hook, goal_events is its only user), surfaced as `GoalEventResponse.comment` (decrypted; null on non-progress kinds) and rendered pre-wrap under the timeline entry by `GoalHistory`; on a multi-event progress save the route attaches it to the LAST-minted descriptor, so it tops the newest-first timeline. Read via `GET /api/v1/goals/{id}/events`, authorized like the single GET; persisted by the route, never the service.
- **Notifications**: every status transition notifies the **subordinate** (the manager is always the actor), and every recorded progress update (value change, milestone tick/untick, or comment-only; v2.8.0) notifies the **counterparty** of the actor — `GOAL_PROGRESS_UPDATED_TO_MANAGER` / `_TO_SUBORDINATE`, params `{subordinate|manager, title}`, built by `goalProgressUpdateNotification` and resolved in `GoalService.updateProgress` (the `transition` pattern) — see the table under "Notifications" in `.claude/docs/features/notifications.md`. Creation, edits, deletion, and true no-op progress PUTs notify nobody.
- **Dashboard-card stat**: `GET /api/v1/teams/members` enriches `managers`/`managed` rows with the directional `activeGoalCount` (`GoalService.activeGoalCountsByManager`/`…BySubordinate` — see "List endpoint conventions" in `.claude/docs/list-endpoints.md`); rendered as a Collaboration-section row by `PersonCardBody` (`components/PersonCardStats.tsx`).
