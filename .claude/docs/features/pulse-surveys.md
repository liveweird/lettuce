# Pulse surveys (v2.0.0)

Recurring anonymous eNPS surveys: admin-managed cycles, per-user encrypted responses, team-aggregated results with k-anonymity, manager participation monitoring, anonymized comments. Server package `pulse/` (+ `settings/AppSettingsService.kt`, `teams/TeamTree.kt`); SPA `/pulse` hub + `/pulse-cycles` admin screen; feature flag `PULSE_SURVEYS`; dictionary `pulse-rotating-questions`.

## Cycle machine (`pulse_cycles`, V48)

`SCHEDULED → OPEN → CLOSED`, terminal `CANCELLED` reachable from ANY of the three (cancelling a CLOSED cycle retracts its results; responses are always kept for audit). **Every transition is a manual ADMIN action** — `planned_open_date`/`planned_close_date` are advisory prefills; the app has zero background jobs and none may act on them. **At most one non-terminal (SCHEDULED/OPEN) cycle exists at a time**: service pre-check → 409, race-proof backstop via V48's partial unique index over a constant (`uq_pulse_cycles_non_terminal`). PUT date edits: SCHEDULED = both dates; OPEN = close date only ("extend" — a changed open date is 400); CLOSED/CANCELLED = 409. Soft-delete column per convention but **no DELETE endpoint** (cancel is the removal — the `days_off_requests` precedent).

## Eligibility snapshot (`pulse_participants`, V49)

Taken at OPEN: active (not soft-deleted) ∧ not deactivated ∧ PULSE_SURVEYS enabled → participant rows. Later churn never changes a cycle's history; a user enabled after open is NOT a participant (403 on my-response). Response rates and participation monitoring read the snapshot. The schedule-time notification audience is computed the same way but deliberately un-stored (may drift from the later snapshot — documented).

## Survey content & responses (`pulse_responses`, V49)

Q1 eNPS 0–10; Q2–Q5 fixed statements (client-side i18n, NOT stored); Q6 rotating question; Q7 optional comment ≤1000 chars. Answers stored as strings (`"0".."10"` / `"1".."5"` / `"NA"`), **all six scored columns + the comment encrypted** (FieldCipher envelopes — the V45 review-ratings precedent; `encryptLegacyRows()` hook in Bootstrap; never filter/sort these columns in SQL). One row per (cycle, user) — UNIQUE + FK into participants; **upsert while OPEN** (`submitted_at` set once, immutable). `GET/PUT …/my-response` is the ONLY endpoint ever serving individual answers — own answers only, and **only while OPEN** (after close: 409 — the anti-copy-paste rule). Production reads go through `PulseResponseService.scopeDataByCycle` (v4.14.0 — one transaction, two set-based statements over a set of cycles; the single-cycle `answersForScope`/`participantCountForScope` remain as the parity test's oracle), which returns the user-id-free `PulseAnswers` type grouped by cycle, so no aggregate can leak an author by construction; comments come back author-free and **shuffled per request**.

## Rotating question (Q6)

Fourth dictionary `PULSE_ROTATING_QUESTION("pulse-rotating-questions")`, seeded by V50 with the six bank statements; admin-editable via the generic dictionary machinery (**deliberately ungated** server-side like all dictionaries — the nav leaf is feature-tagged as pure UI). Pick at SCHEDULE time (`PulseCycleService.pickRotatingQuestion`, injectable `Random`): candidates = ACTIVE entries with the LOWEST usage count over non-cancelled cycles, uniform random among ties — pool-without-replacement with an implicit reset when counts equalize; a cancelled cycle returns its question; a newly added entry (usage 0) is automatically next; an empty bank refuses to schedule (409). The entry's **whole language map is snapshotted** onto the cycle (`rotating_question_text_en` + the `rotating_question_translations` JSON map, V60) — renames never rewrite what a cycle asked. Rotating-question deltas compare only when the previous cycle used the SAME entry id.

## Team scopes (`teams/TeamTree.kt`)

The team hierarchy is derived, not stored: **team T2 is below T1 iff T2's manager ∈ members(T1)** (set-at-a-time BFS, cycle-safe, non-deleted teams, ManagementChain style; wrapped for routes by `TeamService.visibleTeamTreeIds` / `managedTeamTreeIds` / `teamScopeMembers` / `membershipTeamIds`).

- `visibleResultTeamIds(user)` = member-of + managed + everything below either — the RESULTS scope.
- `monitoredTeamIds(user)` = managed + below — the MONITORING scope (participation + comments).
- `memberTeamIds(user)` = teams the user is currently a MEMBER of — the `memberTeams` scope (v2.12.0; the `TeamService` wrapper is named `membershipTeamIds` — a same-name wrapper would shadow the free function inside its own lambda).
- `teamScopeUserIds(team, mode)`: `direct` = current members; `subtree` = members + every transitive subordinate of a member. A manager is never a plain member of their own team — their response aggregates under the team they are a MEMBER of.
- `GET /pulse-surveys/visible-teams` serves the three caller-scoped lists (`resultsTeams`/`monitoredTeams`/`memberTeams`, v2.12.0) to the SPA's pickers for managers and members; **for an HR caller (v3.24.0) the three buckets are now honest** (previously HR got every team in all three, which made the caller-relative scopes indistinguishable and mislabeled in the UI) — HR additionally gets a new **`allTeams`** bucket, omitted for everyone else, backing an explicit "All teams" scope in the Results/Trend tabs.

## Access matrix (who sees what)

| View | Rule |
|---|---|
| Fill/edit own survey | participant + cycle OPEN (upsert) |
| Team aggregates (`…/results`) | cycle CLOSED (409 otherwise — **uniform, HR included**; CANCELLED never serves results) + **the per-cycle fill gate**: caller responded in THIS cycle (no role exemption — ADMIN included) + team ∈ visible tree. **HR is exempt** from the fill gate (auditor precedent, `hr.read` audited, resource `pulseResults`) |
| eNPS trend (`…/trend`) | team access as results; the fill gate applies **point-wise** for non-HR (`NOT_A_RESPONDENT` = no numbers at all) |
| Anonymized comments (`…/comments`) | cycle CLOSED + team ∈ MONITORED tree (managers+ only — members never; **no own-fill requirement**); HR org-wide, audited `pulseComments` |
| **Through a share (v4.12.0, `PULSE_TEAM_RESULTS` — see `.claude/docs/features/sharing.md`)** | `…/results`, `…/comments` and `…/trend` are share-aware via `ShareAccess.readOrShared`: a caller denied in their own right who holds an ACTIVE share of the team's results gets the same guard re-run for the SHARER with the HR role stripped — **the lambdas close over the sharer principal**, so the SHARER's fill gate (per cycle), visible tree and (comments) monitored tree decide, never the sharee's: a cycle the sharer sat out → `403` with the share-lapse detail ("The person who shared this no longer has access to it"); comments through a member-sharer → the same `403` (none to pass on); **comments never reach an INSIDER through a share (user decision after the security audit)**: a caller who is a CURRENT member of the requested scope (`teamScopeMembers(team, mode)`, so direct vs subtree matters) and RESPONDED in that cycle (one scope + responded read, shared with the response count) gets a distinct `403` ("Comments aren't shared with people who answered this survey for the team") while the aggregates stay readable, and `canReadComments` is false for them — outsiders and non-responding members still get the comments when the sharer could, own-right monitors/HR are unchanged; the trend is point-wise over the UNION of the responded sets of the caller (when their own right holds) and every active sharer who still passes (each point is exactly what one principal sees; the trend DTO names no sharer). The order is unchanged (404 → 409-state → 403-identity, the share lookup last, so an OPEN/CANCELLED cycle is 409 for a sharee too); a caller with no active share gets the ORIGINAL denial (and `authz.denied`); the sharee's own `PULSE_SURVEYS` flag is the first gate; a share read NEVER emits `hr.read` (the stripped evaluation has no HR branch). k≥3 withholding is evaluated on the data, so it holds for sharees. Not share-aware (own right only): `…/participation-status`, `…/my-response`, `…/visible-teams` |
| Per-person participation (`…/participation-status`) | cycle OPEN or CLOSED (live monitoring is the point); monitored tree; bare submitted yes/no, never content; HR org-wide, audited `pulseParticipation`; non-managers get an empty list |
| ADMIN | cycle CRUD + settings + per-cycle **counts only** (`…/participation`: participants/responses/rate) — no aggregates, no comments, no per-user status (the v1.26.0 narrowed-ADMIN rule) |

History note: the v2.10.0 per-cycle **team-comparison** view + `…/cycles/{id}/team-comparison` endpoint (+ its `requirePulseComparisonAccess` guard and `pulseComparison` audit resource) were **removed in v2.12.0** — superseded by the two-view Results layout (member/managed + the direct/indirect calculation toggle). The v2.11.0 **multi-scope trend bundle** `…/trend-comparison` (+ `requirePulseTrendComparisonAccess`, the `pulseTrendComparison` audit resource, and the `TeamTree.childTeamsOf`/`TeamService.childTeamIds` helpers) was **removed in v2.14.0** — the Trend tab's team-pills model draws every line from the single-team `…/trend` instead.

**k-anonymity (k=3)**: a scope under 3 responses withholds aggregates AND comments — `insufficientResponses: true` with null/empty payload (a 200 marker, not an error) — applied to the current scope, the previous-cycle scope (no deltas against a withheld baseline), and each trend point. Existence/ordering idiom: cycle reads are read-before-guard (404 visible); results order deliberately **404 → 409-state → 403-identity** so a non-closed cycle answers uniformly for every caller.

## Aggregation (`PulseAggregation.kt`, pure)

Bands: promoters 9–10, passives 7–8, detractors 0–6. `eNPS = round((promoters − detractors) / n × 100)` — one expression since v2.6.2 (mathematically = round(promoterPct − detractorPct), but drift-free; ties round half-toward-+∞, so 12.5 → 13 and −12.5 → −12) (−100..+100); display percentages 1dp. Per driver: NA excluded everywhere; mean 1dp, favorable = 4–5, unfavorable = 1–2, `validCount` always shipped. `responseRate` = responses/participants in scope, 1dp. Change-vs-previous = the immediately preceding non-cancelled CLOSED cycle (max `closed_at`), same scope: eNPS delta (whole points), per-driver mean Δ + favorable Δpp (1dp, computed over the ROUNDED values). **No result is ever framed as statistically significant** (copy rule too — no i18n string may say "significant").

## Settings (`app_settings`, V47)

The app's FIRST runtime-editable config: generic K/V store (`settings/AppSettingsService.kt`, pulse-agnostic), pulse keys `pulse.cadenceWeeks` (default 4) / `pulse.openDays` (default 7), validated 1–52 / 1–90. **Advisory only** — they prefill the admin scheduling form (`open = latest non-cancelled cycle's open + cadence weeks`, `close = open + openDays`); the server never acts on them. `GET/PUT /pulse-surveys/settings` are ADMIN both ways (the alerts reads-included posture); PUT audited with deltas.

## API shape notes

- **`PulseTeamResults` route-stamped flags (v4.12.0)** — `canShare` ("would `POST /shares` accept this team" — the team is in the caller's visible tree in their OWN right, never via the HR role alone, also when this read came through a share: the Share button's gate), `sharedBy` (the sharer's name when the read came through a share, else null) and `canReadComments` ("would `GET …/comments` succeed", computed by running the comments guard — own right, then every active share on its sharer, then the insider rule — false for a CURRENT member of the requested scope (per `mode`) who answered that cycle; HR short-circuits so the probe never audits; lets the card skip a request that could only 403). `false`/null on every internal read; stamped by the results route via `.copy`.

All under `/api/v1/pulse-surveys/*` (tag `pulse-surveys`, 17 operations); every handler resolves `pulseCaller()` FIRST (uniform 403 for a disabled caller). The cycle list is an **unpaged registry** (`{items}`, newest first — a cadence of weeks caps volume; deliberate deviation from the paged-list convention, like review-periods). The `rotatingQuestion` language map on cycle reads (and the results-side `rotatingText` map on the ROTATING driver row) is null for non-admins until OPEN/CLOSED — whole-map-or-null (unopened questions stay unspoiled; CANCELLED reveals nothing to non-admins); the list's `participantCount`/`responseCount` are ADMIN-only enrichment. `DashboardSummary` gained `pulseOpenCloseDate`/`pulseSubmitted` (null unless the caller is a participant of an OPEN cycle) backing the SPA tile.

## Accepted limitations (documented, not bugs)

- `subtree − direct` differencing can isolate a sub-scope under k — accepted for this app's trust model. The managed view's calculation toggle (v2.12.0) presents both scopes deliberately: each is an already-authorized single-team query, independently k-withheld, so switching the toggle discloses nothing differencing could not already derive.
- The previous-cycle delta indirectly reveals a prior aggregate to a current-cycle respondent (the delta is part of the current view).
- Style-based comment attribution is possible at k=3 with visible participation — inherent to the k=3 floor.
- The trend reads every visible closed cycle in two set-based statements (responses + participant counts grouped by cycle, one transaction, v4.14.0 — was 2 statements + 2 transactions per cycle, F7) and still decrypts/aggregates in Kotlin per cycle — fine at this scale; cap later if needed. The results route reads the current and previous cycle through the same reader (one transaction).
- **Per-request cost (v4.15.0).** Every pulse team read resolves the team with `TeamService.readRef` (ONE statement for the id + name — `read`'s second select, the member ids, was never used by a pulse handler), and the HR trend skips the `document_shares` lookup (an HR own read makes every point visible, so a sharer's responded-cycle set cannot widen it; a non-HR own read and every shared read still look the shares up). Budgets: `results` 9/7, `trend` 6/5, `comments` 6/6 (`QueryBudgetTest`). What stays: the three requests per card (results, comments, trend — the 336 calls per statement of F16 were one per request, four requests per team per HR iteration), and no cross-request cache of the closed-cycle list or the team tree (multi-replica staleness).
- The Trend tab fires one `/trend` request per toggled-on team pill (v2.14.0) — the Results per-team-card stance; the queries cache-share with the Results cards' mini-charts (identical `["pulseTrend", teamId, mode]` keys — cards now fetch theirs only when in view). For HR every team is a pill, so an all-on chart is one request (and one `hr.read`/`pulseTrend` audit row) per org team — accepted like their per-team Results view. The per-scope queries (batched across cycles since v4.14.0, one `scopeDataByCycle` call per request) are forced by the never-pair-a-user-with-an-answer invariant — `PulseAnswers` is user-id-free, so a subtree's answers cannot be partitioned into child scopes after the fact; the grouping key is the cycle id, never the user.
- Q1 says "this company" (no organization-name setting exists).
- **A sharee can infer which cycles the sharer answered (v4.12.0, L1)**: the lapse `403` / `sharedBy` on a cycle reveals whether the sharer took part in it — accepted, and the Share dialog warns ("people you share with can tell which survey cycles you took part in").
- **Overlapping-team shares from different sharers (L2)** let a sharee difference two scopes — the same differencing an upper manager can already do over a team and its sub-team; accepted.
- **Shares of a team's results are time-unbounded over cycles (v4.12.0)**: a share covers every CLOSED cycle, past and future, while the sharer keeps the right; a sharee need not have taken any survey (the share is the grant, the sharer's fill gate the limit). An ADMIN or HR user may be a sharee ("whoever I want" — a deliberate act by an own-right reader, withdrawable by them and the team's manager chain); the narrowed-ADMIN rule governs the role's OWN rights only. The previous-cycle delta on a card is the same team's, so it is not a sibling-document leak.

**Sharing in the SPA (v4.12.0).** `PulseResults.tsx` gained a fourth view, **"Shared with me"** (`view=shared`, offered to everyone, with the same calc toggle): its teams come from `GET /shares?view=withMe&resourceType=PULSE_TEAM_RESULTS&status=ACTIVE` (key `["shares","withMe","pulseTeamResults"]`, so a share mutation refreshes it), deduped by team (the newest share names the sharer as the card's `sharedByFallback`). `?view=` wins over the stored pick when the caller may use it (`all` only for `canAudit()`; storage is never rewritten; picking in the control drops `view`/`team`), `?team=` marks the card (`aria-current="true"` + an accent bar on the title, `scrollIntoView`), and a bare `?team=` (the sharer/author/activity-log link, `shareOpenPath`) opens the first of member → managed → all → shared that holds the team; a caller with no own/managed teams but a share defaults to the shared view (HR's `all` still wins). **The fill-gate probe never uses a shared team**: a share-granted read is decided by the SHARER's fill status, so it can neither prove nor disprove the caller's own — the probe is the first team of an own view WITHOUT an active share (a 200 is then an own-right read, a plain 403 is the gate), runs only on own views, and when the gate holds the page still renders full cards for the view's shared teams beside the comments-only monitor cards. `PulseTeamResultCard` takes `highlighted`/`sharedByFallback` and reads the server flags: the **Share button follows `canShare` only** (never `sharedBy`; `ShareButton` with `resourceType="PULSE_TEAM_RESULTS"`, the id is the TEAM id, the dialog worded by the `pulse` context of `shareKindContext`), the "Shared by {name}" line renders from `data.sharedBy` on whichever view returns it, comments are fetched iff `canMonitor || canReadComments` (a member-sharer's share never asks), and a lapse 403 (`isShareLapse` — the sharer sat the cycle out or lost the team) renders the neutral `pulse.results.sharedUnavailable` note (and hides the trend section, whose own 403 would read as "trend pending") instead of the red load error. The Trend tab is unchanged (D13).
