### Performance reviews

A **performance review** (v1.33.0) is written by a **manager** for a **direct report** and assesses one **review period** across four categories — **attitude, delivery, skills, overall** — each a numeric **1–6 rating** plus a **text summary** (≤4000), **both encrypted at rest** (summaries since `V35`, ratings since `V45`/v1.49.0 — the 1–6 range is enforced solely by `validateAssessments`, the DB CHECKs are gone). The rating travels as its NUMBER (1 = doesn't meet expectations … 6 = exceptional); the textual scale wording is the SPA's localized rendering of that number, never stored or transmitted. The API's category shape is the nested `CategoryAssessment {rating, summary}` (both null while unset). Tables `performance_reviews` (`V35`, standard soft-delete) + audit table `performance_review_events` (`V36`); implementation in `server/src/main/kotlin/reviews/` (`PerformanceReviewService`, `PerformanceReviewEventService`, pure `PerformanceReviewEvents.kt`/`PerformanceReviewNotifications.kt` builders, `PerformanceReviewRoutes.kt`) — cloned from the goals package; where this section is silent, the goals behavior applies.

- **Review periods** (`review_periods`, `V34`; `ReviewPeriodService`/`ReviewPeriodRoutes.kt`): the global, ADMIN-curated timeline of month ranges (inclusive ISO `YYYY-MM` bounds in `VARCHAR(7)` — lexicographic == chronological, the date idiom one level up; strict zero-padded `YearMonth` parse). **Append-only and gapless**: a new period must start exactly the month after the latest existing one ends (the first is free) — a gap or overlap is `409`; periods are immutable (no PUT); only the **latest** period may be deleted, and only while **no review references it** (soft-deleted reviews count) — which is why deletion is a **hard delete**, the deliberate exception to the soft-delete convention (a soft-deleted period would poison the no-gap rule; `UNIQUE (start_month)` backstops racing creates via 23505 → 409). API: `GET /api/v1/review-periods` (any authenticated, **unpaged** `{items}` oldest-first — the dictionaries shape), `POST` + `DELETE /{id}` (ADMIN, audited `review_period.created/deleted`). No events table, no notifications.
- **Status machine**: `DRAFT ↔ CALIBRATION ↔ PUBLISHED` (`PerformanceReviewStatus`), both directions, never skipping CALIBRATION — four action endpoints `POST …/{id}/submit|revert|publish|unpublish`, all bodyless; each names its whole edge (submit and unpublish share the CALIBRATION target). **Submit is gated on completeness**: all four ratings set and all four summaries non-blank (`requireCompleteAssessments`, route-side 400 against the pre-read — the goals activate idiom). Creation (`POST /api/v1/performance-reviews`) always lands in DRAFT, accepts **partial** assessments (a draft is the author's scratch space), and **400s while the chosen period hasn't started** (`startMonth > current month` — a fully-future period is not assessable; checked inside the service transaction with an injectable `currentMonth`, the goals `today` idiom; the SPA's create picker disables future options and defaults to the newest **started** period, with an all-future alert).
- **Edit rules** (manager only — the subordinate never edits, ADMIN gets no write): `PUT /{id}` full-replaces the eight assessment values (parties/period/status immutable) while DRAFT or CALIBRATION; **in CALIBRATION the payload must stay complete** — a value may change but never blank out (400, checked in the service transaction); PUBLISHED is read-only (`409` — unpublish first). `DELETE` is manager-only + **DRAFT-only** (non-draft → `400`), soft, no notification — and frees the uniqueness slot.
- **One review per (subordinate, period)** at ANY status — absolute, unlike feedback's open-status-only rule: enforced by the partial unique index over active rows + an in-transaction pre-check that 409s with `ProblemDetail.instance` pointing at the existing review (a different manager hits the same wall; a deleted draft frees the slot).
- **The stored `manager_id` is the author forever** (the goals model, not the team-KPI current-manager derivation): the direct-report check is create-time only; the author keeps write access even if the subordinate later moves teams. Chain reads follow the subordinate's *current* transitive chain.
- **Reads/visibility**: the author and the HR auditor (audited `hr.read`, resource `performanceReview`) at every status; the **subordinate only once PUBLISHED**; managers in the subordinate's transitive chain from **CALIBRATION** onward (calibration is exactly the phase upper managers join to compare ratings; a draft stays private to its author) — see `.claude/docs/authorization.md`.
- **List** (`GET /api/v1/performance-reviews?view=own|managed|team|user`): `own` (default) = caller is the subordinate AND `status == PUBLISHED` (mirrors the read guard — every listed row is openable); `managed` = caller is the manager, every status — `includeIndirect=true` also includes chain managers' reviews minus their DRAFTs; `team` = reviews authored by the caller's direct reports as managers (`includeIndirect` widens to the chain) AND `status ≠ DRAFT`; `user` = the HR auditor view (`requireAuditListAccess`, resource `performanceReview`). Sortable `id`/`managerName`/`subordinateName`/`periodStart` (→ the joined `review_periods.start_month`)/`status`/`createdAt`/`lastModified`, default `-createdAt`; `managerName`/`subordinateName` substring + `managerId`/`subordinateId`/`periodId`/`status` equality + `createdAt[gte]`/`lastModified[gte]` filters. Rows carry party names, the period (id + months), status, and the four **numeric ratings** (decrypted by the service — since `V45` the stored values are envelopes) — never summaries.
- **Events**: `PerformanceReviewEventType` = CREATED / RATING_CHANGED `{category}` (the bare fact — **never the values** since v1.49.0: ratings are encrypted at rest while `params` is plaintext; `V45` scrubbed historical `from`/`to`) / SUMMARY_CHANGED `{category}` (the bare fact — **never the text**) / STATUS_CHANGED `{from,to}` / DELETED. One event per changed aspect; a no-op PUT mints nothing (null and `""` summaries are the same non-value). Read via `GET …/{id}/events`, authorized like the single GET; persisted by the route.
- **Notifications**: only the edges crossing the publication boundary notify the **subordinate** (the manager is always the actor) — publish with a view link, unpublish without one; `DRAFT ↔ CALIBRATION` is silent. See the table under "Notifications" in `.claude/docs/features/notifications.md`.
