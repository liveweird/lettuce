### Team structure & history (v4.17.0, V93)

Teams, rosters and the manager succession line are **dated**. History is for display and admin editing only — **every right (authorization, the management chain, notification fan-outs, pulse scopes, the team-KPI manager) stays "today only"**. Code: `teams/` (`TeamService`, `TeamStructure.kt`, `TeamHistory.kt`, `TeamHistoryService.kt`, `TeamHistoryRoutes.kt`); the per-resource authz lines are in `.claude/docs/authorization-resources.md`.

**Model.** Base tables `teams` (name + soft-delete flag; no manager column any more), `team_memberships` (one row per membership PERIOD of a person in a team) and `team_manager_periods` (the manager succession line). Dates are strict ISO `YYYY-MM-DD` in `VARCHAR(10)` (lexicographic == chronological); a NULL start = "since before records" (what the V93 conversion wrote for every existing row), a NULL end = open-ended, otherwise the end is the **inclusive** last day. Period rows are hard-deleted (the audit events are the trail). Exposed objects: `TeamService.TeamRecords/TeamMemberships/TeamManagerPeriods` (write side) and the read-only views `Teams` (`teams_current`: each team with its manager as of today — a deleted team keeps its last manager) and `TeamMembers` (`team_members`: current memberships). Everything outside `teams/` reads the views, which is why rights are today-only by construction. Never write through a view; "today" is the injectable `clock` and must agree with the views' `CURRENT_DATE` (session time zone = JVM zone, see "Connection pool" in `persistence.md`).

**Rules** (one per-team advisory lock `pg_advisory_xact_lock(93, teamId)` serialises every structure write; the service re-checks the FINAL state in the same transaction).
- A person's periods in one team never overlap (409); a rejoin is a new row; overlaps across teams are fine.
- The manager line is contiguous and a live team always has a manager: each end is the next start − 1, the last period is open, the first start is today or earlier (a NULL start counts). Adjacent periods of the same manager **merge automatically** into the earlier row (a POST that would split a period with the manager it already has is a 409 instead, as a no-op).
- A manager is never a member of their own team on the same day, both directions: an overlap including today is a 400, one on any other day a 409 (the explicit period endpoints also refuse a purely past overlap; the legacy today-writes ignore history).
- A deactivated person cannot get a membership or manager period reaching today or later (400); purely past periods are allowed. A soft-deleted person cannot get one reaching today either. An edit may only shorten or move: any day from today on that the old period did not cover (a start moved earlier included) counts as an extension. For the manager line the check is per manager on the FINAL line (`grownManagers`): any manager whose coverage of today-or-later grew — newly assigned, or a neighbour absorbing days through a DELETE or a moved start — must be active and not deleted (400).
- Period dates are strict ISO within years 1900–9999 (400 otherwise; a derived end one day before year 0 would overflow the column).
- Existing routes mean "from today": `POST /teams` starts the manager and members today; a rename keeps history; a changed manager starts a new period today (corrected in place when today's period started today); removing a member ends the period yesterday (hard-deleted when it started today; a same-day re-add reopens it); a team delete ends open rows today and hard-deletes rows starting later.
- **Pre-V93 soft-deleted teams** have no deletion date and stay open-ended; the **residue hide rule** (a period on a soft-deleted team with a NULL end) applies in exactly two readers — the as-of list and `users/{id}/team-history`.

**Endpoints.** Reads: any authenticated; a missing/deleted team (or user) is 404 before anything else. Writes: ADMIN-only, guard first, then payload validation (strict ISO, end ≥ start → 400), then the service's 404/400/409.
- `GET|POST /teams/{id}/memberships`, `PUT|DELETE …/{membershipId}` — rows `{id, userId, userName, userDeleted, deactivated, startDate|null, endDate|null, current}`, unpaged `{items}`, nulls first; the person is fixed once a row exists; a row of another team is 404; an unchanged PUT is a quiet 204.
- `GET|POST /teams/{id}/managers`, `PUT|DELETE …/{periodId}` — rows `{id, managerId, managerName, managerDeleted, startDate|null, endDate|null, current}`; input `{managerId, startDate|null}`, the end is always derived. POST splits the containing period (a start before the first row prepends); PUT must keep the start strictly between its neighbours' starts (409, never reorders; a start another period holds is a collision); DELETE merges into the predecessor (or the successor, which inherits the start, when it is the first row); the only period cannot be deleted (409).
- `GET /users/{id}/team-history` → `{memberships, managerPeriods}`, rows `{id, team:{id,name,deleted}, startDate, endDate, current}` (`current` is false on a deleted team), residue hidden.
- `GET /teams?asOf=YYYY-MM-DD` — see "List endpoint conventions": manager and roster of that day from the base tables, deleted teams included while their line covers the day, items carry `deleted` and (as-of only) `members`; three statements however many teams.

**Audit.** `team.membership_created|updated|deleted` and `team.manager_period_created|updated|deleted` (ids, dates, change-only `…From/To`; a period that merged into a neighbour also carries `mergedIntoPeriodId`, a deleted one `absorbedByPeriodId`; all three manager-period events carry `removedPeriodIds` when an automatic merge deleted other rows); the legacy `team.*` events gained `membershipId`/`startDate`/`endDate|hardDeleted`/`managerPeriodId`/`membershipsEnded`/`futureRowsRemoved`. **Activity trail (v4.18.0, V94).** Every `team.*` audit line above is paired with one `team_structure_events` row (the eleventh `EventLogTable` clone, keyed on the team, actor = the admin, name snapshots in the params, `TEAM_UPDATED` change-only (rename / handover / roster delta, carrying `nameFrom`/`nameTo`) whereas the `team.updated` audit line fires on every PUT; the other events mirror their audit line — `teams/TeamStructureEvents.kt`) feeding the activity log's `TEAM_MEMBERSHIP` area, actor-only (the affected person's history stays on this page's History section); forward-only from V94. See "Team-structure rows" in `.claude/docs/features/activity-log.md`.

**GraphQL (v4.18.0).** The integration API exposes the history read-only and additively (`Team.memberships`, `Team.managerPeriods`, `User.teamMemberships`, `User.managedTeamPeriods`; see "Team history" in `.claude/docs/features/integration-api.md`). The reads are `TeamHistoryService.membershipsByTeamIds` / `managerPeriodsByTeamIds` / `historyByUserIds` — batched (one transaction, one grouped statement per list) and also the implementation behind the REST `GET …/memberships`, `GET …/managers` and `GET /users/{id}/team-history`, so the residue hide rule and the ordering exist once. Integration reads bypass authorization like the rest of that API; the rights themselves stay today-only.
