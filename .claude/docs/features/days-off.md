### Days off

A **days-off request** (v1.42.0) is a personal ask by its **owner** (self-only create — no create-on-behalf, ADMIN included) covering one **consecutive period** `[start_date, end_date]` (ISO `VARCHAR(10)` bounds, the goals date idiom; single day allowed; **never spanning calendar years** — 400, so the frozen cost attributes to exactly one budget year), typed **PAID | UNPAID**, with **edge half-days** (`start_half`/`end_half`; a single-day request uses `start_half` only — `end_half` there is 400). Tables `days_off_requests` (`V40`, soft-delete column per convention but no DELETE endpoint) + the `public_holidays` registry (`V39`, hard-deleting) + `users.paid_days_off_allowance` (`V38`). Implementation in `server/src/main/kotlin/daysoff/` (`DaysOff.kt` pure math/DTOs, `DaysOffService`, `DaysOffNotifications.kt`, `DaysOffRoutes.kt`, `PublicHoliday*`) — routes/list cloned from goals, the holidays registry from review-periods.

- **Status machine**: `REQUESTED → ACCEPTED | REJECTED` (resolved by a **current direct manager** of the owner via `POST …/{id}/accept|reject`, stamping `resolved_by`/`resolved_at`) plus terminal `CANCELLED` (the owner via `POST …/{id}/cancel` — from REQUESTED anytime, from ACCEPTED only strictly **before** `start_date`, stamping `cancelled_at`; wrong-status → 409). **No events table by design** — the single-transition lifecycle is fully carried by the row's stamps. REQUESTED + ACCEPTED are the **counting** statuses (they reserve paid budget and appear on the calendar); REJECTED/CANCELLED free it.
- **Cost** (`daysOffCostHalfDays`, half-day integer units): a day counts iff not Sat/Sun and not a public holiday; a counted day costs 2 units, minus 1 per half toggle when that edge day is itself counted. A zero-cost period (weekends/holidays only) is 400 for both types. The cost is computed against the then-current holiday registry **at creation and FROZEN** on `cost_half_days` — registry edits never reprice history. API carries `days = costHalfDays / 2.0` (halves are exact in IEEE754); the SPA mirrors the math in `utils/daysOffCost.ts` for the create form's preview.
- **Budget** (PAID only; UNPAID is unlimited): `users.paid_days_off_allowance` (whole days 0–365, null = unconfigured = zero budget) is ADMIN-only assignable via the users POST/PUT (the career-field null/omitted-=-unchanged semantics, guard `requireCanAssignPaidDaysOffAllowance`; audited as `allowanceFrom/To` deltas) and rides `UserResponse` like the career fields. **Carry-over is a closed form** (`remainingHalfDays` in `DaysOff.kt`): anchored at `A = min(earliest counting-PAID year, target year)`, `remaining(Y) = 2·allowance·(Y−A+1) − Σ counting costs in A..Y` — the allowance never phantom-accumulates over empty history, the CURRENT allowance applies to every year (admin edits recompute retroactively — documented), and the value is deliberately unclamped (a retroactive cut carries a deficit forward). **Enforcement at create only**, in-transaction: with the new cost added, `remaining(y) ≥ 0` must hold for every year from the request's through the last counting year (a retroactive create may not break a later carry-funded year) — violation 409. All aggregation runs in Kotlin over the owner's rows (no SQL arithmetic on R2DBC).
- **Overlap invariant**: the owner's counting requests may not intersect (`newStart ≤ e.end AND newEnd ≥ e.start`, plain string compares — safe only behind the strict ISO validation) → 409 with `ProblemDetail.instance` pointing at the conflict (the feedback-duplicate precedent). Create-time only; dates are immutable after create, and CANCELLED/REJECTED rows free the slot.
- **Reads**: read-before-guard (404/403, the goals idiom); owner + HR auditor (audited, resource `daysOff`) at every status, chain managers at every status, teammates only while REQUESTED/ACCEPTED (**calendar parity** — see `.claude/docs/authorization.md`). List views `own | managed | user` (managed = **direct reports only**, matching the resolve right — no `includeIndirect`; `user` = the HR auditor list); sortable `id`/`userName`/`startDate`/`endDate`/`type`/`status`/`days`(→`cost_half_days`)/`createdAt`, default `-startDate`; `userName` substring + `userId` (pin-filter on managed, required on user, rejected on own) + `type`/`status` equality + `startDate[gte|lte]` (validated strict ISO) filters.
- **Calendar** (`GET /api/v1/days-off/calendar?month=YYYY-MM&scope=member|managed`, any authenticated, unpaged — bounded by scope users × ≤31 days): `member` = everyone sharing a non-deleted team with the caller (caller included; a team-less caller sees themselves), `managed` = direct reports. Every scoped user appears (rows must render); counting requests are clipped to the month and expanded per-day **including weekends** (bars render continuously; the grid dims those columns), `half` marking the edge days; the month's holidays are embedded. **Budgets** (`GET /api/v1/days-off/budgets?view=own|managed&year=`): one row per user — `allowance`/`carriedOver`/`reserved` (REQUESTED)/`used` (ACCEPTED)/`remaining`, all in days.
- **Public holidays** (`/api/v1/public-holidays`): the review-periods registry clone — GET any-authenticated unpaged `{items}` date-ascending, POST/DELETE ADMIN-only with audit (`public_holiday.created/deleted`), `UNIQUE (holiday_date)` → 23505 → 409, hard delete (costs stay frozen). `V41` seeds the Polish statutory holidays for 2026–2027 (idempotent; admin rows never overwritten). Known limitation (documented): a top-of-chain manager's request has no direct manager to accept it.
- **Card stats + per-user drill-down (v1.44.0)**: subordinate person cards (dashboard grid at direct scope + details direct-report flavor) show **Next vacation** + **Days-off budget left** via the `/teams/members` enrichment above (`PersonCardBody`'s `showDaysOff` gate, the `showLastReview` idiom; the card's Days-off section since v1.46.0); peer cards show Next vacation only (the `peer` stats variant, unconditional — member rows always carry it). Those manager-side cards also carry a **"Days off" button** → `/users/:id/days-off`: `UserDaysOff.tsx`'s **manager mode** (origins `subordinates`/`team`, or `from=details&manages=1`) — the report's requests (`DaysOffTable view=managed` pinned by `userId`, Accept/Reject inline, settings `userDaysOff.managed`), a per-user budget strip (the managed budgets fetch filtered client-side; a vanished direct-report relationship shows the not-a-report hint), and the manage-capable Corrections modal; the HR `?mode=audit` flavor is unchanged; anyone else redirects to `/days-off`. Links via `userDaysOffLink(userId, name, from, teamId?, audit?, opts?)`.
- **Budget corrections** (v1.43.0, `days_off_corrections` V42): a manager-authored **± adjustment** to a subordinate's paid budget for a **chosen calendar year** — `{userId, year, operation ADD|SUBTRACT, days (0.5 steps), comment}` stored as one **signed half-day int** with the comment **encrypted at rest** (`DaysOffService` carries the cipher; `encryptLegacyRows` hook in `configureBootstrap`). No approval workflow, no per-record events; **writes = the subordinate's CURRENT direct managers** (the resolve right — `requireDaysOffResolve` keyed on the ROW's user; `author_id` is display-only), **reads = the subordinate, chain managers, and HR** (audited `hr.read`, resource `daysOffCorrections`; peers/ADMIN-as-such get nothing — `requireDaysOffCorrectionsRead`). Endpoints: `GET /api/v1/days-off/corrections?userId=[&year=]` (unpaged), `POST`, `PUT`/`DELETE …/{id}` (target user immutable; soft delete). The closed form gains `correctionsByYear` (anchor = earliest counting-or-correction year; signed sums; unclamped — a SUBTRACT may push a year negative, only *request creation* sweeps), budget rows gain `corrected` (the year's net), and the create-sweep counts corrections. Creation notifies the subordinate (`DAYS_OFF_CORRECTED_TO_OWNER`); edits/deletes mint no notification, but since v2.4.1 all three mutations are audit-logged (`days_off_correction.created/updated/deleted` — see `.claude/docs/observability.md`). SPA: the one `components/DaysOffCorrections.tsx` modal body — manager-editable from the budgets table's Corrections column/action, read-only from the own budget card and the HR audit drill-down.
- **Notifications**: see the table under "Notifications" in `.claude/docs/features/notifications.md` — creation → every current direct manager; accept/reject → the owner; cancel-from-ACCEPTED → the resolving manager, cancel-from-REQUESTED → every current direct manager.
