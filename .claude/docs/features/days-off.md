### Days off

A **days-off request** (v1.42.0) is a personal ask by its **owner** (self-create; since v2.29.0 (chain-wide since v2.33.0) a **manager in the owner's TRANSITIVE chain may also record an entry on a report's behalf** — `DaysOffCreateRequest.userId`, the ONE create-on-behalf in the app, guarded by the resolve right and born ACCEPTED with the caller stamped as resolver, audited `days_off.recorded`; ADMIN/HR still get nothing, a self-targeting userId is 403 like any non-manager, and a deactivated target is 400 per the no-new-assignments rule — the vacation-history population flow, every state rule below unchanged) covering one **consecutive period** `[start_date, end_date]` (ISO `VARCHAR(10)` bounds, the goals date idiom; single day allowed; **never spanning calendar years** — 400, so the frozen cost attributes to exactly one budget year), typed **PAID | UNPAID** — a PAID request additionally names the **paid pool** it draws on (`pool_type_id`, v3.2.0 — see "Paid pools" below; UNPAID never does, the V74 CHECK) — with **edge half-days** (`start_half`/`end_half`; a single-day request uses `start_half` only — `end_half` there is 400). Tables `days_off_requests` (`V40`, soft-delete column per convention but no DELETE endpoint) + the `public_holidays` registry (`V39`, hard-deleting) + the paid pools pair `days_off_pool_types`/`days_off_pools` (`V74` — which absorbed and dropped `users.paid_days_off_allowance`, `V38`). Implementation in `server/src/main/kotlin/daysoff/` (`DaysOff.kt` pure math/DTOs, `DaysOffService`, `DaysOffNotifications.kt`, `DaysOffRoutes.kt`, `PublicHoliday*`) — routes/list cloned from goals, the holidays registry from review-periods.

- **Status machine**: `REQUESTED → ACCEPTED | REJECTED` (resolved by **any manager in the owner's TRANSITIVE chain** via `POST …/{id}/accept|reject` — chain-wide since v2.33.0, the chain rule, stamping `resolved_by`/`resolved_at`; an on-behalf create, v2.29.0, skips REQUESTED — the row is BORN ACCEPTED with the recording manager as resolver, since they hold the accept right anyway) plus terminal `CANCELLED` (reworked v2.31.0/V63: the **owner or ANY manager in the owner's transitive chain** via `POST …/{id}/cancel` — from REQUESTED **or ACCEPTED regardless of date**, always with a **mandatory `reason`** (non-blank ≤1000, encrypted at rest — the correction-comment class) stamping `cancelled_at`/`cancelled_by`/`cancel_reason`; wrong-status → 409, blank/oversized reason → 400 after the guard, audited `days_off.cancelled` — never the reason. Rows cancelled pre-rework carry null actor/reason. Note the budget consequence of a retroactive PAID cancel: the freed cost can move the carry-over anchor FORWARD, reducing a later year's accumulated allowance — accepted). **No events table by design** — the single-transition lifecycle is fully carried by the row's stamps. REQUESTED + ACCEPTED are the **counting** statuses (they reserve paid budget and appear on the calendar); REJECTED/CANCELLED free it.
- **Cost** (`daysOffCostHalfDays`, half-day integer units): a day counts iff not Sat/Sun and not a public holiday; a counted day costs 2 units, minus 1 per half toggle when that edge day is itself counted. A zero-cost period (weekends/holidays only) is 400 for both types. The cost is computed against the then-current holiday registry **at creation and FROZEN** on `cost_half_days` — registry edits never reprice history. API carries `days = costHalfDays / 2.0` (halves are exact in IEEE754); the SPA mirrors the math in `utils/daysOffCost.ts` for the create form's preview.
- **Paid pools (v3.2.0, V74)** — a user may hold SEVERAL paid pools, each with its own allowance and its own budget history; every PAID request and every correction targets exactly one. Two tables: **`days_off_pool_types`** — the ORG-WIDE registry of pool KINDS (ADMIN-managed, the public-holidays posture: `GET /api/v1/days-off/pool-types` any authenticated with DAYS_OFF, active kinds only, default first then name; `POST`/`PUT {id}`/`DELETE {id}` ADMIN, audited `days_off_pool_type.created/updated/archived` — the `updated` event carries `grantsAffected` on a carry-over flip, the count of active grants whose history it recomputed, v3.2.1) — `name` (single-line ≤100, unique among active kinds via the `uq_days_off_pool_types_name_active` partial index → 23505 → 409), **`carries_over`** (the admin's per-kind flag: unused days transfer to the next year, or the pool resets every January), `is_default` (the ONE seeded kind — 'Paid days off', carry-over — every pre-V74 PAID row, correction, and allowance maps to it; renameable/re-flaggable, NEVER archivable → 409, and no endpoint moves the flag); soft-deleting = "archived": an archived kind can no longer be granted or targeted, and archiving it **cascades to every active grant in the same transaction** (nobody keeps a pool of a retired kind), while name lookups NEVER filter on the flag (history keeps its label). **`days_off_pools`** — the PER-USER grants `(user_id, pool_type_id) → allowance` (0–365, `uq_days_off_pools_user_type_active` over active rows); soft-deleting = "archived" and a TRUE soft delete (API-RES-007): an archived grant is invisible to every read, and a later re-grant of the same kind INSERTS a fresh row — the pool's history is keyed on `(user_id, pool_type_id)` in the requests/corrections tables, not on the grant row, so it simply continues. Rules: a PAID request/correction names its kind via `poolTypeId` (null = the default kind); an UNPAID request with one is 400; an unknown/archived kind is 400; an EXTRA kind the user holds no ACTIVE grant of is 400 ("no such pool for this user") — the default kind needs no grant (ungranted = zero budget → the create sweep's 409, the pre-v3.2.0 rule). The pool is immutable after create — a correction's PUT treats `poolTypeId` null as unchanged and a DIFFERING kind as 400 (v3.2.1 — never silently kept, the API-RES-004 lost-write shape; `userId` stays the ignored legacy field); re-homing is delete + create. Responses carry `poolTypeId` + `poolName` (the kind's CURRENT name; null for UNPAID) on requests/list rows/calendar entries and corrections; the list gains the `poolTypeId` equality filter. **The teammate redaction (v3.2.1)**: calendar parity discloses THAT a colleague is off, never the category of leave — the member-scope calendar nulls `poolName` on OTHER people's entries (the caller's own bars and the managed scope keep it), and `GET /days-off/{id}` nulls both pool fields when the TEAMMATE rule granted the read (`requireDaysOffRead` returns the granting `DaysOffReadGrant`; owner/chain/HR see the pool). The deactivated-user exemption: the allowance PUT deliberately has no `requireNoDeactivatedUsers` (the corrections precedent — a budget edit is not a new assignment). Grants are written by **`PUT /api/v1/days-off/allowance`** `{userId, allowance, poolTypeId?}` (the v2.32.0 endpoint, now an upsert of ONE (user, kind) grant — creates the pool when the user holds none of that kind, overwrites the allowance otherwise; same chain-only guard-first 403 — never the user, ADMIN, or HR; range 400; idempotent silent 204; two concurrent FIRST grants race on the active-grant unique index → 23505 → a declared 409 (v3.2.1, the create-race class); an actual change — a fresh grant included — is audited `days_off.allowance_changed` (+`poolTypeId`) and notifies the owner with `DAYS_OFF_ALLOWANCE_CHANGED` `{manager, pool, from?, to}`), and archived by **`DELETE /api/v1/days-off/pools/{id}`** (the grant id rides the budget rows as `poolId` — the only endpoint addressing a grant directly; the correction-write preamble: read → 404, then `requireDaysOffResolve` on the row's user; the default pool → 409; audited `days_off_pool.archived`, no notification). The `/teams/members` card stat `daysOffRemaining` is **the default pool's** remaining (`DaysOffService.remainingByUserIds` over `defaultBudgets`) — a one-number summary; extra pools surface on the drill-down. `TestDaysOff.setAllowance(userId, days, poolTypeId = 1u)` is the test fixture (an upsert into `days_off_pools`; `null` hard-deletes the grant — test-only), `TestDaysOff.createPoolType` mints unique extra kinds.
- **Budget** (PAID only; UNPAID is unlimited) — per pool since v3.2.0: **carry-over is a closed form** (`remainingHalfDays` in `DaysOff.kt`) over ONE pool's counting requests and corrections: anchored at `A = min(earliest counting-PAID year, target year)`, `remaining(Y) = 2·allowance·(Y−A+1) + Σ corrections − Σ counting costs in A..Y` — the allowance never phantom-accumulates over empty history, the CURRENT allowance applies to every year (allowance edits recompute retroactively — documented), and the value is deliberately unclamped (a retroactive cut carries a deficit forward). **A non-carry-over kind** (`carriesOver = false`) forces `A = Y`: `remaining(Y) = 2·allowance + corrections[Y] − used[Y]` and `carriedOver` is always 0 (flipping a kind's flag recomputes every affected budget — the allowance-change precedent). **Enforcement at create only**, in-transaction and pool-scoped: with the new cost added, `remaining(y) ≥ 0` must hold for every year from the request's through the pool's last counting year (a retroactive create may not break a later carry-funded year; a non-carry pool checks the request's year only) — violation 409. All aggregation runs in Kotlin over the owner's rows (no SQL arithmetic on R2DBC). The archive-vs-create race (the grant read and the insert share `create`'s READ COMMITTED transaction) is the same accepted class as two concurrent creates both passing the sweep.
- **Overlap invariant**: the owner's counting requests may not intersect (`newStart ≤ e.end AND newEnd ≥ e.start`, plain string compares — safe only behind the strict ISO validation) → 409 with `ProblemDetail.instance` pointing at the conflict (the feedback-duplicate precedent). Create-time only; dates are immutable after create, and CANCELLED/REJECTED rows free the slot.
- **Reads**: read-before-guard (404/403, the goals idiom); owner + HR auditor (audited, resource `daysOff`) at every status, chain managers at every status, teammates only while REQUESTED/ACCEPTED (**calendar parity** — see `.claude/docs/authorization.md`). List views `own | managed | user` (managed = **direct reports** by default — a list scope, not a rights boundary — widened to the whole transitive subtree by the strict-boolean `includeIndirect` — v2.32.0, 400 on other views; rows carry the `canCancel` + `canResolve` capability flags, both chain-wide since v2.33.0 (`canResolve` = REQUESTED + owner in the caller's subtree); `user` = the HR auditor list); sortable `id`/`userName`/`startDate`/`endDate`/`type`/`status`/`days`(→`cost_half_days`)/`createdAt`, default `-startDate`; `userName` substring + `userId` (pin-filter on managed, required on user, rejected on own) + `type`/`status` equality + `startDate[gte|lte]` (validated strict ISO) filters.
- **Calendar** (`GET /api/v1/days-off/calendar?month=YYYY-MM&scope=member|managed`, any authenticated, unpaged — bounded by scope users × ≤31 days): `member` = everyone sharing a non-deleted team with the caller (caller included; a team-less caller sees themselves), `managed` = direct reports. Every scoped user appears (rows must render); counting requests are clipped to the month and expanded per-day **including weekends** (bars render continuously; the grid dims those columns), `half` marking the edge days; the month's holidays are embedded. **Budgets** (`GET /api/v1/days-off/budgets?view=own|managed&year=`): since v3.2.0 **one row per (user, paid pool)** — user name/id, then the default kind first, then pool name: the default kind's row ALWAYS (allowance null when ungranted — "not configured = zero budget"), one row per active extra grant, and history-only rows (`poolArchived` — allowance null, no `poolId`) for extra kinds with a counting request or correction IN that year but no active grant — a grant whose KIND was archived under it (the archive × upsert race: `upsertPool` reads the kind, `archivePoolType` commits, the insert lands) is `poolArchived` too (v3.2.1, `PoolKind.archived`), never a live pool, and `resolvePoolKind` already refuses requests/corrections against it; each row carries `poolId` (the active grant, the DELETE handle)/`poolTypeId`/`poolName`/`carriesOver`/`isDefault`/`poolArchived` plus `allowance`/`carriedOver`/`corrected`/`reserved` (REQUESTED)/`used` (ACCEPTED)/`remaining`, all in days, plus the **`canCorrect`** capability flag (v2.32.0; chain-wide since v2.33.0 — true on every managed-view row, since each is in the caller's subtree by construction; false on view=own). `view=managed` accepts the strict-boolean **`includeIndirect`** (400 with own — the standard shape rule) widening from direct reports to the caller's whole transitive subtree — the drill-down's chain mode.
- **Public holidays** (`/api/v1/public-holidays`): the review-periods registry clone — GET any-authenticated unpaged `{items}` date-ascending, POST/DELETE ADMIN-only with audit (`public_holiday.created/deleted`), `UNIQUE (holiday_date)` → 23505 → 409, hard delete (costs stay frozen). `V41` seeds the Polish statutory holidays for 2026–2027 (idempotent; admin rows never overwritten). Known limitation (documented): a top-of-chain manager's request has no manager anywhere above to accept it.

- **Budget corrections** (v1.43.0, `days_off_corrections` V42): a manager-authored **± adjustment** to a subordinate's paid budget in ONE pool (`poolTypeId`, v3.2.0 — null = the default kind; the grant rule above applies; immutable on PUT) for a **chosen calendar year** — `{userId, year, operation ADD|SUBTRACT, days (0.5 steps), comment, poolTypeId?}` stored as one **signed half-day int** with the comment **encrypted at rest** (`DaysOffService` carries the cipher; `encryptLegacyRows` hook in `configureBootstrap`).
