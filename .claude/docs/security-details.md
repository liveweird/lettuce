### Security details

The on-demand companion of `.claude/docs/security.md` (the dev/prod posture, the fail-closed startup checks, payload validation and encryption at rest — always loaded). Read this before touching authentication flows, outbound email/Teams, rate limits, the proxy/CORS contract, or the seeds.

**Login password verification** (`auth/Passwords.kt` + `auth/AuthRoutes.kt`): an unknown email still performs bcrypt verification against a dummy hash at the default password work factor before returning the same `401` as a wrong password (API-ERR-003 / API-ERR-006). Missing accounts always fail, even if the submitted password matches that dummy hash. The 71-byte UTF-8 limit remains a uniform early rejection for both known and unknown accounts. An email longer than 254 characters (after the canonical fold) is likewise rejected uniformly and early — but as a `400`, not the password rule's `401` — BEFORE the lockout reservation (checkup #37 C1 — `login_lockouts.email` is `VARCHAR(254)`, so reserving one used to `500` with an ERROR stack; length reveals nothing about whether an account exists); every other malformed email stays the uniform `401`. This removes the skipped-bcrypt timing difference; it is not a constant-time guarantee for the entire HTTP request. Lockout checks still run before password verification, and correct-password deactivation and MFA handling retain their existing behavior.

**Sign-in history** (`account_events`, V90, v4.9.0 — the activity log's `ACCOUNT` area): a login that actually COMPLETES — the very points that stamp `users.last_login_at`, i.e. the non-MFA `/login` success (`SIGNED_IN {mfa:"false"}`) and the `/login/mfa` code-exchange success (`SIGNED_IN {mfa:"true"}`) — and an explicit `/logout` (`SIGNED_OUT`) each append one row via `AccountEventService` (`activity/`), owner = actor = the account. **Nothing else is recorded**: no failed attempt, lockout, deactivated 403, MFA challenge or wrong code, no `/refresh`, no password event, **no IP and no user agent** (the OTel audit stream keeps IPs; this table is the user-visible history). Readable through `GET /api/v1/users/{id}/activity` by exactly the `lastLoginAt` audience — the person, a manager in their transitive chain, HR (audited `hr.list`). **Best-effort**: the write and the purge catch every ordinary failure, log it at ERROR and never fail the login/logout (`AccountEventTest`'s failing-service cases); the insert is awaited, but the **retention purge is launched fire-and-forget on the Application scope**, off the request path. **`SIGNED_OUT` is recorded only when the sign-out reaches the server with a live access token** — a session that simply idles out or whose token already expired never signs out explicitly, so a `SIGNED_IN` without a later `SIGNED_OUT` is normal. **Retention — the registered hard-delete exception** (see "Soft delete" in `.claude/docs/persistence.md`): `activity.accountRetentionDays` (`$ACTIVITY_ACCOUNT_RETENTION_DAYS`, default 90, 0 = keep forever) and `activity.accountPurgeIntervalSeconds` (`$ACTIVITY_ACCOUNT_PURGE_INTERVAL_SECONDS`, default 3600, 0 = purge on every write — the test suite's setting) bound it, both **boot-validated** like the other numeric knobs (`requireConfigLong`: retention `0..3650`, interval `0..86400`; `SecurityConfigTest`) — rows older than the retention are deleted on the write path, throttled per instance, org-wide, in bounded batches of 5000 (`id IN (SELECT id … LIMIT n)`, one short transaction each, until a batch deletes nothing — one unbounded DELETE could outlast `statement_timeout` and then fail forever, v4.12.1; the batch size is the `AccountEventService` constructor's `purgeBatchSize`). Forward-only: before v4.9.0 sign-ins exist only as `last_login_at` and audit lines. **Data-protection rationale:** the timeline is visible to the person, their transitive management chain and HR (the `lastLoginAt` audience), holds no IP or user agent, and is purged after the retention window; operators in jurisdictions with employee-monitoring rules should review `activity.accountRetentionDays` (and may set it low) before enabling the log for their workforce.

**Last-login timestamp** (`users.last_login_at`, V78, v3.9.1): a login that actually COMPLETES — the non-MFA `/login` success and the `/login/mfa` code-exchange success, never `/refresh` and never the MFA password/challenge step — stamps `UserService.updateLastLoginAt`. Surfaced as `lastLoginAt` on `GET /users/{id}` and `/teams/members`, gated exactly like `seniorityLevel` (self, a manager in the person's transitive chain, or HR — see "Authorization model" in `.claude/docs/authorization.md`).

**Per-account login lockout** (`auth/LoginThrottle.kt`, wired in `configureAuthRoutes`): after `security.lockout.threshold` (default 5, `$LOGIN_LOCKOUT_THRESHOLD`) consecutive failures for one submitted email, `/login` answers `429` for `security.lockout.durationSeconds` (default 900, `$LOGIN_LOCKOUT_DURATION_SECONDS`) — even with the correct password, and regardless of whether the account exists (no enumeration signal). A success resets the counter. **Since v3.13.1 the attempt is RESERVED atomically before password verification** (`reserveAttempt` — one upsert; a concurrent burst cannot exceed the threshold, since the (threshold + 1)-th in-flight attempt is already answered `429` by the reservation itself), and a correct-password-but-deactivated attempt releases its reservation (`release`) rather than counting toward the lockout. **DB-backed since v3.11.0/V81** (`login_lockouts`, `infra/db/Database.kt` publishes the connected `R2dbcDatabase` for `configureAuthRoutes` to reuse) — replicas share the counters and a restart no longer resets them; there is no background sweeper, `reserveAttempt` opportunistically prunes rows whose lock has expired and that have gone untouched for a week (`COUNTER_RETENTION_MILLIS` — deliberately far longer than the lockout window, so an attacker cannot stay under the threshold by spacing guesses a window apart; the in-memory map never decayed a counter at all), on the next write for ANY key. Writes are bounded in practice by the per-IP `RateLimit` bucket in front of `/login` (production: 10/min per host × the 900s lockout window ≈ 150 live rows per host at any time). Complements that per-IP `RateLimit` bucket, which rotating hosts sidestep. Tests: `LoginThrottleTest` (DB-backed, injected clock) + `LoginLockoutTest` (route) + `AuthStateAcrossInstancesTest` (a lockout tripped via one app instance is enforced via another, over the shared container). The SPA maps the 429 to `auth.accountLocked` — unless the problem `detail` names "sign-in codes", the v3.13.3 MFA issuance cap's 429, which maps to `auth.mfaThrottled` (the two share the status; the detail phrase is the contract).

**Per-IP login bucket** (`security.rateLimit.loginPerMinute`, `$LOGIN_RATE_LIMIT_PER_MINUTE`, registered in `configureAuthRoutes`): blank **follows the mode** — 10/min in production, 1000/min in development — and an explicit number pins it in either mode (the `http.exposeOpenApi` idiom). Development is lifted because the e2e suite drives ~90 logins from one host and otherwise spends minutes sleeping out the bucket; **the per-account lockout above is the actual brute-force defence and is identical in both modes**. The sibling `refresh` (30/min) and `password-reset` (5/min) buckets are deliberately not configurable. `RateLimitResponseTest`, `ForwardedHeadersTest` and `LoginTest` pin the value to `10` explicitly, since tests run in development mode.

**Document-sharing rate limit** (`sharing.rateLimitPerMinute`, `$SHARING_RATE_LIMIT_PER_MINUTE`, default 60, v4.8.0): the `shares` bucket on `POST /api/v1/shares` and `POST /api/v1/shares/{id}/withdraw`, keyed **per caller** (the JWT principal's `userId`, falling back to the host) — each call fans out a notification and an email mirror. Registered in `configureAuthRoutes`' single `install(RateLimit)` and boot-validated through `optionalConfigInt` `1..100000` like the login/integration buckets (a bad value refuses to start in every mode; 0 would answer every request 429). **The mass share has its OWN bucket (v4.10.0)**: `shares-batch` on `POST /api/v1/shares/batch` — `sharing.batchRateLimitPerMinute` (`$SHARING_BATCH_RATE_LIMIT_PER_MINUTE`, default **10**), same per-caller keying, same `1..100000` boot validation through `optionalConfigInt` — because one batch call fans out up to 20 summary notices (+ email + Teams), so sharing the 60/min bucket would have let one caller trigger up to 1,200 sends a minute; a batch neither spends nor is throttled by the single-share/withdraw tokens (the SPA chunks a selection above 200 documents sequentially, which 10/min covers amply). The per-pair daily notification cap (below) is the companion bound on what one victim receives — see `.claude/docs/features/sharing.md`.

**Document-sharing notification cap** (`sharing.notificationDailyCapPerPair`, `$SHARING_NOTIFICATION_DAILY_CAP_PER_PAIR`, default 20 = `SHARE_NOTIFICATION_DAILY_CAP_PER_PAIR` in `sharing/Share.kt`, v4.8.0): the companion of the rate limit above — it bounds what one VICTIM can be made to receive rather than how fast one caller can act. Once a sharer has caused that many share notifications (SHARED + WITHDRAWN, counted from `document_shares` for the (sharer, sharee) pair over a rolling 24 h — **a batch share counts as ONE notice**: every row of one mass share carries the same `batch_id`, V91, and the count is `COUNT(DISTINCT COALESCE(batch_id, id::text))`; withdrawals stay per row) the share/withdrawal still happens but mints no notification (so no in-app, email or Teams message), audited `notified=false`. Boot-validated `1..1000` through `optionalConfigInt` (blank = the default; a bad value refuses to start in every mode) — see `.claude/docs/features/sharing.md`.

**Deactivated accounts at login** (v1.48.0): a **deactivated** account (the reversible V44 admin disable — see "Authorization model" in `.claude/docs/authorization.md`) with CORRECT credentials answers a distinct **403 "Account is deactivated"** — the check runs only after `verifyPassword` succeeds, so it is no enumeration oracle (wrong password stays the uniform 401 and still feeds the lockout counter; the 403 path releases the reservation it took before bcrypt — since v3.13.1 — so the counter does not move and nothing is reset, and a locked account answers 429 first). The SPA maps the 403 to `auth.accountDeactivated`. `/refresh` rejects deactivated users with 401 (their `read()` deliberately still succeeds — data stays readable — so the refresh handler checks the flag explicitly), and the password reset below treats them like unknown addresses (`password_reset.deactivated` audit, no email, uniform 202).

**Self-service password reset** (`POST /api/v1/password-reset`, in `auth/AuthRoutes.kt`; SPA: "Forgot password?" on `/login` → `/reset-password`): body `{email}`; always `202` for a well-formed request — account existence is unobservable (the lookup/generate/send/store work runs **asynchronously** after the response, so latency is uniform too). If the account exists, a new 16-char password is generated server-side (`generatePassword` in `auth/Passwords.kt`), the email is sent **first** and only then the bcrypt hash stored via `UserService.updatePassword` (a delivery failure leaves the old password working); the `password_changed_at` stamp invalidates outstanding refresh tokens. Throttled per submitted email — one request per `security.passwordReset.minIntervalSeconds` (default 60, `$PASSWORD_RESET_MIN_INTERVAL_SECONDS`) — uniformly for existing and unknown addresses (`auth/PasswordResetThrottle.kt`, DB-backed since v3.11.0/V81 (`password_reset_requests`) — shared by replicas, a restart no longer resets it, and a rejected attempt idle past the interval just ages out on the next write for any key), plus a per-IP `RateLimit` bucket (5/min, bounding live rows to roughly 5 per host per interval). `503` when the deployment has no outbound email (`MAIL_TRANSPORT=disabled`). The email renders in the RECIPIENT'S language (V61 `users.language`, EN fallback — `auth/PasswordResetEmail.kt` over the `LocalizedText` catalog in `infra/mail/`), includes a sign-in link only when `mail.appUrl` is set, and warns the recipient that their previous password no longer works. Tests: `PasswordResetThrottleTest` (DB-backed) + `PasswordResetTest` (route, incl. full email→login roundtrip via a `ListAppender` on the `ch.nokillswit.mail` logger) + `AuthStateAcrossInstancesTest` (a throttled request via one instance is enforced via another).

**Email MFA (opt-in, v2.4.0)** (`auth/MfaChallenges.kt` + `auth/MfaEmail.kt`, wired in `configureAuthRoutes`): a per-user second factor behind the `MFA` feature flag — **one of the two inverted-default (opt-in) flags** (the other is `TEAMS_NOTIFICATIONS`, V85 — both in `OPT_IN_FEATURES`, `users/User.kt`): `V52` seeds every existing user as MFA-disabled and `UserService.create` inserts the disabled row for every new user (admin create, CSV import, and test seeds all funnel through it), so MFA is OFF until an admin removes the row via the features PUT (the per-user editor or the `/feature-flags` bulk screen; mind the wholesale-replace semantics — a PUT whose disabled set omits `MFA` ENABLES it, including the "empty array re-enables everything" idiom). With MFA enabled, `POST /login` with correct credentials answers `200 MfaChallengeResponse {mfaRequired, challengeId, expiresAt}` instead of tokens (the branch runs AFTER `verifyPassword` and the deactivated 403, so nothing about enumeration or lockout changes; `login.success` is deliberately NOT emitted); a 6-digit code (`generateMfaCode`, `auth/Passwords.kt`) is held in the DB-backed challenge store (`mfa_challenges`, since v3.11.0/V81 — config `security.mfa.codeTtlSeconds` default 300 `$MFA_CODE_TTL_SECONDS`, `security.mfa.maxAttempts` default 5 `$MFA_MAX_ATTEMPTS`; replicas share pending challenges and a restart no longer invalidates one mid-flight — a correct-password login just needs to be retried against whichever instance answers; a stray challenge is bounded by its own TTL, pruned on the next `issue` for any account, and the MFA login rate bucket caps how many exist at once per host) and emailed in the user's language (V61, EN fallback). `POST /api/v1/login/mfa` `{challengeId, code}` (own per-IP bucket `"mfa"`, hardcoded 10/min in every mode) exchanges it for the ordinary `LoginResponse` — one fresh `userService.read` first (the `/refresh` precedent: current roles/flags; deactivated-in-between → the login 403); every failure mode (unknown/expired/wrong code/attempt cap) is a **uniform 401**, reasons live only in the `login.mfa_failure` audit event; **the attempt cap honours its configuration only since v3.12.2** — from v3.11.0 the store's `maxAttempts` property was shadowed inside its `suspendTransaction` lambda by Exposed's `R2dbcTransaction.maxAttempts` (the statement-retry count, default 3), so every challenge silently allowed exactly 3 guesses whatever `security.mfa.maxAttempts` said (stricter than the deployed default of 5, but a stricter operator setting would have been loosened); the property is `attemptCap` now, and `MfaChallengesTest`/`MfaLoginTest` pin caps that are not 3 — **name no class property after an `R2dbcTransaction` member if it is read inside a transaction lambda** (the innermost implicit receiver wins); verification and challenge update/removal are one atomic per-challenge transition, so concurrent requests cannot reuse a successful challenge or lose failed attempts. Challenges remain single-use. **Pending-challenge cap (checkup #36 Tier D)**: `issue` first prunes expired rows, then counts this account's remaining LIVE challenges — at `security.mfa.maxPendingChallenges` (default 5, `$MFA_MAX_PENDING_CHALLENGES`, range-checked `1..100` at boot like `maxAttempts`) a further correct-password login does not mint a new challenge or send an email; the route answers the uniform `429` (`TooManyRequestsException`, detail carrying the phrase "sign-in codes" — the SPA/tests distinguish it from the per-account lockout 429 by that phrase) and audits `login.mfa_throttled` (ip/email/userId) instead of `login.mfa_challenge`; a consumed or expired challenge frees its slot on the next issue. This bounds the email-flood surface a password holder could otherwise generate (only the per-IP login bucket limited it before, and rotating hosts sidestep that); the per-challenge TTL/attempt-cap guessing bound above is unchanged. **Mail-less deployments fail closed**: on `MAIL_TRANSPORT=disabled` an MFA-enabled login answers `503` (`login.mfa_unavailable`) — don't enable MFA flags on the k8s default `disabled` transport; the features PUT keeps working, so an admin can always flip a flag back. SPA: the Login card's second step (`PinInput`, `auth.mfa*` keys). Tests: `MfaChallengesTest` (DB-backed store, incl. real-concurrency race assertions) + `MfaLoginTest` (route matrix) + the bucket case in `RateLimitResponseTest` + `AuthStateAcrossInstancesTest` (a challenge issued via one instance is exchanged via another); `TestSeedState.restoreSeedAccounts` re-inserts the seed accounts' MFA rows (the pristine V52 state includes them — without that, seed logins answer challenges and half the suite breaks).

**Outbound email** (`infra/mail/`): `configureMail` (registered before the features) publishes `MailerKey` holding a `Mailer` or null; with a live transport it WARNs at startup when `mail.appUrl` (`$MAIL_APP_URL`) is blank — the emails would carry no sign-in/notification link (v3.6.2, `MailConfigTest`; the k8s manifest sets it to the Ingress host). `mail.transport` (`$MAIL_TRANSPORT`) selects `log` (dev default — the full message, **including generated passwords**, goes to the `ch.nokillswit.mail` logger; **production mode refuses to start on it**), `smtp` (Jakarta/Angus Mail over `mail.smtp.*` / `$SMTP_HOST` etc.; a blank host refuses startup in any mode; `mail.smtp.port` (`$SMTP_PORT`) must be an integer `1..65535`, checked whatever the transport — a malformed or out-of-range port refuses startup in any mode, v4.12.1, `SecurityConfigTest`), or `disabled` (the Docker image default via `ENV MAIL_TRANSPORT=disabled` — email features answer 503). The compose demo wires `smtp` → the bundled Mailpit (`http://localhost:8025`); k8s ships `disabled` with `SMTP_USER`/`SMTP_PASSWORD` read (optional) from `lettuce-secrets`. The **notification email mirror** (v2.3.0, see "Email mirror" in `.claude/docs/features/notifications.md`) rides the same transport: on `disabled` it silently sends nothing (no 503 — email is a side effect there), and under the dev `log` transport its messages land in the log too — they carry party names/titles/dates only, never secrets or feedback/goal content.

**Outbound Microsoft Teams (v4.5.0)** (`infra/teams/`): `configureTeams` (registered right after `configureMail`) publishes `TeamsMessengerKey`. `teams.transport` (`$TEAMS_TRANSPORT`, default `disabled` — also the image default, since the yaml default applies) selects `disabled`, `log` (development only — **production refuses it**, the mail precedent) or `botframework` (a single-tenant notification-only bot: client-credentials tokens from Entra, Graph user lookup, Bot Connector proactive messages — JDK `HttpClient`, no extra dependency). Fail-closed boot: an unknown transport, or `botframework` with a blank `TEAMS_TENANT_ID`/`TEAMS_APP_ID`/`TEAMS_APP_SECRET`, refuses to start in **any** mode, and **in production the three base URLs (`TEAMS_SERVICE_URL`/`TEAMS_LOGIN_BASE_URL`/`TEAMS_GRAPH_BASE_URL`) must equal Microsoft's public-cloud defaults exactly** — the client secret is posted to the login URL, so an override would exfiltrate it; the overrides exist only for the dev-mode `teams-stub`. No inbound endpoint exists (Lettuce never receives Teams traffic, so it never verifies Bot Framework tokens), no network call happens at boot, redirects are never followed, bodies are read up to 64 KiB, messages go out with `textFormat: "plain"` (so a display name cannot inject a markdown link into a colleague's DM), the Graph permission is the least-privileged `User.ReadBasic.All`, and the `ch.nokillswit.teams` logger records the failing step, status, recognized Teams sub-code and user id only — never the secret, a token or a response body. `TEAMS_APP_SECRET` is a secret (k8s: `lettuce-secrets`). See `.claude/docs/features/teams-notifications.md`.

**Swagger/OpenAPI gate** (`plugins/Http.kt`): `/openapi` (UI + spec) is served only in development mode, or when `http.exposeOpenApi` (`$HTTP_EXPOSE_OPENAPI`) is explicitly `"true"` — blank follows the mode, `"false"` hides it even in dev. Bearer auth cannot protect a browser-loaded UI (page loads carry no `Authorization` header), hence a gate rather than `authenticate {}`.

**Integration API keys (v3.0.0).** The read-only integration GraphQL API (`/integration/graphql` — see `.claude/docs/features/integration-api.md`) authenticates dedicated technical clients, never users: an admin-issued key `lettuce_int_` + 43 alphabet chars (~258 bits, `generateApiKey` in `auth/Passwords.kt`), shown exactly once in the create response and stored ONLY as its SHA-256 hex (`integration_clients.key_hash`, V71 — no bcrypt: high-entropy random keys need no work factor). Every bad-key shape answers the same 401 (reasons only in the `integration.auth_failed` audit event); revocation (`POST /api/v1/integration-clients/{id}/revoke`) is terminal and immediate. The endpoint is OFF by default (`integration.enabled`, `$INTEGRATION_ENABLED:false` — fail-closed: no routes registered) and per-key rate-limited (`integration.rateLimitPerMinute`, `$INTEGRATION_RATE_LIMIT_PER_MINUTE:120`, bucket keyed on the hashed bearer header); the compose demo enables it. Key management REST stays ADMIN-only including reads and works regardless of the flag. Tests: `IntegrationClientTest` + `IntegrationGraphQlTest`.

**Canonical email identity (v2.35.0, monkey-test MT-001).** Emails are folded to `trim().lowercase()` (`canonicalEmail` in `users/Validation.kt`) at EVERY entry point — user create/update, the CSV import, login, password reset, and `findWithIdByEmail` itself (defense-in-depth) — so one mailbox is one account: `ADMIN@x` can no longer create a second active account beside `admin@x`, and a padded/case-variant login matches (the login/reset throttles were already folding their keys; the asymmetry is gone). `V64` normalized pre-existing rows once; the V18 partial unique index stays byte-wise (all writes are canonical now). Tests: `EmailCanonicalizationTest`.

**Single-line identity fields (v2.35.0, MT-002).** User/team/template names and the unique id are trimmed of surrounding whitespace and reject ISO control characters up-front (`sanitizeSingleLine` in `infra/validation/Text.kt`; email control chars via `validateEmail`) — only NUL was caught before (DB-side 22021). Multi-line content fields (feedback, notes, descriptions, template content) deliberately keep their newlines.

**Request body size cap (v4.14.1)** (`plugins/BodyLimit.kt` + `plugins/ErrorHandling.kt` + `plugins/Http.kt`): before this release no request body was bounded — a JSON array of millions of ids was fully buffered and deserialized before any validator ran. Ktor 3.6's `ktor-server-body-limit` plugin (`RequestBodyLimit`, installed ONCE at the application level) has two hooks. (1) The **Content-Length precheck** runs in the application pipeline's `Validators` phase — after the MT-005 `Plugins`-phase intercept, BEFORE routing, `authenticate {}` and the `rateLimit {}` buckets — and throws `PayloadTooLargeException` when the declared length is over the cap, so nothing is read (with no principal yet, a pre-routing 413 carries no `Server-Timing` and spends no rate-limit token). (2) The **streaming wrapper** (`ApplicationReceivePipeline.Before`) wraps the request channel in a counting copy that closes it with the same exception once the running total passes the cap — bounding chunked/undeclared-length bodies WITHOUT buffering them. EVERY request body now travels through that copy (a small per-request cost; the v4.14.0 perf baseline predates it). **ONE knob:** `http.maxBodyBytes` (`HTTP_MAX_BODY_BYTES`, default **4 MiB**, every route), `requireConfigLong` 1 KiB..1 GiB, refusing startup in EVERY mode. The default is sized from the contract's real worst case, NOT from the typical form: a 1:1 meeting document (create/PUT) carries `points` + `decisions` + `actionItems`, each ≤100 items × ≤4000 chars with no total cap (`oneonones/OneOnOneRoutes.kt`) — 1.2M chars ≈ 1.2 MB of ASCII and ≈ 3.6 MB when every char is 3 UTF-8 bytes (a PLAN goal's 102 × 4000 is similar); `RequestBodyLimitTest` pins that body as NOT a 413. Everything else is far smaller (impact-log PUT ≈ 60 KiB, the CSV user import ≤ ~1.5 MiB once JSON-escaped, GraphQL a few KiB). Raising a per-route limit later means a per-call `bodyLimit { call -> … }` lambda, not a second install (an extra route-level install would run too and the stricter would win). **Two surfacing shapes, both → `413` problem+json** (`Request body must not exceed N bytes`): the precheck throws `PayloadTooLargeException` RAW (its own StatusPages handler); the streaming cut-off surfaces WRAPPED — ContentNegotiation catches every converter `Throwable` and rethrows `BadRequestException("Failed to convert request body…", cause)` with the `PayloadTooLargeException` as the cause, so the `BadRequestException` handler walks the cause chain FIRST (before the MT-007 converter-failure vocabulary), otherwise a chunked oversized body would answer a `400`. **Request DEcompression is off** (`install(Compression) { mode = CompressResponse }`): the default `Mode.All` inflated `Content-Encoding: gzip` request bodies with no decoded-size cap (a gzip bomb) in a phase AFTER the cap's wrapper, i.e. the cap would have counted compressed bytes; no client sends compressed request bodies (integration clients included — a gzip request is a `400` since v4.14.1), so a gzip body is simply malformed JSON and the cap counts wire bytes. **Ordering:** a declared oversized `Content-Length` is a `413` BEFORE `401` — the cheapest rejection, nothing read; the only per-path signal would be that a public route exists, and the cap value is public in the spec — no account/record information. A body-less operation handed an oversized declared `Content-Length` is `413`d too (accepted, undeclared there). **Every 413 carries a `Connection: close` response header, and the server deliberately does NOT force the close:** a conforming HTTP/1.1 client closes the connection itself after reading it. A server-side close (tried and removed in v4.14.1 — `writeAndFlush(EMPTY_BUFFER)` + `ChannelFutureListener.CLOSE`) is unsafe: closing while the client is still uploading (Netty answers `100 Continue` before the cap runs) makes the OS send a RST that can destroy the 413 itself ("connection reset by peer" instead of the problem body), and under pipelining it truncates an earlier in-flight response. Ktor's Netty engine closes only on the REQUEST's keep-alive and never drains a refused body, so a hostile client that ignores the header only parks its OWN connection: the unread remainder sits in kernel socket buffers (`RequestBodyHandler` pulls only as the consumer reads — no heap), bounded at the edge by nginx request buffering and timeouts. Pinned by `RawRequestBodyLimitTest` (a complete 413 + the header on a keep-alive request, and a client that keeps uploading ~1 MiB after the headers still reads the full status line and problem body). **Logging:** each rejection logs ONE line at DEBUG — not INFO: the rejection is anonymous and un-rate-limited, so an INFO line would be a free log sink — `Request body rejected as too large: <METHOD> <path> (Content-Length <n|chunked>, cap <n> bytes)`; the path is `sanitizeForLog`ed (every char outside printable ASCII 0x20..0x7E becomes `?`, capped at 200 chars — Netty passes ESC/DEL/CR/LF through a request line) and never carries the query string. `CallLogging` is not installed, so DEBUG is the only trace; deliberately NOT audited (a malformed-request class like the MT-005/MT-007 400s and the 405: no principal, no mutation). **Residuals, owned by the edge, not the app:** a slow drip UNDER the cap (slowloris) is bounded by nginx's `client_body_timeout` + request buffering, not by this plugin; and an `Expect: 100-continue` client gets Netty's `100 Continue` BEFORE the cap runs, so the "nothing is read" economy holds only for non-Expect clients (the cap still fires once body bytes arrive or the declared length is seen). Accepted edge: `POST /logout` reads its optional body through `runCatching { receiveNullable }`, which swallows a mid-stream cut-off (204, the access `jti` still revoked); the declared-length precheck still `413`s there. Netty itself rejects a request carrying BOTH `Transfer-Encoding: chunked` and `Content-Length` with a `400` (RFC 9112 smuggling guard) before any of this runs. The contract declares the shared `#/components/responses/PayloadTooLarge` on all 58 body-taking operations (Spectral `input-operation-declares-413` + `OpenApiSpecTest`; `/integration/graphql` is governed by its SDL, its 413 is transport-level). **Edge parity:** `k8s/templates/app-ingress.yaml` caps at `proxy-body-size: 4m` — nginx answers with its own HTML 413 first at the edge, so keep that annotation ≥ `http.maxBodyBytes`. Covered by `RequestBodyLimitTest` (declared/at-the-cap/ordering/chunked/default-wired/worst-case 1:1/`no-store`+`Connection: close`/sanitizer/gzip), `RawRequestBodyLimitTest` (real Netty over a raw socket: `Transfer-Encoding: chunked`, TE+CL, a header-only huge `Content-Length`, the keep-alive header, upload-after-headers, control bytes in the path), the oversized-query case in `IntegrationGraphQlTest`, and the knob cases in `SecurityConfigTest`. Negative or overflowing ids INSIDE bodies are the MT-007 `400` by construction — kotlinx-serialization's JSON decoder rejects them (pinned in `PayloadValidationTest`).

**CORS is off by default** (`plugins/Http.kt`): the plugin is installed only when `http.corsHosts` (`$CORS_ALLOWED_HOSTS`, comma-separated hosts) is non-empty. Production is single-origin (Ktor serves the SPA) and dev goes through the Vite proxy, so no cross-origin caller exists by default — `anyHost()` is gone. **Reverse proxy**: set `HTTP_BEHIND_PROXY=true` (config `http.behindProxy`) when TLS terminates at an ingress/proxy — it installs `XForwardedHeaders` so rate-limit buckets key on the real client IP and the HTTPS redirect sees the real scheme; the proxy must set (and strip client-supplied) `X-Forwarded-For`/`X-Forwarded-Proto`. Off by default because honoring those headers from direct clients lets them spoof both. **In Kubernetes the "direct client" is any pod** — the manifests therefore ship NetworkPolicies (v4.7.1): `k8s/templates/app-networkpolicy.yaml` admits the app's 8080 only from the ingress controller's pods, and `k8s/postgres-networkpolicy.yaml` admits PostgreSQL's 5432 only from the app pods (proven on OrbStack; needs an enforcing CNI). **The proxy contract (v3.6.2)**: the proxy must set `X-Forwarded-For`, `X-Forwarded-Proto` and `X-Forwarded-Host` and overwrite client-supplied values — the app reads ONLY those three (Ktor's default list also honoured `X-Forwarded-Server`/`-Protocol`/`-SSL`/`Front-End-Https`, which a proxy that sets just the canonical ones passes through untouched; `plugins/Http.kt` narrows the lists — and since v4.5.2 `X-Forwarded-Port` is not read either: nothing needs it, and a junk client value made Ktor's plugin throw a 500). `X-Forwarded-For` is read from the END, over EVERY header line (v4.5.2 — a proxy such as HAProxy with `option forwardedfor` APPENDS its own line instead of merging into the client's, and Ktor's plugin reads only the first line, so the client's own value would have keyed the rate limiter; `resolveForwardedForOrigin` folds the lines in order, pinned against real Netty by `RawForwardedForLinesTest`; XForwardedHeaders' own for-header list is left EMPTY so it never overwrites the result): `http.proxyHops` (`$HTTP_PROXY_HOPS`, default 1) = trusted proxies that APPEND to it — 1 trusts the value the last proxy wrote, N skips the N-1 addresses trusted proxies appended after the client's (the selection Ktor's `useLastProxy()`/`skipLastProxies()` made, reimplemented over the folded lines); fewer values than hops falls back to the last one. **The fold therefore requires the trusted proxy's value to be physically LAST** — true for replacing proxies (ingress-nginx), for nginx `$proxy_add_x_forwarded_for`, Go/Traefik, Envoy and HAProxy `option forwardedfor`; a proxy that merged its value into the FIRST of several client lines would leave a client value after it, so such a proxy must strip client-supplied X-Forwarded-For (the contract's "overwrite client-supplied values" covers it); Ktor's default was `useFirstProxy`, i.e. whatever the client sent when a proxy appends rather than replaces (ingress-nginx's default REPLACES, so 1 is right there; only count appending hops). `ForwardedHeadersTest` pins the bucket keying, `ProductionHttpTest` (real Netty) pins that the HTTPS-redirect target is the `X-Forwarded-Host` name and that `X-Forwarded-Server` cannot set it. The reference front door is `k8s/templates/app-ingress.yaml` (ingress-nginx: replaces XFF, 308s plain HTTP at the edge, and OVERWRITES `Strict-Transport-Security` — HSTS policy lives in the controller's configmap, the app's header matters pod-direct only). **Community ingress-nginx was retired in March 2026** (https://kubernetes.io/blog/2026/01/29/ingress-nginx-statement/, unpatched thereafter) — that manifest is the local-proof reference only; a production front door must migrate to a maintained controller or the Gateway API, re-verifying this whole proxy contract against it. Health checks over plain HTTP in production mode must send `X-Forwarded-Proto: https` too (the k8s probes do, v3.6.1) — otherwise they get the HTTPS-redirect 301, which the kubelet follows into a refused `:443`. The dedicated probe endpoints are `/healthz` (liveness, no DB) and `/readyz` (readiness, a DB round-trip → 503 when the DB is down) in `plugins/Health.kt` — unauthenticated and outside `/api/`, so the OpenAPI conformance layer ignores them. The security response headers (`plugins/SecurityHeaders.kt`) are appended in the pipeline's **Setup** phase so that redirect carries them as well: appending after the Plugins-phase redirect had committed the response threw and logged an ERROR stack trace per redirected request (`ProductionHttpTest` pins both).

**Response caching (v4.14.0, API-CACHE-001/002)** (`plugins/Http.kt` + `plugins/Routing.kt` + `plugins/RequestPaths.kt`): three classes, no overlap. **Static SPA files** (the `staticFiles` route): files directly under `assets/` (Vite's content-hashed chunks/CSS — the name IS the version) answer `Cache-Control: public, max-age=31536000, immutable` — so nothing unhashed may ever live under `web/public/assets/`; `index.html` (version stamp + per-deploy chunk names), the SPA fallback and the `web/public` root files answer `no-cache`, revalidated by a content-hash **ETag only** (`StrongSha256`, stable across image rebuilds), `304` via `ConditionalHeaders`. **No `Last-Modified` is ever sent and `If-Modified-Since` never decides**: Ktor's `LocalFileContent` always adds an mtime version and ConditionalHeaders answers `304` if ANY version matches, so after a rollback to an older image (older build mtimes) a browser's newer `If-None-Match` + `If-Modified-Since` would pin the stale shell — and a date would disclose the build time. The route-scoped `EtagOnlyValidators` plugin (before ConditionalHeaders) keeps only `EntityTagVersion`s and drops every version when `If-None-Match`/`If-Match` is unparseable (`"x";q=0.5`, `a b` — served as a normal `200`, never a `500`). ConditionalHeaders is installed on the static route ONLY, so no API response can ever acquire `304`/`412` semantics from an `ETag`/`Last-Modified` header it writes. The route also refuses dotfiles (`/.env` → `403`; Ktor serves them by default). A `304` keeps its `Cache-Control` and the CSP/nosniff/HSTS headers. **The dynamic surface — `/api/**` and the integration GraphQL endpoint + schema (`/integration/**`)**: `Cache-Control: no-store` on every response, exactly once (the `CachingHeaders` rule skips a response that already has a `Cache-Control`, because StatusPages re-responds a 405/429 through the hook a second time) — React Query owns client caching, and the SPA sends `Authorization` so browsers never cached these anyway; this is why API `GET`s carry no validators (the register's remaining API-CACHE-001 row). Every path-policy test goes through `ApplicationCall.isApiPath()`/`isApiSurfacePath()` (`plugins/RequestPaths.kt`) — the router skips empty segments and percent-decodes, so `//api/v1/users` reaches the handler and a raw `startsWith("/api/")` would miss it (the MT-005 negative-id intercept shares the helper). The SPA fallback is path-blind (an unknown `/api/…` path still gets `index.html`, as before) but carries only the `no-store`, never a `no-cache`. **Everything else** (`/openapi`, probes, redirects) gets no `Cache-Control` from this policy. Accepted: Compression keeps the strong content ETag across encodings (Ktor's default; `Vary: Accept-Encoding` is set, nothing serves range requests/`PartialContent`). Covered by `StaticContentTest`.

CSRF install is gated behind `security.csrf.enabled` (default **`false`** in `application.yaml`, env-overridable via `SECURITY_CSRF_ENABLED`; the gate is `== true` since v3.6.2 — a missing property can no longer install the localhost-only allow-list); the configured `originMatchesHost()` + `allowOrigin("http://localhost:8080")` + `checkHeader("X-CSRF-Token")` combo is unsatisfiable from both the Ktor test client and the dev SPA on `:5173`, and CSRF protection is anyway moot for this app's bearer-JWT auth model — browsers do not auto-attach `Authorization` headers, so cross-site forms cannot forge an authenticated request. Re-enable only if you move to cookie-based session auth and fix the allow-list accordingly.

**Default admin & demo seed.** Migration `V6__seed_admin.sql` inserts a single bootstrap administrator on first boot: `admin@lettuce.local` / `changeme` (holds the `ADMIN` role — seeded via the old `users.role` column, moved into `user_roles` by `V27`), idempotent via `ON CONFLICT (email) DO NOTHING`. `V9__seed_demo_users_and_teams.sql` additionally seeds a demo org (teams AAA/BBB/CCC with `aaa-one@…`, `manager-aaa@…`, etc.) so the dashboard lists have data — every demo user has no additional roles and logs in with `changeme` (reusing V6's bcrypt hash). The migrations are kept **unchanged** (dev + e2e depend on them; checksums must not change) — production neutralizes them at startup via the bootstrap above.

**The HR demo account (v4.1.0) is a bootstrap seed, not a migration.** `configureBootstrap` (`infra/db/Bootstrap.kt`) seeds `hr@lettuce.local` / `changeme` — "HR Auditor", holding the `HR` role only (no ADMIN, no team, no reports: the relationship-less auditor) — **in development mode only**, and only while the database still looks like a dev database (at least one V9 demo account active — every production-mode boot soft-deletes them, so a database that has ever booted in production never receives it, even from a dev-mode `:server:run` mis-pointed at it; `UserService.anyActiveWithEmails`), and only when no row for that email exists yet in any state (active or soft-deleted), so an account a developer deliberately deleted is never resurrected on a later restart. Two instances seeding one fresh dev database at once tolerate the unique-violation race (the loser treats it as already seeded). It is never inserted by a migration, so — unlike the V9 accounts above — a production database never receives it through Flyway, and a real account at that address is never endangered by a blind by-email purge. Outside development mode, any row at that email is soft-deleted **only while it still carries the well-known seed password hash** (`UserService.softDeleteByEmailsWithPasswordHash`) — this neutralizes a dev database later booted in production, while a REAL pre-existing account at that address with its own password is left completely untouched. The pre-existing fail-closed `countActiveWithPasswordHash` check still runs last, after both purges, as the backstop. Unlike V6/V9, this seed's idempotence and its production-mode removal both key on data, not on a one-time migration step — see `BootstrapTest`. **Kubernetes secrets** live in the `lettuce-secrets` Secret (`k8s/templates/secret.yaml` is a placeholder template — create the real one out-of-band with `kubectl create secret generic`; both deployments consume it via `secretKeyRef`). Both pods run non-root with a read-only root filesystem, no capabilities and the runtime-default seccomp profile (app uid 1000 since v3.8.3, PostgreSQL uid 70 since v3.11.0 — see the manifests' comments for the volume-ownership caveat).

### Config range checks

The numeric-knob boot validation summarized in `.claude/docs/security.md`, in full.

**Auth-security config ranges** (`auth/AuthRoutes.kt`, checkup #36/C5): `security.lockout.threshold`/`durationSeconds`, `security.mfa.codeTtlSeconds`/`maxAttempts`/`maxPendingChallenges`, and `security.passwordReset.minIntervalSeconds` are range-checked at boot — a malformed or out-of-range value (e.g. `LOGIN_LOCKOUT_DURATION_SECONDS=0`, which would never lock while `login.lockout` keeps auditing a trip; or `threshold=0`, locking on the first attempt) is a config error, not a runtime concern, so it **refuses to start in EVERY mode** (`requireConfigInt`/`requireConfigLong` in `infra/config/Config.kt` — shared since checkup #37 C2 with the `postgres.pool.*` bounds, see "Connection pool" in `.claude/docs/persistence.md`; the `security.encryption.key` malformed-key precedent in `security.md`'s fail-closed list). Thresholds/durations/TTLs/intervals must be `>= 1`, and the three seconds-valued windows (lockout duration, password-reset interval, MFA code TTL) at most 30 days (`MAX_DURATION_SECONDS`, v4.5.2 — each is multiplied into milliseconds, and an unbounded value near `Long.MAX_VALUE` overflowed negative and silently disabled the window); the MFA attempt cap and the MFA max-pending-challenges cap must each be `1..100`. **Since v4.5.2 the same boot check covers every remaining numeric knob that was a bare parse**: `jwt.accessExpiresInSeconds` `1..86400` and `jwt.refreshExpiresInSeconds` `1..MAX_DURATION_SECONDS` (an overflow made tokens effectively never expire), `notifications.retentionDays` `0..3650` (0 disables the purge; a negative value put the cutoff in the future, so the purge hard-deleted every seen/user-deleted notification), `notifications.purgeIntervalSeconds`/`feedbacks.expirySweepIntervalSeconds` `0..86400`, and — through `optionalConfigInt`, since blank means "follow the mode"/"default" — `security.rateLimit.loginPerMinute`/`integration.rateLimitPerMinute`/`sharing.rateLimitPerMinute`/`sharing.batchRateLimitPerMinute` `1..100000` (0 or less answered every request 429). `MAX_DURATION_SECONDS` lives in `infra/config/Config.kt`. Covered by `SecurityConfigTest`.
