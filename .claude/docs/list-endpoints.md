### List endpoint conventions

`GET /api/v1/users`, `GET /api/v1/teams`, `GET /api/v1/teams/members`, `GET /api/v1/feedbacks`, `GET /api/v1/one-on-ones`, `GET /api/v1/goals`, `GET /api/v1/team-kpis`, `GET /api/v1/performance-reviews`, `GET /api/v1/days-off`, `GET /api/v1/templates`, `GET /api/v1/notifications`, and `GET /api/v1/alerts` are list endpoints; every list endpoint follows the standard list rules (owned by `api-guidelines/API-GUIDELINES.md`, summarized below). The OpenAPI spec is the contract; document the query params for each list endpoint there. (`teams/members` is caller-relative via `view=member|managed|managers`; `managed` additionally accepts the strict-boolean `includeIndirect` to widen from direct reports to the transitive management chain — same param and semantics as `GET /api/v1/feedbacks?view=team`, `400` with any other view. `managers` and `managed` items are additionally enriched **route-side** with per-person dashboard stats, direction switched per view — latest directional 1:1 + its open action items via `OneOnOneService.latestMeetingStats` / `latestMeetingStatsBySubordinate`, last SENT feedback via `FeedbackService.lastProvidedAt` (received-scoped: only feedback the caller can see) / `lastProvidedTo` (provider-side: never visibility-filtered) — SENT moment from `feedback_events`, pre-V15 rows fall back to `lastModified` — and the directional `activeGoalCount` via `GoalService.activeGoalCountsByManager` / `activeGoalCountsBySubordinate` (ACTIVE goals of the pair only — `0` when none, no visibility question since both parties always see an ACTIVE goal) — plus, `managed` rows **only**, the caller's latest authored performance review (`PerformanceReviewService.latestReviewsBySubordinate` — latest by period, ANY status incl. DRAFT since the caller wrote it; four nullable `lastReview*` fields, v1.34.0); `managed` rows are enriched regardless of `includeIndirect`; `member` items instead carry both peer feedback directions at once — `lastFeedbackGivenAt` via `lastProvidedTo`, `lastFeedbackReceivedAt` via `lastProvidedAt` — with no 1:1 stat. **Every** view's rows additionally carry the person's resolved career-profile triple via `UserService.careerProfilesByUserIds` — view-independent, see "Career profile" in `.claude/docs/features/dictionaries.md`. **Days-off card stats (v1.44.0)**: `managed` rows carry `nextVacationStart` (`DaysOffService.nextAcceptedVacationsByUserIds` — accepted-only, ongoing counts, pending never shows) **and** `daysOffRemaining` (`remainingByUserIds`, current year); `member` rows carry `nextVacationStart` only (teammates see accepted absences by calendar parity, never budgets); `managers` rows carry neither — the card omits rather than half-answers.)

**The generic list rules are owned by `api-guidelines/API-GUIDELINES.md`** (see "API guidelines" in the root CLAUDE.md) — summary: offset pagination `page`/`pageSize` (1-based, default 20, max 100; out-of-range → `400`) in the `{items, page, pageSize, total}` envelope, `total` after filters before pagination with count + page rows in the same `suspendTransaction` (cursor paging is a documented per-endpoint opt-in) [API-LIST-001/002, API-STRUCT-004]; `sort=field`/`-field`, comma-separated multi-field, per-endpoint whitelist → `400`, `id` asc always appended as tiebreaker, default `id` asc documented [API-LIST-003]; whitelisted equality filters on the field's own name plus `field[gte|gt|lte|lt]` bracket operators only where needed, strict `true`/`false` booleans, enums by string name, repeated key reserved for `IN` [API-LIST-004]; `q` free-text first, per-column substring only when a UI requires it [API-LIST-005]; camelCase params, reusable `Page`/`PageSize`/`Sort` under `#/components/parameters` `$ref`'d from each list path, one `*Page` envelope schema per resource, sortable/filterable whitelists documented per path [API-NAME-001..004].

**Project-state notes** (implementation status, not rules — update when they change): repeated-key `IN` is implemented by **no endpoint yet** (the shared parser `optionalString` in `infra/paging/QueryParams.kt` reads only the first value of a repeated key — implement per-endpoint when a UI needs it); `q` is implemented by **no endpoint yet** (current UIs use per-column filters; add the reusable `Q` parameter with the first endpoint that needs it); per-column substring today: `GET /api/v1/users` uses `name` and `email` this way.

**Implementation.**

- The shared helper lives at `infra/paging/Paging.kt`: `ApplicationCall.parsePaging(...)` parses `page`/`pageSize`/`sort` from the query string and validates against per-endpoint whitelists into a `PageRequest`; `Query.applyPaging(req, columns)` applies `.limit(...).offset(...)` + `.orderBy(...)` to an Exposed `Query`. Validation failures throw a typed exception that `StatusPages` maps to `400` + `ProblemDetail`. New list endpoints reuse these rather than re-parsing params.
- **Every per-column substring filter is case- AND accent-insensitive** (v1.47.0): use `column.containsNormalized(value)` from `infra/db/Sql.kt` — it renders `LOWER(public.unaccent(col)) LIKE LOWER(public.unaccent(?))` (extension enabled in `V43`), so "zolw" matches "Żółw" and vice versa. Never hand-roll `lowerCase() like containsPattern(...)` (the pattern builder is `internal` for exactly that reason), and keep unaccent-before-LOWER — the reverse breaks uppercase-diacritic input under the C-locale database. The SPA mirrors the rule client-side: Mantine searchable Select/MultiSelect filtering goes through the theme-level `foldedOptionsFilter` (`web/src/utils/text.ts`, see `web/CLAUDE.md`).
