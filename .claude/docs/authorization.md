### Authorization model

Layered RBAC. Implemented in the `server/src/main/kotlin/authz/` package.

- **Global roles are an additive set** (`user_roles` join table, `V27` — replaced the single V5 `users.role` column): every user is implicitly a regular user (USER is never stored or transmitted), and additional roles — `ADMIN` and `HR` (`UserRole` in `users/User.kt`; a future role is just a new enum value) — only ever ADD privileges. The API carries them as a `roles` array (`[]` = regular user); `isAdmin` (`authz/Guards.kt`) = `ADMIN ∈ roles`. **ADMIN is the management role** (narrowed in v1.26.0): write access to **users, teams, templates, and alerts** (plus the reads those screens need — `requireAdmin`, `requireSelfOrAdmin`, the admin branch of `requireUserRead`, `requireTeamManagerOrAdmin`, `requireCanReassignManager`, `requireCanAssignRoles`) and **nothing else** — no special read or write access to feedbacks, 1:1 meetings, goals, or other users' notifications; there an admin is an ordinary user (e.g. a non-party admin still reads `PUBLIC`+`SENT` feedback, because anyone does). An admin who is a party (provider, manager, recipient…) keeps that ordinary-party access. New users start with no additional roles; only an `ADMIN` may change a user's roles set via the API (`requireCanAssignRoles` — resubmitting the unchanged set is not a change). The users list dropped `role` from the sortable whitelist (a set has no order); its `role` query param means **has-role** (`ADMIN`/`HR`).
- **HR is the read-only auditor role** (v1.25.0; sole auditor since v1.26.0): full read access — every user, feedback, 1:1, and goal, drafts included, content never blanked — with write access exactly regular-user (no management rights; notifications stay recipient-only and alerts management stays ADMIN-only, reads included). Implemented as `isHr()` (`authz/Guards.kt`) plus a `grantHrRead` branch in the three `require*ReadAllowingManager` guards (placed BEFORE the chain walk — HR needs no DB hit, and for goals sees DRAFTs unlike chain managers) and `requireUserRead` at `GET /users/{id}` (the reads-only sibling of `requireSelfOrAdmin`, which keeps guarding the writes). **Every HR-privileged read is audit-logged**: `hr.read` (resource/resourceId/byUserId, emitted only when the ordinary rules missed) and `hr.list` (emitted on every auditor-list use). The **auditor list view `view=user` + required `userId`** exists on the feedback/1:1/goal lists for HR callers only (`requireAuditListAccess`; anyone else — ADMIN included — gets 403; the `counterpartId` validation precedent): rows the target is a party to, at every status, previews never redacted; ordinary sort/filter params compose on top. An admin who needs to audit holds both roles. SPA: `canAudit()` (`api/session.ts`), the **Audit section on `/users/:id/details`** linking the three drill-downs with `?mode=audit` (`from=details` origin; non-auditors silently fall back to the normal views), tables' `VIEW_CONFIG` gained the read-only `user` view. Tests: `HrRoleTest` (routes incl. the audit trail), `GuardsTest` HR section, `FeedbackTable.user.test.tsx` + audit-mode cases in the drill-down page tests, `e2e/tests/hr.spec.ts`.
- **Login** issues a **pair** of JWTs, both carrying `email`, `userId`, a `roles` array claim, and a `typ` claim (`"access"` / `"refresh"`), minted by `auth/Tokens.kt` (`JwtConfig.issueAccessToken` / `issueRefreshToken`). The short-lived **access** token (`jwt.accessExpiresInSeconds`, default 900) is the API bearer; the longer-lived **refresh** token (`jwt.refreshExpiresInSeconds`, default 3600) is exchanged at `POST /api/v1/refresh` for a fresh pair. `LoginResponse` (also the `/refresh` response) exposes `token`/`expiresAt`, `refreshToken`/`refreshExpiresAt`, `userId`, and `roles`. The `jwt {}` verifier in `plugins/Security.kt` additionally requires `typ == "access"`, so a refresh token cannot authenticate an API call.
- **Session auto-extension (pure sliding).** `/api/v1/refresh` (rate-limited, no `authenticate` — the access token may be expired) verifies the refresh token's signature/issuer/audience/`typ`/non-revocation, then does **one** `userService.read(userId)` to confirm the user is still active and pick up their current roles, **rejects tokens whose `iat` predates `users.password_changed_at`** (compared at second granularity — JWT `iat` is second-precision; a missing `iat` counts as epoch 0), and mints a fresh pair. Superseded tokens are **not** rotated out — they stay valid until their own expiry (no blocklist write on refresh); only an idle session (no refresh within the refresh TTL) ends. `/api/v1/logout` revokes the access `jti` (from the principal) **and**, if the client sends the refresh token in the body (`LogoutRequest`), that token's `jti` too. Frontend: `web/src/api/http.ts` `authedFetch` silently refreshes (single-flighted via a module-level in-flight promise) and retries once on a `401`; on refresh failure it clears the session and signs out.
- **Guards** in `authz/Guards.kt` are plain `suspend fun` calls used at the top of each route handler — there is no Ktor plugin or DSL. Each route reads `call.caller()` (which parses the JWT claims into a `CallerPrincipal`) and then invokes the relevant guard.
- **Resource rules**:
  - `POST /api/v1/users`, `DELETE /api/v1/users/{id}` → ADMIN only. Create accepts `sendEmail: true` to mail the new user their credentials (same welcome email as the import, rendered in the request's `language` — default English; `emailSent` in the `UserCreateResponse` reports the outcome, a delivery failure keeps the account; `503` up-front on a mail-less deployment).
  - `POST /api/v1/users/import` → ADMIN only. Mass CSV import (`name,email` per line, split on the LAST comma so names may contain commas; an optional literal header and blank lines are skipped): every row imports independently with no additional roles and a server-generated password returned once per row (statuses `CREATED`/`DUPLICATE`/`PARSE_ERROR`/`EMAIL_FAILED`/`ERROR`); duplicates are classified via the 23505 cause-chain check (`isUniqueViolation`, internal in `plugins/ErrorHandling.kt`). `sendEmails: true` sends each new user a welcome email (`users/WelcomeEmail.kt`; imported users default to English, so it renders EN) — rejected `503` up-front on a mail-less deployment; a per-row delivery failure keeps the account (`EMAIL_FAILED`, password still in the row). Caps: 200 rows / 256 KiB → `400`. SPA: Users → "Mass import" → `/users/import`. A demo file exercising every status lives at `samples/user-import-demo.csv`. Tests: `UserImportTest` + `UserImportParserTest` (the pure parser in `users/UserImport.kt`).

Ordering violations (append not-after-latest, correction leaving the neighbor window), the adjacent-sameness rule (v2.15.2 — a position identical to its neighbor's triple), and a correction pushing a deactivation-closed final row past its stored end (v2.17.0) are 409. A caller who manages nobody gets an empty list (no 403 — the days-off budgets idiom); **no role widening** — HR and ADMIN see exactly their own subordinates, so the endpoint discloses nothing the open users list and the open career-positions GET don't already (since v2.17.0 the full position history + the `deactivated` flag per subordinate — both already readable via those routes — plus the org-wide `earliestStartDate`, a bare date). See "Career progression" in `.claude/docs/features/dictionaries.md`.
  - `POST /api/v1/users/{id}/deactivate`, `POST /api/v1/users/{id}/activate` → ADMIN only; **never one's own account** (self-deactivate → 403, checked before the read so it stays uniform); same-state repeat → 409 (the transition rule); soft-deleted target → 404. **Reversible deactivation (V44)** is orthogonal to the soft-delete: a deactivated user cannot log in (**403 "Account is deactivated"**, checked only AFTER the password verifies — no enumeration oracle; wrong password stays the uniform 401, and the lockout counter deliberately doesn't move on the 403 path), `/refresh` rejects with 401 (`refresh.rejected` reason `deactivated`), self-service password reset silently skips them, and they **cannot be NEWLY assigned** — team member/manager (delta-validated: only newly added members / a changed manager, so a team containing a since-deactivated user stays editable and the member-add re-PUT stays idempotent), goal/1:1/review `subordinateId`, feedback party, or a NEW career position (v2.17.0) — all `400` via `UserService.requireNoDeactivatedUsers` (placed after the authz guards; 403 wins over 400). **Deactivation also closes the career timeline (v2.17.0)**: the final active career position gets today stamped as its stored end date (`closeFinalPosition`, a no-op without positions; reactivation reopens it via `reopenFinalPosition`) — the ONE deliberate exception to "deactivation mutates nothing but the flag". **Everything else is untouched by design**: their historical data reads under exactly the same rights as an active user's (no `*Deactivated` flags on other features' DTOs — the pyramid's `CareerPyramidItem.deactivated` is the one exception, needed for its only-while-positioned drop rule), the email stays reserved (the V18 partial index ignores the column), and the UI surfaces are the admin `/users` list (Inactive badge + `deactivated` strict-boolean filter) plus, since v2.17.0, the Team pyramid's as-of behavior (a deactivated person disappears past their end date). `UserResponse.deactivated` carries the state; Tests: `UserDeactivationTest` (matrix + assignment blocks + the timeline-closing case), plus the login/lockout/refresh/reset cases in `LoginTest`/`LoginLockoutTest`/`RefreshTest`/`PasswordResetTest`.

Gated: the seven feature route files (pulse since v2.0.0) + the two registries; **deliberately ungated**: users, teams (incl. the `/teams/members` enrichment stats), templates, dictionaries, notifications access (but its list/total EXCLUDE types of the recipient's disabled features — see `.claude/docs/features/notifications.md`), alerts, auth, and `GET /dashboard/summary` (the SPA hides tiles).   - `GET /api/v1/dictionaries/{dictionary}` → any authenticated user; `PUT /api/v1/dictionaries/{dictionary}` → ADMIN only (`requireAdmin`), guarded **before** slug resolution so a non-admin gets a uniform 403 whether or not the slug exists. See "Dictionaries" in `.claude/docs/features/dictionaries.md`.
  - `GET/POST/DELETE /api/v1/notifications/*` → the notification's `recipient_id` only (via `requireNotificationRecipient`) — recipient-only for everyone, ADMIN included (the bypass was removed in v1.26.0). Notifications are never created through the API — see "Notifications" in `.claude/docs/features/notifications.md`.
  - `GET/POST/PUT/DELETE /api/v1/alerts` and `/api/v1/alerts/{id}` → ADMIN only (`requireAdmin`), **reads included** (unlike templates — non-admins have no use for the management view). `GET /api/v1/alerts/visible` → any authenticated user. See "Alerts" in `.claude/docs/features/alerts.md`.
- **Existence disclosure (403 vs 404) — deliberate policy (API-ERR-006)**: `GET /users/{id}` guards **before** reading, so a non-admin probe gets a uniform 403 whether or not the id exists; feedback and notification GETs read **before** guarding (missing → 404, existing-but-forbidden → 403), so an id probe can learn that a record exists (never its content or parties). Accepted knowingly: ids are sequential (existence is no secret) and the feedback read matrix already deliberately reveals existence-without-content to requesters. New resources should pick one of these two idioms consciously rather than mixing them.
- **Exceptions**: `UnauthorizedException` (→ 401) and `ForbiddenException` (→ 403) are mapped in `plugins/ErrorHandling.kt`. **All error bodies are RFC 7807 `application/problem+json` (API-ERR-001/002)** (`ProblemDetail{type,title,status,detail,instance}`) — emit them via the `ApplicationCall.respondProblem(status, detail)` helper (it uses an explicit `TextContent` so ContentNegotiation does not relabel the media type as `application/json`). `StatusPages` routes `BadRequestException`→400, `UnauthorizedException`→401, `ForbiddenException`→403, `TooManyRequestsException`→429 (the login lockout — thrown, never `respondProblem`ed directly, see below), unique-violation→409, and a catch-all `Throwable`→500 (logged) through that helper; a `status(TooManyRequests)` handler additionally gives the per-IP `RateLimit` plugin's bodiless 429 a generic problem body — **that handler rewrites any non-StatusPages 429**, which is why caller-specific 429s must go through the exception (handled calls are marked and skipped). The JWT `challenge` in `plugins/Security.kt` also calls `respondProblem` (it runs outside `StatusPages`), and inline `404`s in routes use `respondProblem(NotFound, …)`. Test HTTP clients must register the `application/problem+json` content type (`json(contentType = ContentType.parse("application/problem+json"))`) to decode error bodies with `body<ProblemDetail>()`.
- **Tests**: `server/src/test/kotlin/AuthorizationTest.kt` covers the 401/403 paths and the full `FeedbackVisibility` matrix. The shared `TestUsers.seed` helper defaults to `roles = setOf(UserRole.ADMIN)` so older tests keep working without modification; pass `roles = emptySet()` when you need a non-privileged caller.
