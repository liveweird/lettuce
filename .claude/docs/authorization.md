### Authorization model

Layered RBAC. Implemented in the `server/src/main/kotlin/authz/` package.

- **Global roles are an additive set** (`user_roles` join table, `V27` — replaced the single V5 `users.role` column): every user is implicitly a regular user (USER is never stored or transmitted), and additional roles — `ADMIN` and `HR` (`UserRole` in `users/User.kt`; a future role is just a new enum value) — only ever ADD privileges. The API carries them as a `roles` array (`[]` = regular user); `isAdmin` (`authz/Guards.kt`) = `ADMIN ∈ roles`. **ADMIN is the management role** (narrowed in v1.26.0): write access to **users, teams, templates, and alerts** (plus the reads those screens need — `requireAdmin`, `requireSelfOrAdmin`, the admin branch of `requireUserRead`, `requireCanAssignRoles`) and **nothing else** — no special read or write access to feedbacks, 1:1 meetings, goals, or other users' notifications; there an admin is an ordinary user (e.g. a non-party admin still reads `PUBLIC`+`SENT` feedback, because anyone does). An admin who is a party (provider, manager, recipient…) keeps that ordinary-party access. New users start with no additional roles; only an `ADMIN` may change a user's roles set via the API (`requireCanAssignRoles` — resubmitting the unchanged set is not a change). The users list dropped `role` from the sortable whitelist (a set has no order); its `role` query param means **has-role** (`ADMIN`/`HR`).
- **HR is the read-only auditor role** (v1.25.0; sole auditor since v1.26.0): full read access — every user, feedback, 1:1, goal, team KPI, performance review, impact-log entry (v2.36.0), succession plan (v2.42.0), and days-off entry/correction (plus the pulse auditor reads — see the pulse bullet), drafts included, content never blanked — with write access exactly regular-user (no management rights; notifications stay recipient-only and alerts management stays ADMIN-only, reads included). Implemented as `isHr()` (`authz/Guards.kt`) plus a `grantHrRead` branch in every widened read guard (eleven call sites in `authz/Guards.kt`: the four `require*ReadAllowingManager` guards for feedback/1:1/goal/review, `requireTeamKpiReadAllowingChain`, `requireDaysOffRead`, `requireDaysOffCorrectionsRead`, `requireCareerPositionRead` (v2.25.0), `requireImpactEntryRead` (v2.36.0), `requireSuccessionPlanRead` (v2.42.0) — each placed BEFORE the chain walk, so HR needs no DB hit, and for goals sees DRAFTs unlike chain managers — and `requireUserRead` at `GET /users/{id}`, the reads-only sibling of `requireSelfOrAdmin`, which keeps guarding the writes). **Every HR-privileged read is audit-logged**: `hr.read` (resource/resourceId/byUserId, emitted only when the ordinary rules missed) and `hr.list` (emitted on every auditor-list use). The **auditor list view `view=user` + required `userId`** exists on the feedback/1:1/goal/review/days-off/impact-log/succession-plan lists, and **`view=all` auditor view (org-wide) exists on team-kpis and, since v4.3.0, performance-reviews** (`requireAuditScopeListAccess`, scope key `periodId` — the team-KPI `teamId` sibling), and **`view=user` auditor view (per-person budgets) exists on days-off/budgets**, and **`scope=org` auditor calendar exists on days-off/calendar** (v3.25.0), for HR callers only (`requireAuditListAccess` or `requireAdmin`; anyone else — ADMIN included — gets 403; the `counterpartId` validation precedent): rows at every status, previews never redacted; ordinary sort/filter params compose on top. An admin who needs to audit holds both roles. SPA: `canAudit()` (`api/session.ts`), the **Audit section on `/users/:id/details`** linking the per-area drill-downs (feedbacks/1:1s/goals/reviews/days-off/impact-log/succession-plans) with `?mode=audit` (`from=details` origin; non-auditors silently fall back to the normal views), tables' `VIEW_CONFIG` gained the read-only `user` view. **The development-mode bootstrap seeds a relationship-less auditor for this role** (`hr@lettuce.local` / `changeme`, v4.1.0 — HR only, no ADMIN, no team, no reports; never seeded outside development, and any row at that address is soft-deleted at production boot only while it still carries the well-known seed password, see "Default admin & demo seed" in `.claude/docs/security-details.md`). Tests: `HrRoleTest` (routes incl. the audit trail), `GuardsTest` HR section, `FeedbackTable.user.test.tsx` + audit-mode cases in the drill-down page tests, `e2e/tests/hr.spec.ts`.
- **Login** issues a **pair** of JWTs, both carrying `email`, `userId`, a `roles` array claim, and a `typ` claim (`"access"` / `"refresh"`), minted by `auth/Tokens.kt` (`JwtConfig.issueAccessToken` / `issueRefreshToken`). The short-lived **access** token (`jwt.accessExpiresInSeconds`, default 900) is the API bearer; the longer-lived **refresh** token (`jwt.refreshExpiresInSeconds`, default 3600) is exchanged at `POST /api/v1/refresh` for a fresh pair. `LoginResponse` (also the `/refresh` response) exposes `token`/`expiresAt`, `refreshToken`/`refreshExpiresAt`, `userId`, and `roles`. The `jwt {}` verifier in `plugins/Security.kt` additionally requires `typ == "access"`, so a refresh token cannot authenticate an API call, and — since v4.5.2 — a `jti` and an `exp` claim: a token without a `jti` could never be blocklisted, one without an `exp` would never expire (java-jwt checks expiry only when the claim is present), and Lettuce mints neither (a 401, decided before any database lookup).
- **Session auto-extension (pure sliding).** `/api/v1/refresh` (rate-limited, no `authenticate` — the access token may be expired) verifies the refresh token's signature/issuer/audience/`typ`/non-revocation (and, since v4.5.2, that it carries a `jti` and an `exp` — otherwise `refresh.rejected` reason `malformed`), then does **one** `userService.read(userId)` to confirm the user is still active and pick up their current roles, **rejects tokens whose `iat` predates `users.password_changed_at`** (compared at second granularity — JWT `iat` is second-precision; a missing `iat` counts as epoch 0), and mints a fresh pair. Superseded tokens are **not** rotated out — they stay valid until their own expiry (no blocklist write on refresh); only an idle session (no refresh within the refresh TTL) ends. `/api/v1/logout` revokes the access `jti` (from the principal) **and**, if the client sends the refresh token in the body (`LogoutRequest`), that token's `jti` too. Frontend: `web/src/api/http.ts` `authedFetch` silently refreshes (single-flighted per captured session) and retries once on a `401`; only a definitive refresh rejection ends the current session, while transient failures preserve it. Session transitions are centralized in `web/src/api/session.ts`: stale asynchronous work cannot restore credentials or clear a newer session. Logout clears local state before best-effort revocation; login/logout/expiry and cross-tab session replacements clear query/mutation caches before auth notification and reset authenticated component state (see `web/CLAUDE.md`, "Session isolation").
- **Guards** in `authz/Guards.kt` are plain `suspend fun` calls used at the top of each route handler — there is no Ktor plugin or DSL. Each route reads `call.caller()` (which parses the JWT claims into a `CallerPrincipal`) and then invokes the relevant guard. **Since v4.8.0 a shareable feature's READ preamble additionally admits active sharees** (`ShareAccess.readOrShared` — the same guard re-run for the sharer with the HR role stripped, see "Document sharing" in `.claude/docs/authorization-resources.md`); write preambles never do.
- **THE CHAIN RULE (v2.33.0)** — the app-wide convention that settles "direct or chain?" once: **any right a manager holds by virtue of the management relationship extends to every manager up the TRANSITIVE chain** (the substitute story — someone above can always act when the direct manager is unavailable). Applied to: days-off delete (v3.9.0 — the accept/reject/cancel successor), corrections writes, record-on-behalf, allowance; 1:1/goal/review CREATE (the creator becomes the stored `manager_id`; a review create is first-writer-wins via the one-per-(subordinate, period) 409); career-position writes; team-KPI management; every chain read. Two carve-outs that NEVER widen: **authorship rights** (the stored `manager_id`/`provider_id` on a document — 1:1/goal/review writes, feedback writes: the chain may read, only the author writes) and **DRAFT privacy** (a goal/review DRAFT stays private to its author pair — CALIBRATION is where upper managers join; the pair may still SHARE their own DRAFT — v4.8.0, intended: an own-right reader shares with whoever they choose — while chain managers cannot, since they cannot read it). **Team structure is the third boundary: it is ADMIN territory, not a management right** (see the teams rules in `.claude/docs/authorization-resources.md`), so the rule does not apply there. Notification fan-outs deliberately do NOT widen with the rights (a new days-off entry pings the owner's teammates and their direct managers only — the chain right is pull, not push, unchanged by the v3.9.0 lifecycle removal), and no substitute-acted heads-up is minted (the owner is simply one recipient of the `{person, startDate, endDate}` fan-out — no actor is named). All the chain walks live in `teams/ManagementChain.kt` and exclude the starting user, so "self" never qualifies via the rule.
- **Resource rules** — the per-endpoint rule list (users, career, teams, feedbacks, 1:1s, goals, team KPIs, reviews, days off, holidays, dashboard, pulse, impact log, succession, sharing, integration clients, templates, dictionaries, notifications, alerts) lives in **`.claude/docs/authorization-resources.md`** — a MANDATORY read before adding or changing any route guard, read preamble or capability flag, or reasoning about who may read/write a resource.
- **Existence disclosure (403 vs 404) — deliberate policy (API-ERR-006)**: `GET /users/{id}` guards **before** reading, so a non-admin probe gets a uniform 403 whether or not the id exists; feedback and notification GETs read **before** guarding (missing → 404, existing-but-forbidden → 403), so an id probe can learn that a record exists (never its content or parties). Accepted knowingly: ids are sequential (existence is no secret) and the feedback read matrix already deliberately reveals existence-without-content to requesters. New resources should pick one of these two idioms consciously rather than mixing them. **The ordering rule has one registered exception (v3.24.0/v3.25.0, checkup #37 L4)**: on the LIST endpoints the shape 400s — `view`/`scope` vocabulary, the auditor `userId`/`teamId` pairing rules, `includeIndirect`, paging and sort — deliberately run BEFORE the role gate, so a malformed auditor request is a 400 for HR and non-HR alike and the parameter vocabulary is not a role oracle (`infra/paging/QueryParams.kt` says so at `uintOnlyForView`; `requireAuditListAccess`/`requireAuditScopeListAccess` then gate the read and write `hr.list`). **A second registered exception (v4.10.0, decision D1):** `GET /api/v1/performance-reviews/share-candidates` returns another chain manager's review DRAFT as a stub (existence + the author's NAME, never id/ratings) to the managers above it — see "Mass share" in `.claude/docs/features/performance-reviews.md`. It is only the MUTATING routes' payload validators that sit AFTER the guard, where 403 wins over 400. Which shape 400s precede the gate therefore differs per route by construction — the team-KPI list parses its filters first because the guard needs `filter.teamId` for the audit event, while the performance-review list (both auditor views, v4.3.0) and the three days-off auditor surfaces — the entries list, budgets and the calendar — parse EVERY shape parameter (view/scope, `userId`/`teamId` pairing, `includeIndirect`, paging, the date bounds and filters) first and gate last (the entries list and calendar since v4.0.1).
- **Exceptions**: `UnauthorizedException` (→ 401), `ForbiddenException` (→ 403), and `NotFoundException` (→ 404) are mapped in `plugins/ErrorHandling.kt`. **All error bodies are RFC 7807 `application/problem+json` (API-ERR-001/002)** (`ProblemDetail{type,title,status,detail,instance}`) — emit them via the `ApplicationCall.respondProblem(status, detail)` helper (it uses an explicit `TextContent` so ContentNegotiation does not relabel the media type as `application/json`). `StatusPages` routes `BadRequestException`→400 (**with fixed vocabulary for converter failures**, v2.35.0/MT-007: a `ContentConvertException` anywhere in the cause chain — ContentNegotiation's malformed-JSON wrap, whose raw message carries the target FQCN — answers "Request body is invalid or does not match the expected schema", and the Resources decode wrap "Can't transform call to resource" answers "Path or query parameter is malformed"; our validators' own messages, cause-less, pass through), `CannotTransformContentToTypeException`→400 (v2.34.0 — a body-less/Content-Type-less POST never enters ContentNegotiation, so it isn't wrapped in BadRequestException and used to escape to the 500 catch-all; deliberately NOT the abstract ContentTransformationException parent, which would mislabel a future 415), `PayloadTooLargeException`→413 (see security-details), `UnauthorizedException`→401, `ForbiddenException`→403, `NotFoundException`→404 (**the route 404 convention**: read preambles and zero-row mutation results `throw NotFoundException("<Resource> not found")` — never a hand-rolled `respondProblem(NotFound, …)` + return; the shared `readGuardedX`/`writeGuardedX` route preambles return non-null or throw), `TooManyRequestsException`→429 (the login lockout — thrown, never `respondProblem`ed directly, see below), unique-violation→409, and a catch-all `Throwable`→500 (logged) through that helper; a `status(TooManyRequests)` handler additionally gives the per-IP `RateLimit` plugin's bodiless 429 a generic problem body — **that handler rewrites any non-StatusPages 429**, which is why caller-specific 429s must go through the exception (handled calls are marked and skipped) — and a sibling `status(MethodNotAllowed)` handler (v2.35.0/MT-004) gives routing's bodiless wrong-method 405 a problem body too (no `Allow` header — Ktor doesn't surface the allowed-method set; registered in the guidelines' API-ERR-002 table; test with the default client, the conformance plugin would rightly flag the out-of-spec operation). A pre-routing intercept in `configureErrorHandling` additionally 400s any `/api/` path with a negative-integer segment (v2.35.0/MT-005 — the Resources plugin's parameter decoder maps `UInt` via `decodeInt().toUInt()` (JSON bodies are unaffected, pinned in `PayloadValidationTest`), so `/users/-1` used to WRAP to 4294967295 and flow into the normal lookup instead of failing as the spec's `minimum: 0` promises). The JWT `challenge` in `plugins/Security.kt` also calls `respondProblem` (it runs outside `StatusPages`). **A blocklist lookup that THROWS inside the JWT `validate` block (v3.16.2 — database unreachable, pool acquire timeout) is an outage, not a bad token:** Ktor's JWT provider turns any throw out of `validate` into a plain challenge, so `validate` stashes the cause on the call (`BlocklistFailureKey`) and the challenge answers the catch-all's logged `500` (`respondInternalError`) instead of `401` — the SPA reads a `401` as session expiry and would sign the user out over a transient outage (measured during the v3.16.1 pool work: 7 of a 120-request burst answered `401` that way). A malformed/expired/wrong-audience token never reaches the lookup and stays the uniform `401`. Pinned by `BlocklistOutageTest`. Test HTTP clients must register the `application/problem+json` content type (`json(contentType = ContentType.parse("application/problem+json"))`) to decode error bodies with `body<ProblemDetail>()`.
- **Tests**: `server/src/test/kotlin/AuthorizationTest.kt` covers the 401/403 paths and the full `FeedbackVisibility` matrix. The shared `TestUsers.seed` helper defaults to `roles = setOf(UserRole.ADMIN)` so older tests keep working without modification; pass `roles = emptySet()` when you need a non-privileged caller.
